## Q5: 제안 조건

필수 사실은 통과 수/검사 수다. "제안"은 덧붙인 제안 요청에 답한 run 수, "제안 턴"은 그 요청에 답하느라 쓴 토큰의 중앙값이다. 토큰은 run 전체
(비캐시·캐시 입력과 출력)의 중앙값이다. 무요청은 E4의 A run(반복 3회)이다. 성공은 자동 채점이고 중대 오판 검사의 확정을 반영하지 않았다.

| 모델 | 과제 | 무요청: 성공 · 사실 · 토큰 | 요청: 성공 · 사실 · 토큰 · 제안 · 제안 턴 | 상시: 성공 · 사실 · 토큰 · 알림 |
|---|---|---|---|---|
| gpt-6.1-sol | T07 | 1/3 · 5/9 · 67k | 3/3 · 9/9 · 98k · 3/3 · 13k | 3/3 · 7/9 · 95k · 0 |
| gpt-6.1-sol | T08 | 0/3 · 8/9 · 70k | 0/3 · 8/9 · 102k · 3/3 · 13k | 0/3 · 8/9 · 80k · 0 |
| gpt-6.1-sol | T12 | 0/3 · 6/9 · 328k | 1/3 · 8/9 · 594k · 3/3 · 138k | 0/3 · 6/9 · 434k · 0 |
| Qwen3.8 27B | T07 | 3/3 · 6/9 · 146k | 1/3 · 6/9 · 166k · 3/3 · 19k | 3/3 · 6/9 · 101k · 0 |
| Qwen3.8 27B | T08 | 1/3 · 7/9 · 130k | 1/3 · 9/9 · 160k · 3/3 · 34k | 2/3 · 9/9 · 98k · 0 |
| Qwen3.8 27B | T12 | 0/3 · 8/9 · 1,531k | 0/1 · 3/3 · 7,375k · 1/1 · 1,296k | 0/1 · 2/3 · 1,763k · 0 |

- **필수 사실이 무요청보다 낮은 칸은 Qwen T12의 상시(반복 1회) 하나다**: 2/3, 무요청은 8/9(같은 반복 1은 3/3). 기준에는 편차의 허용이 없으므로
  이 칸은 기준을 채우지 못한 것으로 적었다. 소유자가 아래 사실로 편차로 수용했다(2026-11-21, 대화).
  - 놓친 검사는 `timepoints` 하나다. 무요청 반복 3도 같은 검사를 놓쳤다(반복 1·2는 3/3).
  - 상시 조건이 모델에 주는 것은 시스템 프롬프트의 8 B 차이뿐이다(아래 요청 크기). 제안 후보·알림 기록은 생기지 않았고 제안을 위한 모델 호출도 없었다.
  - Qwen T12는 반복 1만 돌리기로 한 0.32.0의 소유자 결정을 그대로 썼다. 0.32.0의 같은 칸은 3/3이었다.
- **성공 대신 필수 사실을 판정에 썼다**(0.32.0과 같음). Q5의 새 run에서 중대 오판 검사가 걸린 7건을 사람이 확정하지 않았기 때문이다(아래).
- **큰 제안 턴**: gpt T12(138k), Qwen T12(1,296k). 제안 요청에 답하는 턴에서 모델 요청이 여러 번이었다(상태 조회·파일 읽기).
  요청마다 T12의 긴 대화가 입력에 다시 들어가 토큰이 커졌다. Qwen T12 요청의 run 전체는 7,375k이고 호출 100번이다.
  요청한 사람이 고르는 비용이며, 무요청·상시 조건에는 그 턴이 없다.

## Q11: 도구 표면

`default`는 E4의 A run(반복 3회), `coding`·`analytics_read`는 반복 1회다. 원시 읽기는 kit의 기록 파일(journal, run 기록)을 기본 도구로 직접
읽은 호출이다. 호출은 중앙값, 오류·인자 오류·원시 읽기는 합이다. 표면마다 run 수가 달라(3과 1) 합을 그대로 견주지 않는다.
`default`의 성공은 E4의 중대 오판 확정을 반영한 값이고, 좁은 표면의 성공은 자동 채점이다.

`coding`의 T05는 두 모델 모두 실패했다. 필수 사실은 2/2이고, 중대 오판 검사(gpt `unchanged-claim`, Qwen `lost-claim`)가 걸려서다. 사람이 확정하지 않았다.
E4의 T05에서 같은 모델·같은 검사로 걸린 세 건(gpt V `unchanged-claim` 2, Qwen A `lost-claim` 1)은 모두 검사의 오판으로 확정됐다.

### 요청 크기

aelix 0.1.0b2는 요청 본문을 내지 않는다. 그래서 같은 aelix·표면·checkout(`84433ab`)의 dry run으로 쟀다. 하네스의 가짜 모델 서버가
aelix의 첫 요청 본문을 읽는다. 바이트는 UTF-8이다. 시스템 프롬프트에는 그 과제의 프로젝트 맥락이 들어가므로 과제마다 다르다.

| 표면 | 도구 수 | 도구 schema | 시스템 프롬프트(T03) | 첫 요청 전체(T03) |
|---|---|---|---|---|
| `default`(aelix 8 + 확장 6) | 14 | 15,575 B | 22,543 B | 38,120 B |
| `coding` | 10 | 12,871 B | 22,336 B | 35,318 B |
| `analytics_read` | 7 | 10,488 B | 19,651 B | 30,318 B |
| 순정(aelix만, T06) | 8 | 5,795 B | 6,618 B | 12,580 B |

- 확장의 도구 여섯 개가 schema에 9,780 B를 더한다.
- 제안 조건은 요청 크기를 거의 바꾸지 않는다. T07의 첫 요청은 무요청 27,133 B, 요청·상시 각 27,141 B다(시스템 프롬프트의 8 B 차이).

- **과제**:
  - Q5: T07·T08·T12를 기본 표면에서 제안 요청(`requested`)과 상시(`always_on`)로 3회 돌렸다. 두 조건은 반복마다 순서를 바꿨다.
    Qwen T12는 반복 1만이다(0.32.0의 소유자 결정을 그대로 씀).

- **결과**: gpt 26 run(성공 14, 실패 12), Qwen 22 run(성공 13, 실패 9)이 모두 실행됐다. `error`·`not_run`은 0이다.

  포함)를 읽었다. 원인은 [E4 기록](2026-11-21-issue-24-product-eval.md#작업-루트-밖)과 같다(fixture에 남은 하네스 python의 경로, [#217](https://github.com/handochan/aelix-analytics/issues/217)).

## 측정하지 않은 것

- 고정한 모호·유사 요청에서의 도구 선택 정확도, 새 도구를 대안으로 둔 비교(BETA §3의 도구 표면 비교 가운데).
- 실제 세션에서 상시 조건의 문턱 판정과 알림(이 run들에서는 제안 후보 기록이 생기지 않았다). 알림의 발행·창·취소는 결정적 시험으로만 확인했다.
- 제안의 유효성·중복(BETA §3), 알림 뒤 사람이 요청하지 않은 상세 검토 0회와 표면별 유효 제안률(ADR-0008 결정 9), 등록·보류 예제 각 1개
  (BETA §2의 Q5 행). 이 기록의 제안 요청 검사는 답했는지만 본다.
- Qwen T12의 반복 2–3(소유자 결정), 좁은 표면의 반복 2회 이상.
- 실제 모델 run의 요청 본문(위 바이트는 dry run의 첫 요청). 로컬 Qwen([설계](../design/PRODUCT-EVALUATION.md) O10).
