# Issue #13 표식 판정과 쓰기 게이트 측정(PR ①) — 2026-10-08

[#13](https://github.com/handochan/aelix-analytics/issues/13)의 첫 구현 PR ①(kit 0.7.0)은 디렉터리를 두 표식(`analytics.json`·`lab.json`)으로
판정해 모든 쓰기 진입점이 첫 부수 효과 전에 거절하게 하고, 새 writer가 쓸 `analytics.run/2`·`analytics.dataset/1`의 정의와 읽기,
`analytics.event/2` 기록의 표시를 더합니다. 새 기록 가족의 정의와 쓰기 차단을 더하는 기록 형식 PR이므로 운영 정책의 측정 기록이며,
[설계](../design/RECORD-WRITER-AND-MIGRATION.md) 12절이 이 기록에 더한 키 `entry_points`(T8의 진입점 × 디렉터리 상태), `reader`(예제 여섯과
새 가족 예제의 판정), `gate_cost`(쓰기 한 번에 더해진 시간)가 있습니다. 개발 기기(macOS)의 값이고, Linux·Windows의 CI 칸은 PR을 연 뒤의
실행으로 채웁니다(지금 `pending`). 모든 값과 JUnit 파일의 sha256은 [2026-10-08-issue-13-gate.json](2026-10-08-issue-13-gate.json)에 있습니다.
계약에 반영한 것은 [CONTRACTS.md](../CONTRACTS.md) A·B("표식 판정과 쓰기", "프로젝트 찾기")·C·D·E·F1(kit 0.7.0)·G입니다.

이 기록은 구현 리뷰(독립 1회·Codex 1회)의 처분 `364bb1b` 뒤에 다시 재고, 수정 diff 확인의 처분 `8e70acd`(런처·`bin/analytics`의 `open`,
`marker_invalid`의 hint) 뒤에 한 번 더 잰 것입니다. 처음 잰 코드 `634479b`의 값은 JSON의 `first_measure`에, 둘째 `364bb1b`의 값은
`second_measure`에 남겼습니다. 첫 기록이 journal 쓰기의 판정을 두 번이라고 적은 것은 틀렸습니다(세 번, 아래 "쓰기에 더해진 시간").

`unsupported`(`unknown_version`)로 세고 Visualization 키의 버전이 1개, 데이터셋 0개입니다.
헤드는 `/2` run을 읽어 버전이 2개(`/1`·`/2`가 같은 키)이고 가져오기 기록을 읽습니다. 데이터셋은 표식이 고릅니다: 이 예제(`lab.json`)에서는 두
kit 모두 0개이고(`lab.json` 프로젝트의 `data/imported/`는 사람의 디렉터리), 같은 예제의 표식을 `analytics.json`으로 바꾸면 헤드가
`data/imported/fresh.parquet`(`imported`)을 목록에 넣습니다. 첫 측정의 헤드는 `lab.json` 예제에서도 그것을 넣었고, 그것이 리뷰가 찾은 회귀의
모양입니다. 위 예제들의 판정은 둘째 측정(`364bb1b`)의 헤드와 같습니다.

`lab.json` 프로젝트의 `data/imported/`에 사람이 둔 `photo.meta.json`(`{"camera": "x"}`)과 `notes.meta.json`(JSON 아님): 기준은 둘 다 읽지
않습니다. 헤드는 가져오기 기록을 두 자리에서 다 읽으므로(설계 5.3절) `photo.meta.json`을 `unsupported`(`unknown_family`), `notes.meta.json`을
`damaged`(`unparsable`)로 적고, 데이터셋은 기준과 같이 `data/raw/sales.parquet` 하나입니다. 수정 diff 확인이 찾은 것이고, CONTRACTS C4가 이
동작을 적습니다(코드는 바꾸지 않음).

## 쓰기에 더해진 시간(`gate_cost`)

1,000줄 journal의 lab.json 프로젝트에 `core.add_note` 200번, 노트당 평균. 기준과 헤드를 번갈아 네 번 재고 각각의 최솟값입니다(PR #76의 방법은
두 번이고, 둘째 측정에서 헤드의 값이 흔들려 네 번으로 늘렸습니다. 네 번의 값은 모두 JSON에 있습니다). 수정 diff 확인은 쓰기의 경로를 바꾸지
않았습니다(바뀐 것은 `open`과 hint 글).

| 측정 | 기준 `5829c7c` | 헤드 `8e70acd` | 둘째 측정(기준 / `364bb1b`) |
|---|---|---|---|
| 노트 한 번(ms, 최솟값) | 2.2832 | 2.3078 | 1.9309 / 2.0310 |
| 차이 | | +0.025 ms(+1.1%) | +0.100 ms(+5.2%) |
| 네 번의 범위(ms) | 2.28–2.37 | 2.31–2.56 | 1.93–2.01 / 2.03–2.18 |
| `writer.marker_state` / `core.admit` 한 번(µs, 헤드) | | 23.98–30.07 / 25.78–36.81 | 21.13–21.90 / 22.40–24.04 |
| 판정 수: `core.add_note` / `core.append_event` 한 번 | | 3 / 3 | 3 / 3 |
| 계속 읽지 못하는 표식(권한 000)의 판정 한 번(s) | | 2.180–2.208(교체 예산 2.0) | 2.088–2.105 |

이번에는 기준과 헤드가 모두 둘째 측정보다 약 0.35 ms 느렸고(같은 기기, 원인은 살피지 않음) 헤드의 셋째·넷째 값이 2.54–2.56 ms로 흔들렸습니다.
최솟값의 차이(+0.025 ms)는 판정 세 번의 값(이번 값으로 약 0.07–0.09 ms)보다 작으므로 흔들림 안의 값이고, 라운드마다의 차이는 +0.025–+0.223 ms입니다. 그래서
게이트의 비용은 둘째 측정의 값(+0.100 ms)과 판정 한 번의 값으로 읽습니다.

journal 쓰기는 판정을 세 번 합니다: `add_note`·`append_event` 자신의 판정(거절이 검증 오류보다 먼저), `journal_lock`의 잠금 전 판정(잠금 파일이
첫 부수 효과), 잠금 안의 판정. `writer.marker_state`를 감싸 센 값입니다. kit 명령줄의 `record`는 분석 라이브러리를 import하기 전에 한 번 더,
그 앞의 맥락 동기화가 두 번 더 판정합니다. 판정 한 번은 표식 두 개의 `stat`과 작은 JSON 하나의 읽기라 이 기기에서 약 21 µs이고, 세 번이면
약 0.065 ms입니다. 나머지 차이는 기준의 네 값(1.93–2.01 ms)이 흔들리는 폭 안입니다. 처분은 노트 쓰기의 경로를 바꾸지 않았습니다(첫 측정
`634479b`: 1.8828 → 1.9408 ms, +0.058 ms. 그때 기록은 판정을 두 번이라고 잘못 적었고, 시간은 세 번을 모두 포함한 값이었습니다).

읽지 못하는 표식은 설계 4.3절대로 교체의 재시도 예산 안에서 다시 읽으므로 판정 한 번이 약 2.1초입니다. aelix 확장의 `tool_execution_end`
hook은 그런 프로젝트에서 판정을 두 번 하므로 도구 호출마다 약 4초가 걸린다고 봅니다(판정 수에서 낸 값, aelix 세션에서는 재지 않음, CONTRACTS G).
