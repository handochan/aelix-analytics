# Skill 제안의 선택·임계값·비용 정책

작성: 2026-09-18 · 개정: 2026-10-05 · 상태: 설계 제안. 요청 시 기본값, 계수 단위와 베타 상시 모드의 범위는 [ADR-0008](decisions/0008-reuse-proposal-counting-and-deterministic-always-on.md)로 채택했다.
아래 설정은 아직 구현에 없는 후보 계약이다.
[제품 비전](PRODUCT.md)의 분석가 중심 원칙과 [재사용 수명주기](DESIGN-CONTINUITY-AND-REUSE.md#4-재사용-제안에서-라이브러리skill까지)를 구체화한다.
내부 구현은 [아키텍처](ARCHITECTURE.md)의 ProposalPolicy 경계로 분리한다. 정책을 바꿔도 사용자 모드·거절·빈도·기록의 의미는 유지해야 한다.

명칭·영어 기본 UI는 [용어집](TERMINOLOGY-AND-LANGUAGE.md)을 따른다. 표시명은 On demand / Automatic suggestions이며 저장 모드 `on_demand` / `always_on`의 의미는 유지한다.
자동 모드의 선택과 실제 제안 기준 통과, 제안 수락과 skill 등록·사용을 각각 구별한다.

## 1. 분석에 집중할 선택권

분석가는 재사용 자산 관리보다 당장의 질문에 답하는 일에 집중할 수 있어야 한다.
재사용 제안이 유용해도 매 턴의 제안·검토·추가 모델 호출을 기본 부담으로 만들지 않는다.

| 모드 | 활성화 | 자동 관찰·검토 | 사용자에게 제안 |
|---|---|---|---|
| `on_demand` | **기본값**. 사용자가 제안 검토를 요청할 때만 실행 | 제안을 위한 자동 후보 탐색·점수화·추가 모델 호출 없음 | 요청한 범위에서만. 적합한 후보가 없으면 없다고 답함 |
| `always_on` | 사용자가 프로젝트 설정으로 선택. 호스트 세션이 있으면(Aelix) 그 세션 동안만 선택할 수도 있음 | 모델 호출 없이 이미 기록된 근거로 사전 검사·판정. 모델 기반 상세 검토는 사람이 대화에서 요청한 턴에서만 | 기록된 후보가 아래 모든 기준과 빈도 규칙을 통과할 때만 분석의 자연스러운 경계에서 짧게 알림 |

상시 모드는 모든 skill 본문을 프롬프트에 싣거나 매번 skill을 만들라는 뜻이 아니다.
발견·결정·맥락·근거의 기록은 두 모드에서 동일하게 계속한다. 제안을 위한 메모리 재검토는 선택 기능이며 기본 기록과 비용을 구별한다.
등록된 skill을 현재 분석에 사용하는 것은 별도의 사용 정책이다. 기존 Aelix의 관련 시 선택·명시적 호출 설정을 존중하며 제안 모드로 바꾸지 않는다.

설정 우선순위는 명시적 세션 선택 → 프로젝트 설정 → 기본값이다. 현재 모드와 설정 출처를 상태 화면에서 확인할 수 있게 한다.
세션 선택은 호스트 세션이 있는 Aelix에서만 사람 명령으로 하고 범위(`session`)와 함께 journal에 남긴다. 사람용 CLI는 프로젝트 설정만 쓴다.
세션 선택은 현재 세션 파일과 같은 `session`의 마지막 모드 이벤트로 복원한다. 같은 파일을 여는 `/reload`·`/resume`은 그 모드를 유지하고, 새 파일을 만드는 `/new`·`/fork`는 프로젝트 설정을 쓴다.
모드를 바꾸기 위해 새 모델 도구를 추가하지 않고 프로젝트 설정·기존 사람 명령의 설정 경로를 사용한다.
상시에서 요청 시 모드로 바꾸면 대기 중인 자동 검토·알림을 취소한다. 작성해 둔 후보와 근거는 보존한다.

## 2. 상시 모드의 제안 문턱

점수만으로 자동 제안을 허용하지 않는다. 먼저 다음 조건을 모두 확인한다.

1. 원래 run·코드·발견 등 확인 가능한 출처가 있고, 실제 일반화할 처리 또는 분석 방법이 있다.
2. 기존 후보·등록 skill과 같은 내용이면 새 제안 대신 기존 항목의 근거를 연결한다. 단순 rerun은 독립된 재사용 사례로 세지 않는다.
3. 적용 조건과 기대 효과를 설명할 수 있다. 단순한 코드 길이·호출 횟수·문구 반복은 가치의 증거가 아니다.
4. 거절·보류·이전 알림·cooldown 상태와 사용자가 선택한 제안 방식이 허용한다.

그다음 아래 점수를 근거와 함께 계산한다. **8/10 이상**을 초기 자동 제안 임계값으로 제안한다.
이는 논문이 검증한 수치가 아닌 제품 가설이며, 실제 유효 제안률·방해·비용 측정으로 조정한다.

| 항목 | 점수 | 해석 |
|---|---:|---|
| 재사용 수요 | 0–3 | 0: 근거 없음, 1: 한 사례의 추정, 2: 사용자가 반복 필요를 명시, 3: 서로 다른 입력·질문에서 반복 사용 관측 |
| 근거·검사 | 0–3 | 0: 출처 없음, 1: 출처만 있음, 2: 성공 실행과 결과 검사, 3: 다른 입력 또는 경계 조건 검사까지 있음 |
| 적용 범위 | 0–2 | 0: 설명 불가, 1: 조건 또는 제외 조건만 있음, 2: 둘 다 명확 |
| 순효과 | 0–2 | 0: 개선 근거 없음, 1: 구체적인 절감·오류 방지 기대, 2: 작성·유지 비용을 고려한 관측 효과가 있음 |

총점 외에도 `재사용 수요 ≥ 2`, `근거·검사 ≥ 2`, `적용 범위 = 2`, `순효과 ≥ 1`을 요구한다.
점수는 성공 확률이나 분석의 진실성 수치가 아니다. 평가 근거를 확인할 수 없으면 해당 점수를 주지 않는다.
상시 제안 임계값을 넘지 못한 후보를 매 턴 “참고 제안”이라는 이름으로 노출하지 않는다.

### 모델 없는 판정의 술어

베타의 `always_on`은 위 조건과 점수를 다음 술어로만 매긴다([ADR-0008](decisions/0008-reuse-proposal-counting-and-deterministic-always-on.md)). 같은 기록이면 어느 구현이든 같은 점수를 낸다.
항목마다 조건을 만족하는 가장 높은 단계를 주고, 확인할 수 없으면 0점이다. 필드 이름과 검사·효과 기록의 형태는 ADR-0008의 기록 요구를 따른다.

- 근거는 확정 연결만 센다: 작성자가 버전까지 지정했고 관측·선언 근거이며 해석이 `resolved`인 참조다. 이름만 준 참조의 추론 결박과 버전 없는·모호한·누락된·내용이 바뀐 참조는 어떤 항목도 올리지 않는다(#4의 기록 계약 [ADR-0006](decisions/0006-common-record-contract.md)).
- 독립 사용의 수는 후보를 썼다는 관측(후보가 코드로 기록한 파일이 run의 `script`·`modules`에 있음)이나 확정 연결이 있고, 상태가 `ok`이며 재실행(`rerun_of`)이 아닌 run들이 가진 서로 다른 (스크립트 경로, 입력 집합의 경로·sha256)의 수다.
- run의 `ok`는 실행 성공이며 검사 통과가 아니다. 검사는 결과(`passed`·`failed`), 검사한 코드 버전, 검사 run의 확정 연결을 가진 검사 기록만 센다. 통과 검사는 결과가 `passed`이고 검사 run이 `ok`인 것이다. 코드 버전이 바뀌면 이전 버전의 검사를 세지 않는다.
- 사람의 표시는 작성 주체가 사람으로 기록된 것(#13)만 센다. 출처 기록이며 신원 인증이 아니다.
- 글 필드(반복되는 문제·적용 조건·제외 조건·기대 효과)는 비어 있지 않은지만 본다. 내용이 명확한지는 판정하지 않으며, 알림은 이를 작성자의 기록으로 보인다.

| 항목 | 3 | 2 | 1 | 0 |
|---|---|---|---|---|
| 재사용 수요 | 독립 사용 2 이상 | 사람이 반복 필요를 표시 | 독립 사용 1 | 그 밖 |
| 근거·검사 | 현재 코드 버전의 통과 검사 가운데 원래 run과 입력 집합이 다르거나 경계 조건으로 표시한 것이 있음 | 현재 코드 버전의 통과 검사가 있음 | 원래 run·코드·발견의 확정 연결만 있음 | 그 밖 |
| 적용 범위 | — | 적용 조건과 제외 조건이 모두 있음 | 하나만 있음 | 없음 |
| 순효과 | — | 작성·유지 비용과 함께 측정한 효과 기록이 있음 | 추정으로 표시한 기대 효과 기록이 있음 | 그 밖 |

필수 조건 1은 원래 run·코드·발견 가운데 하나에 확정 연결이 있고 반복되는 문제와 제안 산출물 종류가 기록되었는지, 2는 3절의 정체성 규칙과 독립 사용의 정의, 3은 `적용 범위 = 2`와 `순효과 ≥ 1`, 4는 3절의 이력·창·모드 규칙으로 판정한다.
`순효과 ≥ 1`은 추정으로 표시한 기대 효과 기록으로 채운다. 관측하지 않은 효과는 순효과 2를 받지 않는다(2026-10-05 소유자 결정).

요청 시 검토에서는 초기 아이디어도 미검증 후보로 설명할 수 있다. 이 경우에도 등록·검사 완료 상태로 올리지 않는다.
`proposed → trial → validated → registered`의 승격 요건은 제안 모드와 관계없이 동일하다.

## 3. 빈도·중복·중단 규칙

횟수는 프로젝트 기록으로 센다([ADR-0008](decisions/0008-reuse-proposal-counting-and-deterministic-always-on.md)). 호스트 세션과 checkpoint는 계수 단위가 아니다.
사람용 CLI에는 호스트 세션이 없고, 세션을 새로 열 때마다 알림 기회가 늘어나서는 안 되기 때문이다.

| 동작 | 단위·한도 | 이력 |
|---|---|---|
| 요청 시 검토 | 명시적 요청 1건이 검토 1건. 자동 한도·창과 무관하고 창을 쓰지 않음 | 요청을 처리한 kit 동작이 돌려준 후보를 `trigger=requested` 상태 이벤트로 씀(모델이 따로 쓰지 않음). 같은 후보의 자동 재알림을 막음 |
| 자동 사전 검사·판정(`always_on`) | 마지막 검사 뒤 새 기록(journal seq·run 완료)이 있을 때와, 창이 끝난 뒤의 첫 발행 경계에서 증분 실행. 모델 호출도 횟수 한도도 없음 | 진행 위치·대기 집합·판정 통계는 재계산 가능한 캐시 |
| 자동 알림(`always_on`) | 프로젝트당 롤링 24시간에 최대 1회 발행. 마지막 자동 발행 이벤트의 기록 시각부터 셈 | 발행 전에 journal 잠금 안에서 `trigger=automatic` 상태 이벤트를 씀 |

24시간은 검증 전 초기값이다. 빈도 설정은 이 창을 기본값 이상으로 두거나(`cooldown_hours`) 요청 시 모드로 바꿔 자동 알림을 멈추는 쪽만 받는다.
이 빈도·모드 제어는 분석 방해를 줄이기 위한 동작 정책이며, 토큰 사용량의 측정 목표와는 별개다.
분석 오류 처리·실행 중·연속 탐색 중에는 끼어들지 않고, 질문이 마무리되거나 사용자가 결과를 검토하는 경계에서만 알린다.

자동 알림을 발행하는 표면은 다음뿐이다.

- Aelix: 에이전트 턴이 끝난 뒤 사전 검사하고, 다음 턴을 시작할 때 그 턴의 맥락 블록에서 발행하거나 사람 명령 `/analytics`의 상태 출력에서 발행한다.
- 사람용 CLI: 텍스트 `status`(`analytics status`, 런처가 `--text`로 부름)에서만 발행한다.

kit의 JSON `status`, `context`, 모델 도구, Workspace는 기록된 후보와 발행한 알림을 목록으로만 보이고 발행하지 않는다. 에이전트 요청으로 기록된 CLI 호출(#13)도 같다.
맥락 블록은 모델의 system prompt다([현재 계약](CONTRACTS.md) A). 거기에 낸 알림은 모델에 보이는 안내이며 사람에게 보였다고 기록하지 않는다.
사람용 상태 화면(`/analytics`, 텍스트 `status`, Workspace의 Insights)은 자동으로 발행한 알림 가운데 아직 수락·거절·보류하지 않은 것을 보인다. 맥락 블록으로 낸 알림도 이 경로로 사람에게 닿으며, 이를 위해 모델 턴을 따로 시작하지 않는다.

후보의 정체성은 후보 ID(논리 키)와 후보 사이의 명시적 중복·통합 관계다. 후보를 고친 새 버전은 같은 후보다.
같은 주제·핵심 방법·적용 조건이면 새 후보를 쓰지 않고 기존 후보에 근거를 연결하거나 중복·통합 관계를 남긴다. 원래 후보와 그 이력은 지우지 않고, 묶인 후보들의 알림·거절·보류 이력을 함께 센다.
자동 경로는 내용의 같음을 판정하지 않는다. 대신 확정 근거가 모두, 이미 알림·거절·보류 이력이 있는 다른 후보의 확정 근거에 드는 후보는 자동으로 알리지 않고 요청 시 검토에서 중복 의심으로 보인다.
세션을 새로 열거나 파일명을 바꿨다는 이유로 새 후보처럼 알리지 않는다.

같은 후보는 새 근거가 있을 때만 자동으로 다시 알린다. 새 근거는 그 후보(와 관계로 묶인 후보)의 마지막 알림·거절·보류 이벤트가 남긴 근거 버전 집합에 없던 확정 근거가 2절의 점수 항목 하나 이상을 그때의 단계보다 올린 것이다.
같은 근거의 재참조, 후보 문구·적용 조건의 수정, 추론 결박, 독립 사용이 아닌 run, 다른 코드 버전의 검사는 새 근거가 아니다. 검사나 적용 범위의 변화는 그것을 보이는 새 확정 근거(예: 다른 입력의 통과 검사)가 점수 항목을 올릴 때만 센다.
거절·보류한 후보는 그때 남긴 사유 항목(2절의 필수 조건·점수 항목)을 새 근거가 올릴 때만 자동으로 다시 알린다. 사유 항목이 없거나 그 밖의 경우에는 사용자의 명시적 재검토 요청으로만 보인다.
자동 검토에서 제안 없음이 반복되어도 기준을 낮추거나 추가 모델 호출을 계속하지 않는다.

자동 알림은 제안의 제목·이유·근거 ID를 짧게 보여 준다. 긴 skill 본문과 생성 코드는 사용자가 상세를 열거나 요청할 때 제공한다. 상세를 여는 읽기는 모델을 부르지 않는다.
aelix UI 알림 같은 새 호스트 표면을 쓰면 [현재 계약](CONTRACTS.md) A가 바뀌므로 그 갱신과 headless 대비를 함께 한다.
정적 HTML은 후보와 상태를 보여 주며, 읽기만으로 설정 변경·등록·코드 실행을 수행하지 않는다. 기록된 후보와 발행한 알림을 목록으로 읽는 화면은 알림이 아니며 창을 쓰지 않는다.

발행한 알림, 요청 시 검토가 돌려준 후보, 거절·보류, 정책 변경의 근거는 요청 구분(`trigger`)과 함께 journal의 상태 이벤트로 남긴다.
알림 이벤트는 표면, 판정에 쓴 근거 버전 집합과 항목별 점수, 기준(`as_of_seq`), 요청 주체와 실행 수단을 담는다. 거절·보류는 사유 항목과 그때의 근거 버전 집합·항목별 점수를 담는다.
재계산 가능한 관찰 통계와 대기 집합(기준을 넘었으나 창 때문에 발행하지 않은 후보)만 캐시에 둔다. 새 세션·재시작·캐시 삭제가 cooldown이나 거절 이력을 지워 재알림을 만드는 일이 없어야 한다.
자동 알림은 발행 직전 journal 잠금 안에서 모드·창·이력을 다시 확인하고 상태 이벤트를 쓴 뒤 발행한다. 표면에 내지 못해도 다시 발행하지 않는다(중복보다 누락).
그래서 동시 요청도 같은 프로젝트의 알림 횟수를 중복 소비하지 않고, 상시에서 요청 시로 바꾸면 대기 중인 알림이 취소된다.
창이 지나면 새 기록이 없어도 다음 발행 경계에서 대기 집합을 다시 평가해, 총점이 가장 높은 후보(같으면 기준을 먼저 넘은 후보) 하나를 발행한다.
시계가 마지막 자동 발행의 기록 시각보다 앞으로 돌아가 경계가 불분명하면 창 안으로 본다. 상태 화면은 다음 자동 발행이 가능한 시각과 기다리는 이유(창·시계 역행)를 보인다.

## 4. 분석과 제안의 비용 측정

`on_demand`에서 요청하지 않은 제안을 위한 **추가 모델 호출·입력 토큰·출력 토큰은 0**이어야 한다.
분석 자체에 필요한 기록·조회 비용을 제안 비용으로 숨기거나, 반대로 제안 비용을 기본 맥락 기록에 섞지 않는다.
여기서 0은 요청하지 않은 자동 검토를 시작하지 않는 모드의 결과이며, 실행 중 토큰을 잘라내는 제한이 아니다.
공통 도구 schema와 최소 정책 지침의 고정 비용은 상시 입력 사용량에 포함해 별도로 공개한다.
요청하지 않은 후보 목록·skill 본문·재사용 검토 지침을 기본 프롬프트에 추가하지 않는다.

베타의 `always_on`은 모델을 부르지 않는다([ADR-0008](decisions/0008-reuse-proposal-counting-and-deterministic-always-on.md)). 자동 경로는 세 단계다.

1. 사전 검사: 마지막 검사 뒤의 새 기록에서 기록된 후보의 독립 사용·중복·검사 상태·거절·cooldown을 확인한다. 창이 지난 뒤의 첫 발행 경계에서는 새 기록이 없어도 대기 집합을 다시 본다. 전체 세션을 반복해서 읽지 않는다.
2. 판정: 2절의 필수 조건과 점수를 2절의 술어로만 매긴다. 후보 기록의 필드와 run 관측(스크립트·모듈의 경로와 해시, 입력, 상태)만 쓰고, 확인할 수 없는 항목은 0점이다.
3. 알림: 기준을 넘은 후보 하나를 앞 절의 표면과 빈도 안에서 발행한다. 맥락 블록으로 발행하면 그 턴의 맥락 블록에 한 번 제목·이유·근거 ID와 고정 지침 한 줄(사람에게 전하기만 하고, 사람이 요청하기 전에는 검토하지 않는다)만 넣는다. 그 바이트·토큰은 최소 정책 지침의 비용으로 따로 측정한다. 이는 검토 지시가 아니다.

기록된 후보가 없는 신호(예: 같은 프로젝트 모듈을 다른 스크립트·입력의 run이 씀)는 요청 시 검토에서 미검증 아이디어로만 보여 주고 자동으로 알리지 않는다.
알림의 상세를 여는 읽기(CLI, `/analytics`, Workspace)는 모델 호출 0회이고 이벤트를 쓰지 않는다.
모델 기반 상세 검토는 사람이 대화에서 알림을 보여 달라고 하거나 검토를 요청한 턴에서만 한다. 사람 명령만으로 모델 검토를 시작하려면 확장이 턴을 시작해야 하므로(현재 계약 A의 변경) 베타는 하지 않는다(2026-10-05 소유자 결정).
요청 시 검토는 명시적 요청(사람 명령, CLI 하위 명령, 기존 모델 도구의 명시 인자)으로 시작하고, 진입점의 이름과 인자는 #17이 Q11 측정으로 정한다. 요청을 처리한 kit 동작이 `trigger=requested` 이벤트를 쓴다.
확장은 provider·모델 API를 부르지 않고 턴을 시작하지 않는다([현재 계약](CONTRACTS.md) A).
모델이 스스로 새 후보를 찾아 알리는 자동 상세 검토는 베타 뒤 측정 결과로 따로 결정한다.

모델 기반 상세 검토의 초기 성능 비교 목표는 **검토 1건당 입력 1,024 tokens·출력 256 tokens**다. 베타에서는 사람이 요청한 상세 검토가 대상이다.
이 수치는 강제 상한이 아니며, 초과했다고 검토·제안을 중단하거나 근거와 설명을 잘라내지 않는다.
검토 횟수는 앞 절의 단위를 따른다. 선택적 모델 호출의 지침·근거 조회·출력·재시도·집계 가능한 reasoning 사용량까지 비용에 포함한다.
같은 모델 호출에 섞여 정확히 분리할 수 없으면 분리 불가 또는 추정값으로 표시한다. 미측정을 비용 0으로 표시하거나 측정 불가만으로 기능을 끄지 않는다.

분석을 우선하며, 사용자에게 끼어드는 시점과 빈도는 앞 절의 정책을 따른다.
사용자가 요청한 상세 검토는 별도 과제로 사용량을 기록한다. Aelix에서는 `trigger=requested` 이벤트를 쓴 턴의 모델 사용량을 그 요청에 기록하고, 같은 턴의 다른 작업과 나눌 수 없으면 분리 불가로 표시한다.
측정 목표는 소비·예약·이월되는 실행 잔액이 아니다.
실제 모델 context window·provider 제약은 별도로 다루며, 측정용 숫자를 API의 강제 출력 상한으로 그대로 전달하지 않는다.

설정의 개념 예시(프로젝트 표식의 `reuse_proposals`):

```json
{
  "reuse_proposals": {
    "mode": "on_demand",
    "min_score": 8,
    "cooldown_hours": 24,
    "measurement_targets": {
      "input_tokens_per_review": 1024,
      "output_tokens_per_review": 256
    }
  }
}
```

`cooldown_hours`는 프로젝트당 자동 알림의 최소 간격이며 기본값(지금 24) 이상만 받는다. 더 작은 값은 설정 검사가 오류로 보고하고, 고칠 때까지 자동 알림을 하지 않는다. 기본값으로 조용히 바꾸지 않는다.
세션·checkpoint별 한도 키는 두지 않는다.
기본 화면에는 두 모드의 선택과 자동 검토를 쉬는 설정만 노출하고, 점수·빈도의 세부값은 고급 설정으로 둔다.
`measurement_targets`는 모델 기반 상세 검토 1건의 성능 보고·비교에만 사용하며 실행 허용 여부를 결정하지 않는다.
이 설정은 형식 전환 뒤의 프로젝트 표식(`analytics.json`)에 둘 후보다. 현재 `lab.json`에 넣어도 동작하지 않으며, 도입 시 호환 reader와 설정 검사부터 구현한다.

## 5. 검증할 행동

| 상황 | 기대 결과 |
|---|---|
| 기본 모드로 여러 세션 분석 | 자동 후보 탐색·알림·추가 모델 호출 없음. 발견·맥락 기록은 유지 |
| 요청 시 후보가 없음 | 제안 없음으로 종료. skill을 억지로 생성하지 않음 |
| 상시이지만 임계값 미만 | 알림·등록 없음. 기준을 낮춰 재시도하지 않음 |
| 점수는 높지만 근거·적용 조건이 부족 | 필수 조건에서 거절 |
| 상시의 자동 판정 | 추가 모델 호출 0회. 공유 점수 fixture에서 구현마다 같은 항목별 점수. 검사 기록 없는 성공 run, 추론 결박, 재실행, 같은 (스크립트 경로, 입력 집합)의 run, 관측하지 않은 효과, 다른 코드 버전의 검사는 해당 항목을 올리지 않음. 추정으로 표시한 기대 효과는 순효과 1까지 올리고 `순효과 ≥ 1`을 채움 |
| 새 세션·재시작·캐시 삭제 뒤 같은 후보 | 기존 알림·거절·cooldown 이력 유지. 재알림 없음 |
| 후보 문구만 고치거나 같은 근거를 다시 참조 | 새 근거가 아님. 자동 재알림 없음 |
| 같은 근거로 새 ID의 후보를 씀 | 자동으로 알리지 않음. 요청 시 검토에 중복 의심으로 보임 |
| 거절·보류한 후보의 사유 항목을 새 근거가 올림 | 창이 허용하면 자동으로 다시 알림. 사유 항목이 없으면 요청으로만 보임 |
| 24시간 안에 다른 후보가 기준을 넘음 | 창이 지나기 전에는 알리지 않음. 창이 지나면 새 기록이 없어도, 캐시를 지운 뒤에도 다음 발행 경계에서 발행. 요청 시 조회에는 보임 |
| 사람용 CLI(호스트 세션 없음) | 같은 프로젝트 기록·창을 씀. 텍스트 `status`에서만 발행. 모델 호출 0회 |
| 에이전트가 CLI의 `status`·`context`나 모델 도구를 부름 | 목록만 줌. 발행하지 않고 창을 쓰지 않음 |
| Aelix에서 발행한 뒤 CLI로 이어 감 | 같은 후보를 다시 발행하지 않음. 상태 화면·Insights에 답하지 않은 알림으로 보임 |
| 맥락 블록으로 발행 | 이벤트에 표면이 남고 사람이 봤다고 기록하지 않음. 사람용 상태 화면에 답하지 않은 알림으로 보임. 사람이 요청하지 않은 상세 검토 0회(Q5 리허설) |
| 알림의 상세를 엶 | 모델 호출 시도 0회, 이벤트 없음. 모델 기반 상세 검토는 대화에서 요청한 턴에서만 하고 `requested` 이벤트와 사용량을 따로 남김. 사람 명령만으로는 시작하지 않음 |
| 명시적 요청 | 요청한 검토는 자동 창을 쓰지 않음. 돌려준 후보는 새 근거 없이 자동으로 다시 알리지 않음 |
| 적합한 후보가 여러 개 | 총점이 가장 높은 후보(같으면 기준을 먼저 넘은 후보)만 발행. 나머지는 대기 집합에 남고 요청 시 조회에 보임 |
| 토큰 측정 목표 초과 | 사용량·초과 정도·품질 효과를 기록. 초과만으로 검토·조회·제안을 중단하지 않음 |
| 토큰 계측 불가 | 미측정 또는 별도 단위로 표시. 비용 0으로 간주하거나 자동으로 기능을 끄지 않음 |
| 상시를 끄거나 두 프로세스가 동시에 알리려 함 | 대기 알림 취소. 잠금 안에서 다시 확인해 많아야 한 번 발행(중복보다 누락) |
| 시계가 마지막 자동 발행보다 앞으로 돌아감 | 창 안으로 보고 발행하지 않음. 상태 화면에 다음 가능 시각과 이유를 보임 |
| 기본값보다 짧은 `cooldown_hours` | 설정 검사 오류. 고칠 때까지 자동 알림 없음 |
| 세션 한정 모드에서 `/reload`·`/resume`, `/new`·`/fork` | 앞의 둘은 그 세션의 모드 유지, 뒤의 둘은 프로젝트 설정 |
| 제안을 받아들임 | 후보·검사·등록 단계를 지킴. 제안 수락만으로 전역 등록하지 않음 |

유효 제안률은 “표시한 제안 중 분석가가 재사용 가치가 있다고 판단한 비율”로 따로 측정한다. 분모는 발행 표면별로 나눠 세며, 맥락 블록으로만 낸 알림을 사람에게 표시한 제안으로 세지 않는다.
수락률만 높이려고 적절한 후보를 누락할 수 있으므로, 정답 후보가 있는 fixture의 회수율·중복률·중단 횟수·과제 성공·전체 토큰도 함께 본다.
근거가 충분해도 제안이 0개인 세션은 정상이다. 사용자가 요청 시 모드를 선택한 것을 품질 저하로 분류하지 않는다.
