# 공식 베타의 출시 기준과 작업 순서

작성: 2026-09-17 · 개정: 2026-09-19 · 상태: 출시 기준 제안. 이 문서는 통과 보고서가 아니다.
기존 동작·비용의 비교 기준점은 `7b205cd`로 유지한다. 제품 명칭 정리 이후의 구현 참조는 `21b6a3c`이며, 그 뒤 PR #25의 `441a501`은 문서·운영 설정 변경이다.
비교 기준점은 최신 HEAD를 뜻하지 않는다. 각 검증 결과에는 실제 검사한 commit·작업 사본의 기준을 따로 기록한다. 이 문서는 조사·설계·기여 기준이며 검증 통과 보고서가 아니다.

## 1. 출시할 약속

제품 비전은 **사람과 에이전트가 검증 가능한 분석 프로젝트를 함께 이어 가는 새로운 분석 도구·플랫폼**이다.
첫 베타는 그 출발로서 단일 로컬 프로젝트의 자유로운 Python 분석, 발견·판단·근거·이력의 지속적 기록과 조회를 제공한다.
사람이 CLI·SDK로 에이전트 없이 직접 분석을 완료하는 경로와, 사람 → 에이전트 → 사람이 같은 프로젝트를 이어받는 경로를 필수로 검증한다.
분석은 목적·현재 지표·질문을 중심으로 이어지고, 미정 정의의 구체화·여러 지표·정의 수정과 파생을 기록한다.
재사용 제안은 사용자가 선택하는 기능이며, 자동 제안 없이 분석에 집중하는 흐름도 완전한 제품 사용 시나리오다.
진행 중 분석의 팀 공유는 독립 build와 지원 대상을 명시한 첫 publish 경로까지를 범위로 둔다(2026-10-03 소유자 결정으로 확정). 원격 호스팅·공동 편집의 전체 구현을 전제하지 않는다.
분석 도중 만드는 자유 형식 보고서는 Reports에서 당시 내용·근거·버전을 보존하고, 여러 컬럼의 반복 보고서와 선택 버전 공유를 지원한다.
베타는 장기 플랫폼의 첫 검증 범위다. 초기 구현부터 [아키텍처](ARCHITECTURE.md)의 핵심 계약·교체 경계·호환성 기준을 적용한다.
공식 표면은 [용어집](TERMINOLOGY-AND-LANGUAGE.md)의 Analytics·Workspace·Visualization·Report로 통일하며 UI·템플릿은 영어를 기본으로 한다. 다국어 사용자 내용과 과거 기록은 보존한다.
“공식”은 유지관리·설치·호환성·검증 책임을 명시한다는 의미다. 샌드박스·완전 재현·분석 결론 인증을 뜻하지 않는다.

지원 플랫폼은 Linux·macOS·Windows로 확정했다([ADR-0002](decisions/0002-python-support-and-platform-scope.md)).
이는 지원 목표이며, 지원표에는 실제 설치·실행 증거가 있는 범위만 검증됨으로 적는다.
플랫폼에 따라 달라지는 잠금·기록 교체·자식 프로세스 제어·run 제한 시간과 취소는 이식 가능한 경계 뒤에 있고
([ADR-0003](decisions/0003-portable-boundaries-and-in-process-kit-loading.md)), Linux·macOS·Windows에서 실행한 범위와
Windows의 선언된 한계, 실행하지 않은 것은 [현재 계약](CONTRACTS.md)의 F·G절에 있다. 사람용 진입점은 체크아웃의 POSIX 셸
스크립트 `bin/analytics`와, Windows를 포함한 모든 플랫폼에서 설치본이 주는 `analytics`다. Windows 콘솔의 Ctrl+C·Ctrl+Break는 의사 콘솔과 고전 콘솔에서 측정했고, 사람이 누른 키와 Windows의 실제 aelix 세션은 실행하지 않았다. Aelix 호스트의 Windows 지원을 이 확장의 Windows 지원으로 옮겨 적지 않는다.
“로컬 모델 지원”도 시험한 모델·양자화·context 설정·도구 호출 경로를 명시한다.

현재 사용자가 지정한 지원 하단 기준은 **Qwen3.8 27B**다. 정확한 serving ID·버전·양자화·backend·tokenizer·실제 context 설정을 고정한 검증이 필요하다.
이 모델과 프론티어 모델의 정상 사용 설정을 주 검증 대상으로 삼는다. 8K 등의 축소 문맥 시험은 별도 진단이며 기본 실행 한도나 하단 모델의 정의가 아니다.
더 작은 모델의 실행을 차단하지 않고, 모델 발전에 따라 릴리스별 기준을 재검토한다.
[참고 세션](REVIEW-REFERENCE-SESSION-2026-09-18.md)은 GLM-5.3-Flash의 기록이며 Qwen 지원 통과 증거가 아니다.

## 2. 첫 베타의 필수 게이트

수치가 있는 항목은 초기 수용 목표다. 구현 전에 fixture·장비·모델·측정법을 확정하고, 조정하면 이유를 남긴다.
토큰·문자 수 목표는 **성능 측정 기준**이다. 수치 초과만으로 실행을 제한하거나 출시를 실패 처리하지 않는다.
계측의 정확성, 과제 품질·비용 비교, 필요한 정보에 계속 접근할 수 있는지를 검증한다.

### 아키텍처 경계의 검증

[ADR-0001](decisions/0001-evolvable-platform-boundaries.md)(2026-10-03 채택, 채택은 구현 완료가 아님)의 구조를 따르는 구현은 다음을 확인한다.
항목별로 맡는 Issue는 그 ADR의 [구현에서 확인할 것](decisions/0001-evolvable-platform-boundaries.md#구현에서-확인할-것)에 있다.
역방향 import 검사(`tests/test_layers.py`, 계층표는 [아키텍처 §11](ARCHITECTURE.md#계층과-의존-방향-검사))와 플랫폼 포트 세 구현의 공통 계약 시험
(`tests/test_contracts.py`)은 #43부터 저장소 CI에서 돈다. 정책 Strategy의 계약 시험(#17·#20)과 나머지 항목은 남았고, Q15의 판정은 출시 결과표가 한다.

- core의 의미·읽기 흐름이 Aelix·UI·분석 라이브러리 없이 실제로 호출된다. import만 성공하는 것을 독립성 증거로 삼지 않는다.
- 대표 Strategy 또는 adapter를 대체해도 ID·버전·근거·상태 계약이 유지된다. 명목적인 base class 상속만 시험하지 않는다.
- 설정된 구현과 프로젝트별 상태를 명시적으로 주입하며, 두 프로젝트·세션의 초점·정책·캐시가 섞이지 않는다.
- 지원하지 않는 기능·호환되지 않는 구현은 사유를 드러낸다. 기록 의미나 공유 범위를 바꾸는 조용한 fallback을 하지 않는다.
- 내부 확장점의 증가가 모델 도구 증가·정형 분석법 강제·토큰 강제 제한으로 이어지지 않는다.
- 이전 프로젝트·스크립트·읽기 결과·게시본의 의미를 보존하고 전환·지원 범위를 설명한다.

모든 미래 backend를 먼저 구현할 필요는 없다. 현재 요구가 있는 교체 사례와 테스트 adapter로 경계를 입증하고,
새 저장·실행·게시 구현이 추가될 때 같은 계약 시험을 확장한다.

### 명칭과 영어 기본값의 검증

[전체 용어 점검](REVIEW-TERMINOLOGY-2026-09-18.md)의 N0-a/b/c를 Q1·Q4·Q6·Q7·Q10·Q11·Q13·Q15·Q16에 걸쳐 검증한다.
CLI·SDK·명령·flag·환경·오류·예제·도구 schema에 같은 Analytics 이름을 쓰고, 구·신 별칭을 기본 도구에 중복 등록하지 않는다.
새 기본 프로젝트·데모의 Overview·Insights·Reports·Visualizations·Data·Runs·Timeline·Context와 속성·빈 화면·오류·접근성 label을 영어로 확인한다.
한국어 세션 내용·열 이름·Visualization 제목·Report 본문·옛 CONTEXT와 Unicode 경로는 그대로 보존한다.

Workspace를 다시 렌더해도 Report·Visualization 원본은 바뀌지 않아야 한다. 이름만 바뀐다고 행 대응·새 renderer 지원이 생겼다고 표시하지 않는다.
namespace·저장 경로 전환은 예전 journal·run·코드·이미지의 바이트와 참조를 보존하고, 모르는 가족·버전의 경고·거절과 일반 구버전 writer 차단을 검증한다.
옛 명칭은 legacy reader·fixture·migration 안내·과거 증거에서만 의도적으로 유지한다. 한국어 또는 `lab` 검색 결과 0건을 통과 기준으로 삼지 않는다.

### Aelix 설치 검증

깨끗한 환경에 지원 대상 Aelix를 먼저 설치한 뒤 같은 환경에 확장을 설치한다.
등록된 `aelix.extensions` endpoint가 **실제로 존재**하고 `aelix extension verify`가 결합된 manifest를 보고하는지 확인한다.
검증할 endpoint가 0개여도 종료 코드가 0일 수 있으므로 종료 코드만 검사하지 않는다.
이후 실제 로드 → 프로젝트 생성 → import → query → run → finding → 리포트 열기 → 세션 재개를 수행한다.

manifest·template·CSS·JS·kit 코드가 모두 설치물에 포함되고, 체크아웃을 다른 곳으로 옮겨도 설치본이 동작해야 한다.
분석 라이브러리가 호스트 환경에 유입되지 않았는지 확인한다. 지원 최소 버전과 출시 시점의 지원 버전을 각각 시험한다.
[근거: Aelix ADR-0207](https://github.com/handochan/aelix-ai/blob/026bd15db229d86d61b74fd3b8c1d8eb0f750715/docs/decisions/0207-a-catalog-listed-pack-must-bind-a-manifest.md).

### 사람의 직접 분석과 작성 주체 전환 검증

[직접 분석 설계](DESIGN-CONTINUITY-AND-REUSE.md#사람이-직접-분석하는-경로)를 다음 두 경로로 검증한다. 둘 다 필수이며 결과와 증거를 따로 남긴다.

**Q17-a — 사람만으로 분석 완료:** Aelix가 설치되지 않았고 모델 설정·인증이 없는 새 환경에 출시할 배포본과 필요한 분석 의존성을 설치한다.
설치 준비 뒤에는 로컬 합성 데이터를 사용하고, 모델 실행·호출 경로를 차단·계측해 호출과 시도가 모두 0임을 확인한다. API 키가 없다는 사실만으로 이를 대신하지 않는다.

1. CLI로 프로젝트를 생성하고 CONTEXT에 목적·질문을 적는다. 데이터를 가져와 SQL로 탐색한다.
2. 사람이 편집기에서 Python 스크립트를 작성하고 CLI로 실행한다. SDK와 일반 라이브러리 경로를 포함해 코드 스냅샷·관측된 입력·환경·Visualization·첨부 데이터를 확인한다.
3. CLI와 SDK로 발견·판단·열린 질문을 남기고 정확한 run·결과 버전을 연결한다. 원장 JSON 수동 편집 없이 완료한다.
4. 사람이 중간 Report를 작성·등록하고 분석을 계속한다. 코드·판단·보고서를 수정해 새 버전을 저장한 뒤 이전 버전의 본문·첨부·근거가 유지되는지 확인한다.
5. Workspace를 렌더하고 결과 → 데이터·코드 → 발견·보고서로 이동한다. CLI·SDK 프로세스를 종료한 뒤 다시 열어 목적·발견·다음 작업을 회수한다.

실패한 스크립트를 수정해 다시 실행하는 사례도 포함한다. 실행 실패·기록 상태·새 시도의 관계를 확인하며 이전 실패 기록을 성공으로 덮어쓰지 않는다.
현재 지원되는 명령·인자만 사용하는 안내로 소유자가 직접 최소 1회 수행하고, 도움말·오류 안내·막힌 단계·수동 우회·완료 시간을 남긴다.
수행자는 결과표에 적는다(2026-10-03 소유자 결정, [#39](https://github.com/handochan/aelix-analytics/issues/39). 이전 기준은 작성자 외 분석가였다).
CLI 출력·run·journal·보고서 manifest·원본 해시·모델 호출 계측과 재개 결과를 증거로 보존한다. 기존 코드의 단위 시험만으로 사람 사용성까지 통과 처리하지 않는다.

**Q17-b — 사람 → 에이전트 → 사람:** Q17-a에서 만든 프로젝트의 기록을 기준으로, 별도 Aelix 환경의 새 세션에서 지원 대상 실제 모델이 후속 분석을 수행한다.
이전 대화를 붙여 넣지 않고 프로젝트에서 목적·발견·열린 질문·근거를 읽어 새 코드·실행·발견을 추가한다. 세션 종료 후 사람은 Aelix·모델 없는 경로로 결과를 검토·수정하고 새 기록을 남긴다.
각 인계 전후에 기존 ID·내용 버전·근거 참조·보존 파일 해시가 유지되고 새 실행·정정·보고서가 별도 ID/버전으로 연결되는지 확인한다.
작성·요청 주체와 실행 수단을 구별하며, 에이전트의 CLI 호출을 사람 작성으로 기록하지 않는다. 세션 참조가 없는 사람 기록도 조회·참조할 수 있어야 한다.

Q17-b는 Q2·Q13의 실제 모델 과제와 묶어 수행할 수 있다. 사용한 환경·모델·호스트·기록 기준을 명시하고 같은 실행의 비용을 중복 집계하지 않는다.
에이전트 구간의 모델 사용량을 Q17-a의 0회 결과와 섞지 않는다. 실제 모델 구간이 미실행이면 Q17-b는 미실행이며, 모의 호출로 통과를 대신하지 않는다.
노트북 실행 기록 adapter와 브라우저 분석 편집·동시 공동 쓰기는 이 베타 게이트의 지원 선언에 포함하지 않는다.

## 3. 분석 연속성과 비용의 측정법

테스트 데이터는 합성 또는 공개 가능한 fixture로 고정한다. 기존 동작의 비교 기준점은 `7b205cd`이며,
이전 Aelix Analytics Engine 대비 점수가 공식 베타의 합격 기준은 아니다.
새 기능 때문에 기존 버전에서 완료할 수 없는 과제는 별도 표시하고, 실패가 적은 토큰으로 끝났다는 이유로 효율적이라고 보지 않는다.

| 시나리오 | 확인할 내용 |
|---|---|
| 새 세션에서 이어 하기 | 목적·현재 지표 묶음·정의 버전·미정 사항·최신 유효 발견·다음 확인을 회수 |
| 오래된 중요한 발견 | 최근 12개 밖에 있어도 관련 질문으로 검색 가능 |
| 뒤늦은 정정 | 기록 시점과 데이터 기간, 원래 판단과 대체 판단을 구분 |
| 근거의 현재/과거 | 최신 차트가 달라져도 당시 근거를 읽음. 미보존이면 그렇게 답함 |
| 중단·누락 | 기록이 불완전하다는 사실을 보존하고 실행 성공과 구별 |
| 반복 방법 | 기존 후보를 찾고 적용 조건을 확인. 중복 제안을 무작정 늘리지 않음 |
| 분석 방향 변경 | 정의 수정·새 지표 파생·조건별 조회를 구별하고 변경 이유와 이전 질문으로 돌아갈 수 있음 |
| 여러 지표의 해석 | 주요 지표·보조 지표·상충과 관측 범위를 유지하며 다음 작업의 목적을 설명 |

최소 12개 과제를 만들고 Qwen3.8 27B, 프론티어 모델 1종에서 각각 실제 사용할 실행 설정으로 3회 측정한다.
기준 모델을 시험할 수 없으면 미실행으로 남기고 다른 모델의 결과를 대신 채우지 않는다. 축소 문맥·추가 모델 시험은 별도 결과로 보고한다.
모델·설정별 36회 이상의 과제 실행에서 성공률 목표는 90% 이상이며 위 표의 중대 오판은 0건이다.
실패한 과제 실행을 분모에서 제외하지 않는다. 과제 안에서의 재시도는 해당 실행의 비용과 호출 수에 모두 포함한다.
정답은 사람이 작성한 필수 사실·근거 ID·불확실성 표시로 판정하며, 모델의 자기평가만 사용하지 않는다.
실제 모델 실행과 별도로, 결정적 fixture의 ID·관계·사용량 계측·호환성은 모두 통과해야 한다.

기록할 항목:

- 모델 이름·버전/양자화·tokenizer·context 설정·출력 예약량, kit와 Aelix의 버전, 데이터·질문·seed 또는 반복 번호.
- 시스템 지침·도구 schema·자동 맥락·조회 결과·skill·이미지를 포함한 **전체 입력**, 출력, 별도 요약/제안 모델 호출.
- 캐시된 입력과 비캐시 입력을 분리한 과제 전체 토큰, 도구 호출·재시도·지연 시간.
- 필수 사실 회수율, 근거 ID 정답률, 오래된 판단의 오용, 완수 여부와 누락 사유.

기본 조회·색인·프로젝트 화면과 저장된 보고서의 렌더에는 LLM 호출 0회를 목표로 한다. 보고서 본문 작성·선택적 제안 생성 비용은 별도 표기한다.
동일 성공 과제의 전체 입력·출력 중앙값을 줄이는 것이 목표지만, 호출 수를 늘려 억지로 짧게 나눈 것을 개선으로 인정하지 않는다.
품질은 동일한데 비용만 증가하면 회귀로 검토한다. 품질이 개선되면서 비용도 늘면 수치와 절충 이유를 ADR/PR에 남긴다.
측정 목표를 넘더라도 과제에 필요한 정보와 작업을 제공한다. 토큰 목표 달성을 위해 답의 정확성·완결성을 희생하지 않는다.
현재 `.lab/telemetry.jsonl`에는 모델 토큰 필드가 없으므로, 호스트/provider usage 또는 모델 tokenizer 기반 별도 측정이 필요하다.

### 제안 옵션과 도구 표면의 별도 측정

같은 분석 과제를 `on_demand` 무요청, `on_demand` 명시 요청, `always_on`의 세 조건으로 나누어 비교한다.
무요청 조건에서는 제안을 위한 자동 후보 탐색·알림·추가 모델 토큰이 0이고, 발견·맥락 기록의 완수율은 유지되어야 한다.
상시 조건은 임계값 위·아래, 필수 근거 누락, 중복 후보, 다른 세션·CLI·동시 요청, 에이전트의 CLI·모델 도구 호출, 24시간 창 안의 두 번째 후보와 창이 지난 뒤 새 기록 없이 남은 후보, 명시적 요청 뒤의 자동 알림, 캐시 삭제와 중간 해제를 시험한다.
베타의 상시 조건은 모델 없이 판정·발행한다. 알림의 상세를 여는 읽기는 모델을 부르지 않고, 모델 기반 상세 검토는 명시 요청으로 따로 센다([ADR-0008](decisions/0008-reuse-proposal-counting-and-deterministic-always-on.md)).
토큰 목표 초과·계측 불가에서도 그것만으로 기능을 중단하지 않고 상태를 정확히 기록하는지 확인한다.
적합한 후보가 없는 세션에서 0건을 제안하는 것은 정상 결과다.

제안의 유효성·중복·분석 방해와 비용을 함께 기록한다. 분석 토큰과 제안 토큰, 입력과 출력, 기본 경로와 선택적 모델 검토를 분리한다.
8/10·프로젝트당 24시간 등의 초기 정책값은 검증된 연구 임계값이 아니므로, 기본값을 바꿀 때 fixture 결과와 사용자의 방해 정도를 근거로 남긴다. 사용자 설정은 창을 기본값보다 짧게 할 수 없다.

도구 표면 비교에서는 도구 이름 수뿐 아니라 총 schema 길이·enum/인자 분기·유사 기능을 센다.
정답 도구가 하나인 요청, 여러 기존 기능을 조합하는 요청, 모호한 요청, 관련 없는 유사 도구가 있는 요청을 고정한다.
잘못된 도구·인자·불필요한 호출·실패 복구·과제 완수와 비용을 함께 비교한다.
새 도구 수가 0이어도 `action` 분기와 설명이 크게 늘어 선택 오류를 만들면 회귀다.
새 도구가 더 좋은 대안임을 입증하면 ADR에 기본 노출 여부·호환성·측정 결과를 명시할 수 있다.

### 지표 중심 분석의 검증

[지표 중심 분석 설계](METRIC-DRIVEN-ANALYSIS.md)의 M0·최소 M1을 첫 베타의 기록·메모리·UI 시험에 포함한다.
정의가 미정이어도 탐색을 시작할 수 있어야 하고, 구체화된 정의는 결과와 당시 버전으로 연결되어야 한다.
새 세션이 “지금 어떤 지표의 어떤 질문을 왜 풀고 있고 다음에 무엇을 확인할 것인가”를 근거와 함께 답할 수 있는지 본다.
활동량·차트 개수로 이를 대체하지 않는다.

같은 이름의 다른 정의, 분자·분모·단위·기준 모집단 변경, 집계 수준 변경, 코드 오류 수정, 최신 정의로의 자동 치환,
오래된 부모 지표에 묶인 파생 결과, 단순 범위 조회마다 지표를 늘리는 사례를 포함한다.
분석 목적으로 연결된 run과 실제로 지표를 계산한 run을 구별하며, 원문 기록에 없는 과거 정의를 추정해 확정하지 않는다.

### 실사용 경험과 자유도의 회귀 검증

참고 세션의 EDA·스텝 프로파일·시점별 점수·전체 센서 그림 흐름을 합성 fixture로 재현한다.
기존과 동일한 코드·지표·방법을 강제하지 않고, 질문 해결·검사 가능한 근거·적절한 해석·오류 복구·후속 확장을 평가한다.
Qwen과 프론티어 모델이 서로 다른 올바른 방법을 선택할 수 있어야 한다.

- 활성 프로젝트가 cwd와 다른 경우에도 복구 가능한 경로 안내를 제공한다.
- SDK `analytics.record`(옛 `lab.note`)와 모델 도구의 차이, 라이브러리 오류, 실패 뒤 부분 산출물을 숨기지 않고 수정 후 이어 간다.
- 지표·그림을 사전 등록하지 않은 탐색과 사용자 정의 Python·추가 의존성·다중 패널을 수행할 수 있다.
- 첨부 데이터가 요약 또는 일부 계열인 경우 완전한 플롯 대응으로 표시하지 않는다.
- 기준 프로파일을 추정한 데이터와 평가 데이터를 구별하고, 미검증 해석을 실행 성공만으로 확정하지 않는다.

참고 세션의 응답에는 수치·해석의 보완점이 있으므로 이전 답변을 그대로 기대 정답으로 쓰지 않는다.
회귀 검증은 분석의 표현력을 줄여 오류를 피하는 방식보다, 선택 가능한 방법을 유지하면서 기록·복구·검토를 개선하는지를 본다.

## 4. 화면과 규모 검증

사람 탐색 과제는 소유자가 직접 수행하고 경로·시간·오탐을 기록한다(2026-10-03 소유자 결정, [#39](https://github.com/handochan/aelix-analytics/issues/39). 이전 기준은 작성자 외 최소 2명이었다).
첫 목표는 발견에서 정확한 실행 코드 또는 플롯 표까지 3회 이내의 주요 선택, 브라우저 뒤로 가기로 같은 카드 복원이다.
로그 상세와 대형 표의 추가 페이지는 별도로 센다. 중간에 최신 버전으로 잘못 이동하면 클릭 수와 관계없이 실패다.
좁은 화면·키보드·JavaScript 없이도 텍스트 관계와 링크로 핵심 근거를 읽을 수 있어야 한다.

| 규모 fixture | 구성 후보 | 첫 베타 요구 |
|---|---|---|
| S | 30 runs, 300 events, 5 datasets, 작은 차트·표 | 전체 흐름과 첫 설치·생성의 기준 |
| M | 300 runs, 10,000 events, 20 datasets, 총 데이터 1 GB 이내 | 검색·관계·첫 화면의 제한 크기, warm/cold 및 재구축 비용 측정 |
| L | 3,000 runs, 100,000 events, 입력이 매우 많은 run | 후속 부하 시험. 측정 전 지원 선언하지 않음 |

각 fixture에는 정정·철회·미보존 데이터·동일 chart ID·순환 참조·긴 한국어 내용을 포함한다.
장비·디스크·Python·SQLite·브라우저·라이브러리 버전을 고정해 warm/cold를 구분하고,
반복 측정의 p50/p95·최대 메모리·읽은 파일량·생성 HTML 크기를 기록한다.
초기 목표 후보는 M의 warm 제한 조회 p95 500 ms 이내, 캐시가 있는 첫 화면 사용 가능 p95 2초 이내다.
그림·데이터 프로파일·최초 구축 시간은 별도로 측정하고, 느린 cold 작업을 warm 숫자에 숨기지 않는다.
이 시간은 현재 실측값이나 성능 보장이 아니며, 베타 지원표에는 실제 달성한 범위를 적는다.

### 공유 빌드와 게시의 검증

작업 프로젝트가 없는 별도 위치에서 생성 패키지의 `file://` 열기와 HTTP 하위 경로 열기를 확인한다.
지표·차트·관계·포함된 근거로 이동했다가 같은 버전으로 돌아오고, 진행 중 상태·게시 시점·제외 범위가 보이는지 본다.
이미지·첨부 표·CSS·JS가 원본 경로나 개발자의 환경에 기대지 않아야 한다.

read/evidence 프로필 각각의 HTML·inline JSON·검색 인덱스·다운로드 파일을 검사한다.
선택하지 않은 원시 데이터·세션·로컬 경로·로그가 숨겨진 자원으로 남지 않아야 하고, 미포함 근거를 완전 재현 가능으로 표시하지 않는다.
사용자 정의 차트의 정적 대체·지원 범위와 로컬에서의 자유로운 분석도 함께 확인한다.

첫 P1 게시 대상은 사용자가 지정한 폴더다([ADR-0009](decisions/0009-first-publish-target.md), 채택, 구현 전). 그 대상에서 독자 접근·페이지와 자원 일치·고정 버전 주소·최신 주소를 확인한다.
업로드 중단·동일 빌드 재시도·게시 중 원본 변경·이전 게시본 유지·권한에 맞는 직접 자원 접근을 시험한다.
증거는 CI Linux(필수)에서 두 번째 계정이 HTML·이미지·JS·첨부를 file 경로로 직접 연 결과(권한의 증거)와 루프백 HTTP 하위 경로로 연 결과(자원 해석의 증거), macOS·Windows에서 시도한 결과, 단계마다 중단한 뒤의 두 포인터, 같은 빌드의 재사용과 같은 ID·다른 내용의 거절, 표식 없이 비어 있지 않은 폴더와 다른 프로젝트 channel의 거절이다.
실제 다른 독자의 열람은 [#24](https://github.com/handochan/aelix-analytics/issues/24) 리허설에서 소유자가 한다. 소유자의 다른 기기나 다른 계정으로 게시본을 연 결과가 Q14의 통과이며, 수행자는 결과표에 적고 기기·계정·경로를 그대로 적는다(2026-10-05 소유자 결정). 그 결과를 팀원의 열람으로 옮겨 적지 않는다.
폴더 대상은 팀 전용을 제공하지 않으므로 그 한계를 명시한다. 로컬 링크 검사만으로 원격 게시나 팀 접근을 통과 처리하지 않는다.

### 보고서 산출물의 검증

진행 중이며 지표가 미정인 분석에서 중간 보고서를 만들고 계속 분석한다. Markdown/HTML의 자유 본문과 다른 문서 파일의 보존·다운로드를 확인한다.
v2 작성·차트 재계산·프로젝트 HTML 재생성 뒤에도 v1의 본문·첨부 해시·근거 버전이 같아야 한다.
작성 시점·분석 기준·대상 기간·게시 시각을 구별하고, 과거 본문을 최신 정의나 정정된 발견으로 조용히 바꾸지 않는다.

하나의 보고서에 여러 컬럼을 넣는 경우와 컬럼별 보고서를 묶는 경우를 각각 검증한다.
요청 20개 중 18개만 성공한 예제, 실패분 추가 후 새 묶음, 같은 이전 버전에 대한 갱신 충돌을 포함한다.
보고서 → 당시 차트·지표·발견 → 원래 버전·섹션의 왕복과 차트에서 인용 보고서를 찾는 흐름을 확인한다.
등록 중단·파일 누락·완료 이벤트 누락을 숨기지 않고, 재시도가 완료 버전을 덮어쓰거나 생성 코드를 무조건 재실행하지 않는지 확인한다.
기본 조회·렌더·공유에 추가 LLM 호출이 없고 전체 본문·이미지를 상시 문맥에 넣지 않는지 측정한다.
임의 HTML의 격리 보기·미지원 형식의 대체 경로와 자유 본문·첨부에 남은 공유 제외 대상도 Q10·Q14와 함께 확인한다.

## 5. 구현 순서

각 행은 완료 조건이 있는 단계이며 여러 PR로 나눌 수 있다. 이름 변경·대규모 파일 이동·기록 의미 변경을 한 PR에 섞지 않는다.
지표와 분석 초점은 처음부터 B1의 기록·참조 계약에 포함한다. 이력 기능을 모두 만든 뒤 붙이는 부가 기능으로 미루지 않는다.

| B2-a 제한된 메모리 회수 | 기존 읽기 표면 활용을 우선해 현재 분석 방향·검색·ID 읽기·변경 조회 제공. 파생 인덱스·상태·출처·다음 페이지. CONTEXT 자동 수정은 포함하지 않음 | 현재 지표·미정 사항·오래된 발견·정정·짧은 한국어·인덱스 미지원·조회 중 변경 통과. 기본 경로 LLM 호출 0회와 Q11·Q12 | B1-a, B1-d |

B1-a는 새 기억 종류나 그래프 UI가 없어도 현재의 주입 비용 문제를 줄일 수 있다.
B1-b도 기존 기록에 대한 읽기 기능으로 먼저 검토할 수 있다. 반면 새 상태를 쓰는 B1-c는 호환성 전환을 생략해서는 안 된다.
이후 checkpoint(B2-b), 제안 정책·무요청 경로(B3-a), 모델 호출 없는 상시 사전 검사·판정·비용 계측·알림(B3-b),
재사용 검사·등록 예제(B3-c), HTML 연결과 복귀(B4)를 각각 별도 PR로 이어 간다.
보고서 B4-r은 보존·등록·버전 계약과 Reports 탐색·반복 묶음을 나눠 검토한다. 독립 보고서 파일은 재생성 가능한 `workspace/` 안에만 보관하지 않는다.
공유는 P0의 독립 build·범위 투영과 P1의 첫 publisher를 나누어 B4-s에서 검토한다. 확장 패키지 배포 B5와 분석 게시를 혼동하지 않는다.
베타의 상시 모드는 결정적 단계까지이고, 모델 기반 상세 검토는 사람이 대화에서 요청한 턴에서만 한다([ADR-0008](decisions/0008-reuse-proposal-counting-and-deterministic-always-on.md)).
상시 모델 검토는 베타 뒤에 무요청 모드와 결정적 사전 검사의 실제 사용량·분석 방해를 측정한 결과로 따로 결정한다.

공식 배포 이름·라이선스·지원표 결정과 wheel 구성 검토는 이 흐름과 별개로 B5에서 준비할 수 있다.
최종 등록·배포는 기능 코드와 설치 검증이 합쳐진 동일 artifact를 대상으로 한다.

## 6. 베타 뒤의 가장 중요한 우선순위

안정성 문제와 데이터 손실 가능성은 아래 계획보다 먼저 처리한다. 그다음 우선순위는 다음과 같다.

1. **재실행 의미 보강:** helper·환경·입력의 당시/현재 버전을 구별하고, 복원이 안 되는 이유를 설명한다.
2. **요청 멱등성:** 키·요청 지문·상태 영수증을 도입하고, 중복 실행·변경된 의도·불확실 상태를 구별한다.
3. **관리 산출물의 commit·recover:** 단계마다 중단하고 복구를 반복해도 일관된 상태를 만든다.
4. **큰 프로젝트의 증분 처리:** event 인덱싱·리포트·프로파일의 비용을 측정해 필요한 부분부터 줄인다.
5. **재사용 효과의 검증 후 자동화:** 후보 추출·중복 통합·등록 지원을 확장하고, 필요한 경우에만 의미 검색을 추가한다.
6. **선택 기반 후속 분석:** 기존 Analytics의 SelectionRef 의미를 참고해 F1의 저장 선택과 F2의 후속 실행을 도입한다. 행 대응·버전 고정·쓰기 복구를 먼저 검증한다.

F1·F2는 [설계의 후속 분석 경로](DESIGN-CONTINUITY-AND-REUSE.md#향후-선택-기반-후속-분석)와 연결한다.
후속 게이트는 다른 스냅샷 선택의 거절, 집계·파생 표의 행 단위 표시, 새 세션에서 선택 재개,
선택 → 실행 → 발견 → 원래 차트의 왕복, 선택 저장 실패·중복 처리다.
첫 베타에서 이를 구현하지 않더라도 ID·버전·근거·입력 계약이 후속 연결을 가로막지 않도록 검토한다.
이 기능의 도입은 상시 도구 수 증가를 기본 전제로 하지 않는다.

복구 완료 조건에는 `prepared` 상태, 일부 파일만 게시됨, run 완료 후 journal 누락, report 실패,
같은 복구를 두 번 실행, 외부 부작용이 불확실한 작업을 포함한다. 회복 불가능한 상태는 명시적으로 남긴다.
이는 임의 Python과 외부 서비스까지 묶는 exactly-once·rollback 약속이 아니다.

## 7. 기여·출시 기록의 형식

PR에는 문제를 재현하는 입력, 변경 후 행동, 바뀐 계약, 비교 결과, 남은 한계를 적는다.
정책·호환성·저장 형식의 결정은 채택 시 `docs/decisions/`에 근거를 남긴다.
작은 표시 수정에 불필요한 시험을 추가하지 않되, 근거·시간·사용량 계측·복구 의미를 바꾸면 해당 회귀 사례를 반드시 검증한다.

출시 리허설 결과표는 최소 다음 열을 가진다.

| Gate | 결과(pass/fail/not run) | commit·artifact | 환경·모델 | 수행자 | 증거 경로 | 제한·후속 작업 |
|---|---|---|---|---|---|---|
| Q1–Q17 각각 | 미실행 | 미정 | 미정 | 미정 | 미정 | 구현·검증 필요. Q17-a/b는 결과·증거를 각각 기록 |

필수 게이트 실패·미실행, 설명되지 않은 기록 유실, 잘못된 버전 연결, 실제 문맥 한계로 과제를 진행하지 못하는 문제,
설치물 누락은 출시 보류 사유다. 알려진 복구·멱등성 한계는 지원 범위를 제한해 공개하되, 그것을 구현 완료로 표시하지 않는다.
구체적인 기여 절차는 [CONTRIBUTING.md](../CONTRIBUTING.md)에 있다.
