네 문제에는 원인이 둘 겹쳐 있다.

1. **기록 지점이 특정 표면에 묶여 있다.** 근거는 kit의 실행 경로에, 관찰은 aelix의 `bash`에, 맥락 주입은 aelix의 hook에 걸려 있다. 에이전트가 다른 도구를 쓰거나
   호스트가 바뀌면 같은 일이 기록되지 않는다.
2. **근거와 참조의 단위가 run에 묶인 파일과 로컬 경로다.** 표가 아닌 파일(문서, 이미지)은 run이 입력으로 선언했거나 출력으로 남겼을 때만 가리킬 수 있다
   (선언한 입력은 형식을 가리지 않는다). 가져오기와 자동 감지는 표 형식뿐이고, 파일 안의 위치를 가리키는 방법이 없으며, 도구의 결과는 가리킬 방법이 없다.
   본문이 대상을 가리키는 가장 쉬운 방법은 절대 경로다.

실험(#196)에서 확인한 것은 다음과 같다. 모두 aelix 0.1.0b2, macOS에서의 값이다.

- aelix의 `tool_result` hook은 다른 확장이 등록한 도구에도 불리고 결과 블록과 `details`가 실린다(시험으로 돌림). MCP 서버의 도구도 같은 hook을 지나고
  `structuredContent`가 `details`로 온다는 것은 aelix의 코드에서 읽었고 돌려 보지 않았다. `tool_execution_end` hook에는 결과가 없다.
  확장이 보는 결과는 앞서 로드된 확장이 고친 것까지이고, 뒤에 로드된 확장이 덧붙인 것은 보이지 않는다.
- 한 메시지의 호출 가운데 `execution_mode`가 sequential인 도구가 하나라도 있으면 그 메시지의 호출은 하나씩 실행된다. aelix의 bash·write·edit와 이 kit의
  도구 여섯 개가 sequential이다. 함께 실행되는 것은 read·grep·find·ls와 sequential로 등록하지 않은 다른 도구끼리다.
- 다른 확장의 도구가 프로젝트의 `data/`에 쓴 파일은 main에서 telemetry의 한 줄(도구 이름) 말고는 어떤 기록에도 남지 않는다.
- 비용(로컬 디스크, 중앙값): 호출 하나에 로그 한 줄과 결과 보관으로 결과 1–14 KB에서 약 0.5 ms, 1 MB에서 약 4 ms가 더 든다. 파일 1,000개인 프로젝트를
  한 번 훑는 데 약 9 ms, 10,000개에 약 73 ms다. 기록 하나의 수치 대조는 그 프로세스의 첫 번째가 약 106 ms, 그 뒤는 약 3 ms이고, 최근 결과가 1 MB씩이면
  약 600 ms다. 고정 프롬프트는 작은 프로젝트에서 요청의 전체 글자 수가 약 10% 많았다.
- 실험 branch에서 aelix 통합 시험 1,142개와 저장소 전체 시험 3,483개가 통과했다(`4a6d461`). 실제 모델로 돌린 세션, 실제 MCP 서버, 별도 프로세스의 세션,
  Windows는 돌려 보지 않았다.

호스트가 결정 1의 사건을 줄 수 있는지는 다음까지 확인했다. 결정이 아니라 읽은 것이고, 호스트별 대응은 #192가 실제 버전으로 확인한다.

| 호스트 | 확인한 방법 | 읽은 것 |
|---|---|---|
| aelix 0.1.0b2 | 코드를 읽고 실험의 시험으로 돌림 | 세션 시작과 프롬프트는 `before_agent_start`(세션의 첫 번째가 세션 시작), 호출의 시작은 `tool_execution_start`·`tool_call`, 호출의 끝은 `tool_result`·`tool_execution_end`, 에이전트 정지는 `agent_end`, 대화 압축은 `session_compact`가 준다. 시스템 프롬프트, 메시지(`context` hook), 도구 결과 뒤의 글을 모두 전할 수 있다 |
| Claude Code | [공식 hooks 문서](https://code.claude.com/docs/en/hooks)를 2026-11-18에 읽음(일부). 돌려 보지 않음 | `SessionStart`·`UserPromptSubmit`·`PreToolUse`·`PostToolUse`·`Stop`이 있고, `PostToolUse`의 입력에 도구의 인자와 결과가 있으며 MCP 도구와 하위 에이전트의 호출에도 불린다고 적혀 있다. 압축 뒤에는 `SessionStart`가 다시 불려 맥락을 넣을 수 있다고 적혀 있다. 추가한 맥락은 시스템 프롬프트가 아니라 대화에 들어간다. `PostToolUse`는 성공한 호출의 사건이고 실패는 다른 사건이다. 두 사건의 입력 예시에 모두 `tool_use_id`가 있지만 같은 값이라고 적은 문장은 찾지 못했다. 명령을 실행하는 hook 말고 다른 종류의 hook도 문서에 있다 |

## 결정

### 1. 경계 사건: 호스트가 알리고 kit이 판단한다

세션에서 일어나는 일을 kit은 **경계 사건**(boundary event)으로만 안다. 호스트 어댑터는 사건을 kit에 옮기고, 무엇을 남기고 무엇을 알릴지는 kit이 정한다.

| 사건 | 언제 | 호스트가 주는 것 | kit이 하는 일 |
|---|---|---|---|
| 세션 시작 | 세션이 시작되거나 이어질 때 | 세션 식별자, 작업 디렉터리 | 프로젝트를 찾고, 세션 동안 바뀌지 않는 맥락과 시작 시점의 상태를 돌려준다 |
| 프롬프트 | 사람이 프롬프트를 보낼 때마다 | 세션 식별자 | 지난 프롬프트 이후의 변경분(다른 세션·사람의 기록, 파일 변경)을 돌려준다 |
| 호출의 시작(선택) | 도구 호출 직전 | 호출 식별자, 도구의 이름과 역할, 인자 | 실행 창의 시작을 잡는다. 관찰된 활동을 쓰는 호출이면(지금은 aelix의 `bash`, 결정 7) ADR-0015의 앞 상태를 본다 |
| 호출의 끝 | 도구 호출이 끝나 결과가 정해진 뒤 | 호출 식별자, 도구의 이름과 역할, 인자, 결과 블록, 도구가 준 구조화된 결과, 오류 여부 | 세션 로그에 남기고, 결과를 보관하고, 관찰된 활동을 쓰는 호출이면 ADR-0015의 뒤 상태를 보고, 결과 뒤에 붙일 글이 있으면 돌려준다 |
| 에이전트 정지 | 에이전트가 응답을 마쳤을 때 | 세션 식별자 | 파일 상태를 대조하고 Workspace를 갱신한다. 호스트를 기다리게 하지 않는다 |
| 대화 압축 | 호스트가 대화를 줄였을 때 | 세션 식별자 | 시작 시점의 상태를 다시 주도록 표시한다 |

- **이 여섯 사건과 아래의 세 가지 반환이 이 ADR의 최소 집합이다.** #192의 조사에서 더할 것이 나오면 이 ADR을 개정한다.
- **kit의 진입점은 하나다.** 사건마다 kit의 같은 함수를 부른다. 프로세스 안에서 kit을 로드하는 호스트(aelix)는 함수를 직접 부르고, 명령을 실행하는 hook만 있는
  호스트는 같은 함수를 부르는 kit CLI에 사건을 JSON으로 넘긴다. 사건의 형식과 CLI의 이름은 호스트 어댑터 ADR이 정한다.
- **어댑터는 옮기기만 한다.** 호스트의 사건을 위 사건으로 바꾸고, kit이 돌려준 것을 호스트의 방식으로 전달한다. 프로젝트의 파일을 직접 쓰지 않고,
  무엇이 분석 단계인지나 무엇을 알릴지를 판정하지 않는다([아키텍처](../ARCHITECTURE.md) 4절: "호스트·화면마다 같은 규칙을 다시 구현하지 않는다").
  호스트의 도구 이름을 **역할**(셸 실행, 파일 쓰기, 파일 읽기, 그 밖)로 옮기는 것은 어댑터의 일이고, kit은 이름이 아니라 역할로 판단한다.
- **같은 사건은 어느 호스트에서 와도 세션 로그의 같은 줄이 된다.** journal의 관찰된 활동은 예외다. `observed_activity`의 형식은 aelix에 묶여 있어
  (ADR-0015 결정 1·2: aelix `bash`, aelix 세션, aelix의 `tool_call_id`) 지금은 aelix 어댑터의 사건에서만 쓴다. 다른 호스트의 셸 실행 도구를
  관찰된 활동으로 기록할지는 호스트 어댑터 ADR이 ADR-0015의 개정으로 정한다.
- **프로젝트의 활성화와 신뢰 판정은 지금 그대로다**(계약 A의 "작업 디렉터리에서 찾은 프로젝트"). 신뢰되지 않은 프로젝트에서는 사건을 받아도 맥락을 돌려주지
  않고 아무것도 쓰지 않는다. 사람에게 묻는 방법은 호스트마다 다르고 #192가 정한다.
- **kit이 호스트에 돌려주는 것은 세 가지다**: 세션 동안 바뀌지 않는 맥락, 그 시점에 모델에게 전할 글, 도구 결과 뒤에 붙일 글. 호스트가 그 가운데
  전달할 방법이 없는 것은 전달하지 않고, 어댑터의 문서가 그 차이를 적는다.
- **사건을 다 주지 못하는 호스트도 받는다.** 호출의 시작이 없으면 함께 실행된 호출을 알 수 없고 ADR-0015의 앞 상태가 없다. 호출의 끝이 없으면 세션 로그와
  결과 보관이 없다. 프롬프트와 에이전트 정지만 있어도 파일 상태의 대조는 동작한다. 사건이 하나도 없으면 지금의 CLI·SDK 경로다.
- **프로세스 사이의 통로는 환경의 상속뿐이다.** 하위 에이전트처럼 다른 프로세스에서 도는 세션은 자기 어댑터가 있으면 자기 사건을 자기 세션 식별자로 알린다.
  어댑터가 없으면 그 프로세스가 한 일은 부모 세션의 그 도구 호출의 실행 창과 파일 상태의 대조로만 보인다.
- **사람의 `!` 명령은 감싸지 않는다**(ADR-0015의 결정과 이유를 유지). 그 명령이 남긴 파일 변경은 파일 상태의 대조가 "어느 호출의 밖에서 바뀜"으로 잡는다.

### 2. 세션 로그와 journal

세션에서 본 것(호출, 결과의 해시, 대조의 결과)은 **세션 로그**에 남긴다. 세션 로그는 보조 로그다.

- journal의 줄이 아니다. seq가 없고, 공통 reader·출처 추적·Timeline·공유본이 읽지 않는다. 지워도 journal이 말하는 것은 달라지지 않는다.
- 줄마다 형식의 이름과 판을 갖고, 읽는 쪽은 모르는 형식의 줄을 지나친다. 전환(migration)의 대상이 아니다.
- 프로젝트의 이력이 아니다. 그 기계의 그 세션이 본 것이므로 기본으로 git에서 제외한다(OQ2). 프로젝트의 `.gitignore`를 고치지 않아도 제외되도록 스스로를
  무시하는 디렉터리에 둔다(템플릿의 줄은 기존 프로젝트에 닿지 않는다). 실험(#196)은 세션 로그를 `telemetry.jsonl` 옆에 두어 새 템플릿에서 git이 추적했다.
  이 결정은 그와 다르다.
- ADR-0015 결정 5의 원칙을 따른다: 가리기 전의 글, 그 해시, 그 길이를 남기지 않는다. 세션 로그에 인자의 글은 없고, 인자의 해시와 크기는 가림 규칙을
  적용한 뒤의 글에서 계산한다. 실험은 가리기 전의 인자를 해시했다. 이 결정은 그와 다르다.

journal에 올라가는 길은 셋이다.

1. **저자가 근거로 인용할 때.** 발견·결정 같은 기록의 참조가 호출이나 등록된 원천을 가리킨다. kit이 대조로 찾은 호출을 kit이 참조로 올리지는 않는다(OQ6).
2. **데이터로 가져올 때.** 보관된 결과나 파일을 가져오기가 받는다. 지금의 가져오기 기록은 원본을 파일 경로로 적으므로
   ([계약 C4](../CONTRACTS.md#c4-가져오기-기록-dataimportednamemetajson)), 호출의 결과를 받으려면 그 형식을 고쳐야 한다(후속 결정).
3. **관찰된 활동.** ADR-0015 그대로다.

- 이 ADR은 새 기록 종류(kind)를 더하지 않는다. 새 참조 종류는 [ADR-0006](0006-common-record-contract.md) 1절 2항(새 kind·type·relation만 더함)과
  3항(쓰기 규칙을 더하는 PR의 `min_writer_version`)을 따르며 참조 ADR이 정한다. journal 줄의 종류가 늘지 않으므로
  [ADR-0014](0014-publication-record-contract.md) 결정 2의 `content_seq` 집합도 바꾸지 않는다.
- **호출을 가리키는 참조는 세션 로그 없이도 읽힌다.** 그 호출을 알아보는 데 필요한 최소한(도구의 이름, 시각, 결과의 해시와 크기)을 참조가 스스로 갖는다.
  공통 reader는 세션 로그를 읽지 않는다. 대상의 바이트가 남아 있는지, 기한이 지나 지워졌는지, 이 기계에 없는지는 ADR-0006 4절의 닫힌 상태에 없는 구분이다.
  그 판정은 4절의 개정이고 참조 ADR이 정한다.

모든 호출을 journal에 남기지 않는 이유는 ADR-0015가 "모든 bash 호출을 기록"을 기각한 이유와 같다. 기록할 사실이 없는 호출이 Timeline을 덮고, 추적되는 이력에
세션의 세부가 쌓인다.

### 3. 근거의 단위: 해시로 가리키는 바이트

근거가 될 수 있는 것의 단위는 **바이트와 그 sha256, 매체 종류, 그 안의 위치**다. 지금도 run의 입력·출력은 형식과 관계없이 경로와 해시로 가리킨다.
이 결정이 더하는 것은 run과 가져오기에 묶이지 않은 바이트(도구의 결과, 변환 없이 등록한 원천)와 그 안의 위치다.

보관의 수명은 셋이다.

| 수명 | 무엇 | 어디에, 얼마나 |
|---|---|---|
| 임시 보관 | 호출의 끝에서 본 결과 | 프로젝트의 캐시. git이 무시하고, 결과 하나의 크기·전체 크기·기간에 상한이 있으며 넘으면 오래된 것부터 지운다. 보관하기 전에 가림 규칙(ADR-0015 결정 5)을 적용한다: 규칙이 자격 증명을 찾은 결과와, 비밀일 수 있는 이름의 파일(같은 결정의 목록)을 읽은 결과는 보관하지 않고 해시도 남기지 않는다 |
| 남김 | 기록의 근거로 쓰인 결과 | 프로젝트의 상태 디렉터리. 기본으로 git에서 제외한다. 제외를 풀지는 프로젝트의 사용자가 정하며, `data/`의 제외를 푸는 것과 같은 판단이다(가림 규칙은 자격 증명만 찾고 데이터 행·개인 정보는 찾지 않는다). 크기 상한을 넘은 결과는 남기지 않는다 |
| 가져옴 | 데이터셋, 그리고 변환 없이 등록한 원천 | 데이터셋은 지금의 `data/`와 그 git 규칙. 원천을 두는 자리는 #193의 파일럿 뒤에 정한다 |

- **원천**은 표로 바꾸지 않고 파일의 목록과 해시로 등록한 입력이다. 형식은 #193의 파일럿 뒤에 정한다. 이 이름은 용어집 5절의 Source file·Imported data와
  겹치므로 공개 이름은 그 ADR이 정한다.
- **위치 지정자**(locator)는 근거 안의 자리다: 문서의 쪽, 텍스트의 줄 범위, 이미지의 영역, 표의 행. 문법은 참조 ADR이 정한다.
- 해시는 그 바이트가 있었다는 사실만 말한다. [용어집](../TERMINOLOGY-AND-LANGUAGE.md) 5절대로, 참조가 있다고 자료의 보존이나 결론의 검토가 끝난 것은 아니다.
- 공유본에는 임시 보관과 남긴 결과를 넣지 않는다. 그 대상은 지금의 `not_included` 표시다(종류와 사유만, 이름·ID 없음).

**ADR-0015와의 관계.** ADR-0015는 관찰된 활동에 출력을 남기지 않기로 했고(결정 5: "출력(stdout·stderr)은 남기지 않는다. 출력은 aelix 세션 기록에 있고"),
대안 "출력 저장"을 "데이터 행·개인 정보가 들고 크다. aelix 세션에 이미 있다"는 이유로 기각했다. 이 결정은 그 문장들을 좁히는 개정이다(결정 7).

- 관찰된 활동의 기록과 첨부에는 여전히 출력을 남기지 않는다. journal과 `.analytics/observed/`는 git이 추적하는 이력이기 때문이다.
- "데이터 행·개인 정보가 들고 크다"에 대해: 보관은 기본으로 git 밖에 있고 크기와 기간에 상한이 있다. 그래도 임시 보관에는 결과의 원문이 그 기계의
  프로젝트 캐시에 평문으로 있다. 데이터 행과 개인 정보가 들 수 있고, 가림 규칙이 찾지 못한 비밀도 들 수 있다. 소유자가 알고 정할 일이다(OQ3).
- "aelix 세션에 이미 있다"에 대해: 호스트의 세션 기록은 프로젝트 밖에 있다. 다른 프로세스와 다른 호스트에서 닿지 않고, 프로젝트를 검토하는 쪽이 읽을 수 없다.
  호스트마다 형식도 다르다.
- 보관을 끄면 해시만 남고, 기록의 수치 대조는 동작하지 않는다.

### 4. 기호 참조

기록과 Report 본문이 프로젝트의 대상을 가리킬 때는 **기호 참조**를 쓸 수 있다. 기호 참조는 대상의 종류와 식별자, 필요하면 위치 지정자로 이루어지고
환경 값을 담지 않는다.

- 지금 기록이 받는 이름(run ID, `e<seq>`, `스크립트::시각화`, 데이터셋 이름)은 그대로 기호 참조다. 더하는 것은 호출, 원천, 프로젝트 안의 파일을 가리키는 참조다.
- **구조화된 참조**(기록의 참조, Report의 `based_on`)는 표시하거나 게시하는 쪽이 해석한다. Workspace는 로컬의 대상으로, 공유본은 포함한 대상이나
  지금의 `not_included` 표시로 잇는다. 지금의 동작이고 새 참조 종류도 같은 규칙을 따른다.
- **Report 본문 안의 기호 참조는 그 자체가 대상의 ID다.** 대상이 공유 범위 안이면 지금처럼 통과하고, 범위 밖이면 지금처럼 `leak_found`로 멈춘다
  (본문의 run ID·`스크립트::시각화`·프로젝트 상대 경로는 누출 검사의 강한 토큰이다). build는 본문을 고치지 않는다. 범위 밖 대상을 가리킨 본문을
  어떻게 풀지는 결정 5의 후보에 속한다.
- 그래서 기호 참조가 본문에서 없애는 누출 사유는 환경 값(절대 경로)이다. 범위 밖 대상의 ID라는 사유는 그대로 남는다.
- 절대 경로를 쓴 본문도 계속 저장된다([ADR-0013](0013-report-storage-and-collections.md): 저장한 바이트를 고치지 않고, 파일 종류를 가려 받지 않는다).
  기호 참조는 강제가 아니다.
- 문법과 새 참조 종류는 참조 ADR이 정한다. ADR-0006의 참조 `type`은 닫힌 목록이므로 기록 형식 변경이다.

### 5. 네 자리의 검사: 알리고, 게시만 막는다

세션이 프로젝트에 남기는 자리는 넷이다: 파일, 기록, 저장한 Report, 공유본. 앞의 둘은 이 ADR이 검사를 정하고, 뒤의 둘은 지킬 것만 정한다.

| 자리 | 검사 | 결과가 가는 곳 |
|---|---|---|
| 파일 | **상태 대조**: 지난번에 본 상태와 비교해, run·가져오기·관찰된 활동이 말하지 않는 변경을 찾고 세션 로그의 호출에 대조한다. 그 파일을 가리킨 호출, 실행 창이 수정 시각을 포함하는 호출들, 어느 호출의 밖 가운데 하나다 | 세션 로그, 다음 프롬프트의 변경분(OQ7) |
| 기록 | **수치 대조**: 기록의 글에 적힌 수치를 그 세션의 보관된 결과에서 찾는다 | 세션 로그, 기록을 쓴 요청의 답(OQ4) |
| 저장한 Report | 지금은 없다. 저장할 때 알리는 검사는 #187의 후보다 | — |
| 공유본 | 지금의 누출 검사. 보장은 지금 검사의 범위와 한계 그대로다([계약 D2](../CONTRACTS.md#d2-공유-범위의-무쓰기-미리보기-kit-0230)·D5) | build의 오류 |

- **검사는 결정적이다.** 모델을 부르지 않는다([제품 방향](../PRODUCT.md)의 설계 경계).
- **상태 대조와 수치 대조는 알리기만 한다.** 쓰기와 기록을 막거나 고치지 않는다. 막는 것은 지금처럼 공유 build의 누출 검사뿐이다.
- **이 검사들은 서로 다른 신호이고, 지금의 상태들과도 합치지 않는다.** "수치가 결과에서 보임"은 실행 성공·근거 연결·재실행 비교·분석 검사·결론 검토 가운데
  어느 것도 아니다([용어집](../TERMINOLOGY-AND-LANGUAGE.md) 6절). 인사이트의 근거 칸, 출처 추적의 확인 줄, 확정 연결의 수에 들어가지 않는다.
  화면에서 보여 주는 방식은 후보를 비교해 소유자가 고른다(#188과 같은 방식).

공유가 막혔을 때 고치는 길은 #187이 기준선 측정과 후보 비교 뒤에 소유자 결정으로 고른다. 이 ADR은 그 선택이 지켜야 할 것만 정한다.

- 공유본의 보장을 낮추지 않는다. 검사 강도를 독자에 따라 낮추는 안은 보장을 바꾸는 결정이고 #187의 소유자 결정으로 남는다.
- build는 고른 버전의 바이트를 그대로 담고 같은 검사를 한다. 본문을 가리거나 고치지 않는다
  ([계약 D2](../CONTRACTS.md#d2-공유-범위의-무쓰기-미리보기-kit-0230), [공유 설계](../PUBLISH-AND-SHARING.md)).
- 저장된 Report 버전은 고치지 않는다(ADR-0013).
- 알리는 검사는 build보다 앞에 둘 수 있다. 알리는 것은 저장을 막지 않는다.

이 모델과 맞는 후보는 셋이고, #187이 먼저 검토할 방향으로 권한다(OQ8).

- **저장할 때 알림**: 형식을 판정하고, 공유 범위와 무관하게 판정되는 누출(환경 값)을 찾아 저장한 요청의 답으로 알린다.
- **원본을 두는 파생 버전**: 환경 값을 기호 참조로, 범위 밖 대상을 가리킨 참조를 자리표시자로 바꾼 버전을 kit이 만든다. 원본과 한 변환을 기록하고
  원본과 같다고 표시하지 않는다([보고서 산출물 설계](../REPORT-ARTIFACTS.md)의 "가공한 공유용 파일"). 같은 `report_id`의 버전인지, kit이 저장할 때
  만드는지 요청할 때 만드는지는 열려 있다.
- **기호 참조**(결정 4).

### 6. 프롬프트와 도구 표면

- 시스템 프롬프트에 붙이는 부분은 세션 동안 바이트가 같아야 한다. 기록에 따라 바뀌는 것(시작 시점의 상태, 변경분)은 메시지로 전한다.
  모델 제공자의 캐시는 요청의 앞부분이 같아야 맞고, 시스템 프롬프트는 여러 확장이 나눠 쓰기 때문이다.
- 세션 중에 바뀔 수 있는 사실은 고정 부분에 두지 않는다. 활성 프로젝트가 바뀌면 고정 부분을 새로 만든다.
- 지금의 맥락 블록은 그 요청에만 적용되고 쌓이지 않는다(계약 A). 이 결정에서는 변경분 메시지가 대화에 쌓이고, 시작 시점의 상태는 대화 압축 전까지
  그 시점 그대로다. 그 세션 자신의 기록은 변경분으로 다시 알리지 않는다.
- 이 ADR의 기능은 상시 도구를 더하지 않는다([제품 방향](../PRODUCT.md)의 설계 경계: 기능 확장이 상시 도구 수 증가를 뜻하지 않게 한다).
  알림은 기존 도구의 답과 프롬프트의 변경분에 붙고, 읽기는 기존 조회와 CLI에 붙는다.
- 호스트가 달라도 같은 규칙이다. 세션 동안 바뀌지 않는 맥락과 변경분을 호스트의 어느 자리에 넣을지는 어댑터가 정한다.

### 7. ADR-0015의 개정

채택하면 ADR-0015를 두 곳에서 고친다. `observed_activity`의 뜻·조건·형식과 나머지 결정은 그대로다.

**결정 1의 "범위 밖" 문단.** 다음 뜻으로 고친다. 원문의 나머지(telemetry의 `wrote_managed_path`는 그대로, `!` 명령을 관찰하지 않는 이유)는 둔다.

> 범위 밖: 관찰된 활동으로 기록하는 것은 aelix의 `bash` 호출뿐이다. write·edit 도구의 직접 쓰기와 다른 확장·MCP 도구의 호출은 관찰된 활동으로 기록하지 않고,
> [ADR-0016](0016-session-boundary-model.md)의 경계 사건으로 보아 세션 로그에 남기며 그 변경은 파일 상태의 대조가 다룬다. 사람의 `!`·`!!` 명령은 감싸지 않는다.
> aelix 밖 호스트는 그 호스트의 어댑터가 사건을 줄 때 같은 세션 로그를 갖는다.

**결정 5의 출력 문장과 대안 표의 "출력 저장".** 관찰된 활동의 기록과 첨부에 출력을 남기지 않는다는 뜻으로 좁히고, 호출 결과의 보관은 이 ADR의 결정 3이
정한다고 적는다.

반영하는 곳: ADR-0015 본문의 결정 1 문단, 결정 5의 출력 문장, 소유자 결정 표의 OQ2 행, 대안 표에 날짜와 함께 적는다(ADR-0006·ADR-0014가 ADR-0015의
개정을 적은 방식). [계약 C22](../CONTRACTS.md#c22-관찰된-활동-kit-0321-171)의 같은 문장은 구현 PR이 고친다.

ADR-0015가 기각한 입력 캡처(`sitecustomize`·`PYTHONPATH` 주입)는 이 ADR이 되살리지 않는다. kit이 띄우는 run 안에서 읽은 파일을 형식과 관계없이 남기는 것과,
프로젝트의 venv 안에서 도는 kit 밖 Python을 기록하는 것은 #191이 따로 정한다.

### 8. 주장하지 않는 것

- **완전성**: 사건을 주지 않는 호스트, 어댑터가 없는 프로세스, 프로젝트가 활성화되기 전의 호출, 상한을 넘은 결과와 훑기는 보이지 않는다.
- **기록이 되었다는 것**: write·edit와 다른 도구가 바꾼 파일은 가져오거나 run으로 다시 만들기 전에는 journal과 출처 추적에 나타나지 않는다.
  남는 곳은 git 밖의 세션 로그와 다음 프롬프트의 알림뿐이다.
- **인과**: 실행 창이 파일의 수정 시각을 포함한다는 것은 그 호출이 도는 동안 바뀌었다는 뜻이다. 그 호출이 바꿨다는 뜻이 아니다.
- **상태 대조의 범위**: 본 두 시점 사이의 차이다. 그 사이에 생겼다가 없어진 파일과 여러 번 덮어쓴 중간 판은 모른다. 세션의 첫 훑기 전의 변경은 모른다.
  범위는 관찰과 같아 `scripts/`와 관리 영역을 보지 않는다. 파일의 수정 시각에 기댄다. 상한에 걸려 버린 훑기는 실험에서 어디에도 남지 않았다.
- **수치 대조의 정확성**: 수치가 결과에서 보였다는 것은 그 수가 거기 있었다는 뜻이다. 같은 숫자의 다른 양일 수 있고, 짧은 수는 우연히 맞을 수 있다.
  기록이나 자기가 쓴 파일을 되읽은 결과에서 보인 것일 수 있다(순환). 보이지 않은 수치는 본 수들에서 계산한 값일 수 있다. 실험은 한 자리 수, 날짜·연도,
  한국어 수 단위를 찾지 않았고, 최근 호출과 읽는 양·시간에 상한을 두었다. 실제 분석에서 수치가 보이는 비율과 우연히 맞는 비율은 재지 않았다.
- **결과의 동일성**: 세션 로그의 해시는 어댑터가 본 결과의 해시다. 호스트나 다른 확장이 그 뒤에 결과를 고치면 모델이 본 것과 다를 수 있다.
- **호스트 사이의 동등성**: 호스트가 주는 사건과 전달할 수 있는 것이 다르면 남는 것도 다르다. 도구 표면, 사람 명령, 신뢰 확인은 사건 밖에 있고
  호스트마다 따로 만들어야 한다.
- **비밀의 제거**: 가림 규칙은 거부 목록이다. 규칙을 적용했다는 뜻이지 비밀이 남지 않았다는 뜻이 아니다. 임시 보관에는 규칙이 찾지 못한 비밀이 평문으로
  있을 수 있다.
- **재현**: 세션 로그와 보관된 결과는 재실행의 대상이 아니다. run의 보장([계약 C2](../CONTRACTS.md#c2-run-runsidrunjson))은 run에만 있다.
- **사람의 직접 분석에 대한 같은 검사**: 호스트 없이 CLI로 일하는 사람의 터미널 출력은 보이지 않는다. 상태 대조는 CLI로 돌릴 수 있고, 수치 대조는 볼 결과가 없다.

| OQ6 | 수치 대조로 kit이 찾은 호출을 kit이 그 기록의 참조로 올리는가 | 올리지 않는다. 기록의 참조는 저자의 인용이고, 인사이트의 근거 칸·출처 추적·확정 연결이 그것을 센다. kit이 찾은 것을 참조로 올리면 "수치가 보임"이 근거 연결에 섞인다. 답이 수치가 보인 호출을 알려 주므로 저자가 인용할 수 있다. 올리기로 한다면 확정 연결이 되지 않게 하고 저자의 인용과 따로 세며, 기록을 쓰기 전에 대조해야 한다 |
| OQ7 | 상태 대조가 찾은 변경을 다음 프롬프트에서 모델에게 알리는가 | 알린다. 에이전트 자신의 write·edit는 세션 로그에만 남기고 알리지 않는다. ADR-0015 OQ3(Python이 아닌 명령의 변경도 알림)을 다른 도구로 넓히는 것이다. 실제 모델의 반응은 재지 않았다 |
| OQ8 | #187의 후보 가운데 저장할 때 알림, 원본을 두는 파생 버전, 기호 참조를 먼저 검토할 방향으로 삼는가 | 삼는다. 고르는 것과 형식은 #187의 기준선 측정과 후보 비교 뒤의 소유자 결정이다(결정 5) |

## 대안과 선택 이유

| 대안 | 검토 결과 |
|---|---|
| 문제마다 ADR을 따로(지금의 Issue 구성 그대로) | 관찰 지점, 근거의 단위, 참조 방식이 Issue마다 정해져 넷이 서로 다른 경계를 갖게 된다. 형식은 따로 정하되 모델은 하나로 둔다 |
| 형식까지 담은 하나의 ADR | 기록 형식 변경이 여럿이라 설계 리뷰의 범위가 끝없이 커진다(리뷰 예산의 취지). 호스트 조사(#192)와 비정형 파일럿(#193) 전에 형식을 굳히게 된다 |
| `observed_activity`를 모든 도구로 넓힘 | journal 줄과 Timeline이 호출 수만큼 늘고, 채택한 기록 종류의 뜻이 바뀐다. ADR-0015가 "모든 bash 호출을 기록"을 기각한 이유가 그대로 적용된다 |
| 세션 로그를 journal의 새 기록 종류로 | 위와 같고, 그 줄들이 공유본의 내용 기준(`content_seq`)을 움직이지 않게 하려면 ADR-0014를 다시 개정해야 한다 |
| kit이 찾은 호출을 기록의 참조로 올림 | 기록의 참조는 인용이고 근거 연결로 세어진다. 우연히 맞거나 순환한 대조가 근거로 보이게 된다. 새 참조 종류의 첫 쓰기가 세션의 기록마다 표식의 floor를 올린다(OQ6) |
| MCP 서버 하나를 공통 표면으로 | 도구 표면은 옮길 수 있지만, MCP 서버는 자기 도구의 호출만 본다. 다른 도구의 호출과 결과, 프롬프트의 시점은 호스트의 hook이 있어야 보인다. 도구 표면을 어떻게 낼지는 #192가 정한다 |
| 프로젝트 venv 주입을 기본 기록 지점으로 | ADR-0015가 기각한 이유(사용자의 프로그램 동작을 바꿈, 이식 경계 밖)가 남아 있고, Python이 아닌 도구와 다른 호스트를 다루지 못한다. 깊이를 더하는 층으로 #191이 다룬다 |
| build가 본문의 환경 값을 가리고 통과시킴 | "사용자 바이트를 가리거나 재작성하지 않는다"(계약 D2)와 "P0에는 가린 사본이 없다"([공유 build 설계](../design/PUBLICATION-BUILD.md) OQ13)를 깬다 |
| 누출 검사를 독자에 따라 약하게 | 보장의 범위를 바꾼다. #187의 소유자 결정으로 남긴다 |
| 기호 참조를 강제(경로를 쓴 본문을 거절) | 본문 형식을 강제하지 않는다는 원칙(ADR-0013, 제품 방향의 설계 경계)을 깬다 |
| 수치 대조가 맞지 않으면 기록을 거절 | 보이지 않은 수치는 계산한 값일 수 있어 거짓 거절이 생기고, 강제하지 않는다는 성질(제품 방향의 "분석 표현과 자율성")을 깬다 |

## 결과와 영향

- 관찰의 범위가 "aelix의 bash"에서 "어댑터가 알린 모든 호출"로 넓어지지만 journal은 그만큼 늘지 않는다. 늘어나는 것은 git 밖의 세션 로그와 보관이다.
  그래서 다른 도구가 바꾼 파일은 "기록됨"이 아니라 "보이고 알려짐"이 된다(결정 8).
- 호스트를 더하는 일 가운데 관찰과 맥락 전달이 "사건을 옮기는 어댑터를 쓰는 일"이 된다. 판단 로직은 kit에 하나다. 도구 표면, 사람 명령, 신뢰 확인은
  호스트마다 남는다.
- run과 가져오기에 묶이지 않은 자료(도구의 결과, 등록한 원천)와 그 안의 위치를 가리킬 수 있게 된다. 무엇이 실제로 끊기는지는 #193의 파일럿이 본다.
- 공유에서 이 ADR이 바꾸는 것은 없다. #187이 고를 후보에 지킬 것과 방향을 준다. 기호 참조가 본문에서 줄이는 사유는 환경 값뿐이다.
  실제 보고서의 통과율이 얼마나 오르는지는 #187의 기준선으로 잰다.
- 비용: 호출마다 로그 한 줄과 결과 보관, 프롬프트와 에이전트 정지마다 파일 훑기 한 번, 기록마다 수치 대조("맥락과 현재 코드"의 실험값).
  프로젝트의 캐시에 결과 바이트가 쌓이고(상한 있음), 변경분 메시지가 대화에 쌓인다. 명령형 hook을 쓰는 호스트에서는 사건마다 프로세스 하나가 뜬다(재지 않았다).
- 계약 A가 넓어진다: `context`·`session_compact` hook, 모든 도구에 대한 `tool_result` 처리. 구현 PR이 계약 A와 용어집을 고친다.
- 사람의 직접 분석 경로는 바뀌지 않는다. 호스트가 없으면 세션 로그가 없고, 기록·실행·공유는 지금과 같다.

| 호출의 결과를 받는 가져오기(가져오기 기록의 원본 표기) | 참조 ADR 또는 구현 Issue | 결정 2의 둘째 길 |
| kit run 안의 읽기 기록 확대, 프로젝트 venv 안의 기록 | #191 | 결정 7의 마지막 문단 |

| 검사의 결과를 화면에서 보여 주는 방식 | 후보 비교 뒤 소유자 결정(#188과 같은 방식) | 결정 5 |

구현의 순서는 다음을 권한다: 프롬프트(결정 6) → 세션 로그(결정 1·2) → 결과 보관과 수치 대조(결정 3·5) → 상태 대조(결정 5) → 참조 → 다른 호스트.
앞의 넷은 실험이 시제품으로 만든 것이고, 보조 로그와 도구의 답·프롬프트만 바꾸며 기록 형식을 바꾸지 않는다. 참조를 쓰는 일은 참조 ADR과 schema,
버전 처리가 끝난 뒤에 시작한다. 뒤의 둘은 시제품이 없다.

## 확인하지 않은 것

- 실제 모델로 돌린 세션: 수치 대조의 구절과 변경분 알림에 모델이 어떻게 반응하는지, 토큰과 캐시 적중이 실제로 어떻게 달라지는지.
- aelix가 아닌 호스트에서의 동작. 호스트별 확장 지점은 #192가 공식 문서와 실제 버전으로 확인한다.
- 실제 MCP 서버와 실제 데이터 원천 어댑터, 별도 프로세스의 세션, Windows.
- 시제품이 없는 결정: 기호 참조와 위치 지정자, 호출을 가리키는 참조, 원천 등록, 보관된 결과의 가져오기, 저장할 때 알림과 파생 버전, 명령형 hook을 거치는
  경로(사건 사이의 상태를 파일에 두는 것과 동시 쓰기), 세션 로그를 git에서 제외한 배치, 가린 뒤의 인자 해시와 보관 전 가림.
- 실제 보고서의 공유 통과율과 막힌 사유의 분포(#187), 비정형 과제에서 근거가 끊기는 지점(#193), 근거가 남은 실행의 비율(#191).
