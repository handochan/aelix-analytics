# ADR-0008: 재사용 제안의 계수 단위와 베타 상시 모드의 범위

Date: 2026-10-03

Status: Accepted — 2026-10-03 소유자 결정, 결정 5의 순효과와 결정 6의 상세 열기는 2026-10-05 소유자 결정 (Issue #6)
[Issue #6](https://github.com/handochan/aelix-analytics/issues/6)의 두 질문 — 자동 검토·알림을 무엇으로 세는가, 베타의 상시 모드에서
모델 기반 상세 검토를 어떻게 하는가 — 에 소유자가 권장안을 골랐다. 채택은 결정의 확정이며 구현이 아니다. 현재 코드에는 재사용
제안 기능이 없고 [현재 계약](../CONTRACTS.md)도 바뀌지 않는다. 구현은 [#17](https://github.com/handochan/aelix-analytics/issues/17)이 한다.
아래의 설정 키·이벤트 필드·명령 이름은 제안이며 현재 동작이 아니다.
계수와 판정은 #4의 공통 기록 계약인 ADR-0006(docs/issue-4-record-contract 병합 뒤 링크)의 논리 키·확정 연결·추론 결박·
`record_update`에 기댄다. 그 계약이 '결과와 비용'의 기록 요구를 담지 않으면 #17 착수 전에 맞춘다.

## 배경

[제안 정책](../SKILL-PROPOSAL-POLICY.md)은 자동 검토·알림의 횟수를 서로 다른 단위로 적었다. 본문은 "checkpoint당 최대 1회 상세 검토,
세션당 최대 1회 자동 알림, 프로젝트 기준 24시간 cooldown" 중 가장 엄격한 것이고, 설정 예시는 검토·알림을 모두 세션당으로 셌다.
측정 목표도 세션 전체 단위였다(이 결정 직전 `d7b6f18`의 56–57행, 86행, 102–107행).

두 단위 모두 사람 경로에서 정의되지 않는다. 사람용 CLI에는 호스트 세션이 없다. 이벤트의 `session`은 aelix 세션 파일 경로가
있을 때만 남는다(현재 계약 C1). checkpoint는 아직 없다([#16](https://github.com/handochan/aelix-analytics/issues/16)).
이 단위 때문에 #17이 #16을 기다렸지만, [베타 품질 기준](../BETA-QUALITY-GATES.md) §5의 B3 의존은 B1뿐이다.

정책은 상시 모드를 "모델 없는 사전 검사 → 필요한 후보만 제한된 상세 검토"의 두 단계로 적었다(81–84행). 그런데 확장은 provider·
모델 API와 `send_message` 같은 세션 조작을 쓰지 않고(현재 계약 A), 사람 경로의 게이트는 모델 호출·시도 0회다(Q17-a).
자동 상세 검토를 실행할 경로가 지금 없다. 베타 품질 기준 §5는 상시 모델 검토를 무요청 모드와 결정적 사전 검사를 완성한 뒤에
더하라고 정했다.

## 결정

1. **요청 시(`on_demand`)가 기본값이고, 횟수는 프로젝트 기록으로 센다.** 호스트 세션과 checkpoint는 계수 단위가 아니다.
   세션은 출처 참조와 Aelix의 세션 한정 모드(결정 7)에만 쓴다. 단위는 동작마다 다르다.

| 동작 | 단위와 한도 |
|---|---|
| 요청 시 검토 | 명시적 요청 1건이 검토 1건이다. 자동 한도·창과 무관하고 창을 쓰지 않는다 |
| 자동 사전 검사·판정(`always_on`) | 마지막 검사 뒤 새 기록(journal seq·run 완료)이 있을 때와, 창이 끝난 뒤의 첫 발행 경계에서 증분으로 한다. 모델 호출도 횟수 한도도 없다 |
| 자동 알림(`always_on`) | 프로젝트당 롤링 24시간에 최대 1회 발행한다. 같은 후보는 새 근거(결정 5)가 있을 때만 다시 알린다. 거절·보류한 후보는 그때 남긴 사유 항목을 새 근거가 올릴 때만 다시 알리고, 그 밖에는 명시적 요청으로만 보인다 |

2. **24시간은 검증 전 초기값이다.** 빈도 설정은 창을 기본값 이상으로 두는 쪽(`cooldown_hours`)과 요청 시 모드로 자동 알림을
   멈추는 쪽만 받는다. 기본값보다 짧은 값은 설정 검사가 오류로 보고하고, 고칠 때까지 자동 알림을 하지 않는다. 기본값으로 조용히
   바꾸지 않는다. 기본값은 fixture 결과와 방해 측정을 근거로 바꾼다(베타 품질 기준 §3).
3. **이력은 journal에 있다.** 다음을 journal의 상태 이벤트로 남긴다.
   - 알림: 자동으로 발행했거나 요청 시 검토가 돌려준 후보. 대상 후보, 요청 구분(`trigger`: `requested`·`automatic`), 표면, 판정에
     쓴 근거 버전 집합과 항목별 점수, 기준(`as_of_seq`), 요청 주체와 실행 수단(#13)이 들어간다. 표면에 낸 사실이며 사람이 봤다는
     기록이 아니다. 요청 시 검토의 이벤트는 요청을 처리한 kit 동작이 쓰고, 모델이 따로 쓰지 않는다.
   - 거절·보류: 사유 항목(정책 §2의 필수 조건·점수 항목)과 그때의 근거 버전 집합·항목별 점수.
   - 모드 변경: 모드와 범위(`project`·`session`).
   - 후보 사이의 중복·통합 관계. 원래 후보와 그 이력은 지우지 않는다.

   캐시에는 재계산할 수 있는 진행 위치, 대기 집합(기준을 넘었으나 창 때문에 발행하지 않은 후보), 통계만 둔다. 새 세션·재시작·
   캐시 삭제는 새 알림 기회가 아니다. 요청 시 검토가 돌려준 후보는 자동 창을 쓰지 않지만 같은 후보의 자동 재알림을 막는다.
   기록된 후보와 발행한 알림을 목록으로 읽는 화면은 알림이 아니며 이벤트를 쓰지 않는다.
4. **알림은 기록한 뒤 발행한다.** 발행 직전 journal 잠금 안에서 모드·창·이력을 다시 확인하고 이벤트를 쓴 뒤 표면에 낸다. 표면에
   내지 못해도 다시 발행하지 않는다(중복보다 누락). 그 알림은 사람용 상태 화면에서 볼 수 있다(결정 7). 같은 확인이 동시 발행의
   중복과, 상시에서 요청 시로 바꾼 뒤의 대기 알림을 막는다. 대기 집합에서는 총점이 가장 높은 후보, 같으면 기준을 먼저 넘은 후보
   하나를 발행한다. 창은 마지막 자동 발행 이벤트의 기록 시각부터 센다. 시계가 그 시각보다 앞으로 돌아가 경계가 불분명하면 창 안으로
   보고, 상태 화면에 다음 자동 발행이 가능한 시각과 기다리는 이유(창·시계 역행)를 보인다.
5. **베타의 `always_on`은 모델 없이 판정한다.** 필수 조건과 점수는 [정책](../SKILL-PROPOSAL-POLICY.md) §2의 술어로만 매긴다.
   같은 기록이면 어느 구현이든 같은 점수를 낸다.
   - 근거는 확정 연결만 센다. 이름만 준 참조의 추론 결박은 어떤 항목도 올리지 않는다(#4의 소유자 결정).
   - run의 `ok`는 실행 성공이며 검사 통과가 아니다. 검사 기록(결과·검사한 코드 버전·검사 run)이 없으면 근거·검사는 1을 넘지
     않는다. 글 필드는 비어 있지 않은지만 본다.
   - 추정으로 표시한 기대 효과 기록은 순효과 1이며 필수 조건 `순효과 ≥ 1`을 채운다. 관측하지 않은 효과는 순효과 2를 받지
     않는다(2026-10-05 소유자 결정).
   - 독립 사용의 수는 후보를 썼다는 관측이나 확정 연결이 있고 상태가 `ok`이며 재실행이 아닌 run들이 가진 서로 다른 (스크립트
     경로, 입력 집합)의 수다.
   - 확인할 수 없는 항목은 0점이다. 기준을 넘은 후보만 제목·이유·근거 ID로 짧게 알린다. 기록된 후보가 없는 신호(예: 같은 프로젝트
     모듈을 다른 스크립트·입력의 run이 씀)는 요청 시 검토에서 미검증 아이디어로만 보여 주고 자동으로 알리지 않는다.
   - 후보 정체성은 후보 ID(논리 키)와 명시적 중복·통합 관계다. 자동 경로는 내용의 같음을 판정하지 않는다. 확정 근거가 모두, 이미
     알림·거절·보류 이력이 있는 다른 후보의 확정 근거에 드는 후보는 자동으로 알리지 않고 요청 시 검토에서 중복 의심으로 보인다.
   - 새 근거는 그 후보(와 관계로 묶인 후보)의 마지막 알림·거절·보류 이벤트가 남긴 근거 버전 집합에 없던 확정 근거가 점수 항목
     하나 이상을 그때의 단계보다 올린 것이다. 같은 근거의 재참조, 후보 문구·적용 조건의 수정, 추론 결박, 독립 사용이 아닌 run,
     다른 코드 버전의 검사는 새 근거가 아니다. 검사나 적용 범위의 변화는 그것을 보이는 새 확정 근거(예: 다른 입력의 통과 검사)가
     점수 항목을 올릴 때만 센다.
6. **모델 기반 상세 검토는 사람이 대화에서 요청한 턴에서만 한다.** 알림의 상세를 여는 읽기(CLI, `/analytics`, Workspace)는 모델
   호출 0회이고 이벤트를 쓰지 않는다. 모델 기반 상세 검토는 사람이 대화에서 알림을 보여 달라고 하거나 검토를 요청한 턴에서만 한다.
   사람 명령만으로 모델 검토를 시작하려면 확장이 턴을 시작해야 하므로(현재 계약 A의 변경) 베타는 하지 않는다(2026-10-05 소유자 결정).
   그 턴에서 에이전트가 요청 시 검토의 진입점을 부르면 kit이 `trigger=requested` 이벤트를 쓴다. 그 턴의 모델 사용량은 그 요청의
   상세 검토 사용량으로 따로 기록하고, 같은 턴의 다른 작업과 나눌 수 없으면 분리 불가로 표시한다(정책 §4). 확장은 provider·모델
   API를 부르지 않고 턴을 시작하지 않는다(현재 계약 A). 모델이 스스로 새 후보를 찾아 알리는 자동 상세 검토는 베타 뒤에
   [#44](https://github.com/handochan/aelix-analytics/issues/44)에서 측정한 뒤, 계약 A의 변경 여부와 함께 따로 결정한다.
7. **발행은 정해진 기존 표면에서만 한다.** 새 모델 도구는 더하지 않는다.
   - Aelix는 에이전트 턴이 끝난 뒤 사전 검사한다. 발행은 다음 턴을 시작할 때 그 턴의 맥락 블록에서 하거나, 사람 명령
     `/analytics`의 상태 출력에서 한다. 맥락 블록은 모델의 system prompt다(현재 계약 A). 거기에 낸 알림은 모델에 보이는 안내이며
     사람에게 보인 알림이 아니다. 제목·이유·근거 ID와 고정 지침 한 줄(사람에게 전하기만 하고, 사람이 요청하기 전에는 검토하지
     않는다)만 넣고 그 바이트·토큰을 따로 측정한다. 재사용 검토 지침·후보 목록은 넣지 않는다.
   - 사람용 CLI는 텍스트 `status`(`analytics status`, 런처가 `--text`로 부른다)에서만 발행한다.
   - kit의 JSON `status`, `context`, 모델 도구, Workspace는 기록된 후보와 발행한 알림을 목록으로만 보인다. #13이 에이전트
     요청으로 기록한 CLI 호출도 그렇다.
   - 사람용 상태 화면(`/analytics`, 텍스트 `status`, Workspace의 Insights)은 자동으로 발행한 알림 가운데 아직 수락·거절·보류하지
     않은 것을 보인다. 맥락 블록으로 낸 알림도 이 경로로 사람에게 닿으며, 이를 위해 모델 턴을 따로 시작하지 않는다.
   - run·query·import·오류 처리 중에는 발행하지 않는다.
   - 세션 한정 모드는 호스트 세션이 있는 Aelix에서만 사람 명령으로 바꾸고, 현재 세션 파일과 같은 `session`의 마지막 모드
     이벤트로 복원한다. 같은 파일을 여는 `/reload`·`/resume`은 그 모드를 유지하고, 새 파일을 만드는 `/new`·`/fork`는 프로젝트
     설정을 쓴다. CLI는 프로젝트 설정만 쓴다.
   - aelix UI 알림(`ui.notify`) 같은 새 호스트 표면을 쓰면 계약 A가 바뀌므로 A의 갱신과 headless 대비를 #17의 수용 조건에 넣는다.
     checkpoint(#16)가 생기면 그 생성을 발행 경계로 더할 수 있다. 계수 단위는 그대로다.
8. **설정은 프로젝트 표식의 `reuse_proposals`다.** `mode`(`on_demand`·`always_on`), `min_score`(초기값 8), `cooldown_hours`(기본값 24,
   기본값 이상), `measurement_targets`(모델 기반 상세 검토 1건당 입력 1,024·출력 256 tokens)를 둔다. 정책의 옛 예시 키
   `skill_proposals`와 세션별 한도(`*_per_session`)를 대체한다. 측정 목표는 실행 제한이 아니며 실행 허용 여부를 정하지 않는다.

## 대안과 선택 이유

| 대안 | 검토 결과 |
|---|---|
| checkpoint 구간마다 최대 1회 | "질문 하나가 끝나면 한 번"에 맞고 원문 변경이 적다. 그러나 #17이 #16을 계속 기다리고, checkpoint를 만들지 않는 사람 CLI에는 자동 알림이 사실상 없다. 에이전트가 checkpoint를 자주 만들면 알림도 잦아져 빈도가 다른 기능의 사용 습관에 묶인다 |
| 호스트 세션마다 최대 1회 | 확장의 메모리 상태로 가장 쉽게 구현한다. 그러나 세션이 없는 CLI와 의미가 갈리고, 세션을 새로 열수록 기회가 늘어 24시간에만 기대게 된다. 세션 카운터는 재시작하면 사라져 결국 journal 기록이 따로 필요하다 |
| 다음 턴에 주 모델이 상세 검토 | 새 표면 없이 모델 판단을 쓴다. 그러나 검토 비용이 분석 턴에 섞여 Q5의 별도 측정이 추정이 되고, 탐색 중에도 끼어들 수 있다. 사람 CLI에는 모델이 없어 두 경로의 의미가 갈린다 |
| 확장이 따로 모델 호출 | 비용을 정확히 나누고 분석 턴을 방해하지 않는다. 그러나 계약 A의 변경(provider·인증)과 요금·실패·취소·재시도 처리가 필요하고, 대화에 보이지 않는 모델 호출이 생긴다. CLI에는 적용할 수 없다 |
| 베타에서 상시 모드를 뺌 | #17이 가장 작다. 그러나 Q5의 요청 시/상시 옵션과 제품 문서를 줄여야 하고, #17을 베타에 남긴 소유자 결정(2026-10-03)과 맞지 않는다 |
| 알림을 aelix UI 알림으로 기본 표시 | 사람에게 바로 보인다. 그러나 확장이 쓰는 aelix 표면이 늘어 계약 A가 바뀌고, headless에서는 동작하지 않는다. 선택 경로로만 둔다 |
| 맥락 블록의 알림을 사람에게 보인 알림으로 기록 | 맥락 블록은 모델의 system prompt로 간다(현재 계약 A). 사람이 봤는지가 모델의 출력에 달리고, 보지 못한 알림이 유효 제안률의 분모를 부풀린다. 발행과 표면을 기록하고 사람용 상태 화면이 답하지 않은 알림을 보이게 했다 |
| 후보 정체성을 내용의 유사도로 판정 | 모델 없이는 판정할 수 없고 구현마다 갈린다. 후보 ID와 명시적 관계, 근거의 포함으로 판정하고, 근거가 같은 다른 후보를 자동으로 알리지 않는 누락을 감수한다 |

## 결과와 비용

- #17은 #16을 기다리지 않는다. [#13](https://github.com/handochan/aelix-analytics/issues/13)(공통 writer와 상태 변경 검증) 의존은
  남는다. #16은 checkpoint와 인계로 Q17 E2E([#23](https://github.com/handochan/aelix-analytics/issues/23))의 경로에 남는다.
- #16이 B4 경로에서 빠지므로 정정 이력 조회의 소유를 여기서 정한다. 정정(`supersedes`)·철회(`record_update`)는 #13의 공통 writer가
  쓰고 [#15](https://github.com/handochan/aelix-analytics/issues/15)의 제한 조회가 읽는다. #16은 그 이력으로 checkpoint의
  `needs_review`를 표시하지만 조회를 소유하지 않는다. 그래서 B4([#18](https://github.com/handochan/aelix-analytics/issues/18))는
  B2-a(#15)·B3(#17)에 의존하고 checkpoint를 기다리지 않는다(베타 품질 기준 §5).
- 모델이 스스로 새 후보를 찾지 않는다. 자동 알림은 사람이나 에이전트가 기록한 후보가 새 근거(두 번째 독립 사용, 검사)로 기준을
  넘을 때로 한정되어 체감 가치가 낮을 수 있다. 베타 리허설의 세 조건 비교(베타 품질 기준 §3)로 확인한다.
- 자동 판정은 글 필드의 내용을 판정하지 않는다. 알림은 적용 조건·기대 효과를 작성자의 기록으로 보이고, 내용의 검토는 요청 시
  검토가 한다. 검사 기록이 없으면 성공 run이 많아도 자동으로 알리지 않는다.
- 맥락 블록으로 낸 알림은 모델이 전하지 않으면 사람이 상태 화면을 볼 때까지 보이지 않는다. 그래도 창은 그 발행으로 쓰인다.
- 교대 중 한쪽(예: Aelix)에서 발행한 알림은 다른 쪽(CLI)에서 다시 발행하지 않는다. 상태 화면·Insights에서 답하지 않은 알림으로 본다.
- 24시간은 검증 전 값이다. 너무 드물면 유용한 후보가 늦게 보인다. fixture와 방해 측정으로 기본값을 조정한다.
- 이력이 journal에 있고 요청 구분이 남으므로, 베타 뒤 모델 기반 자동 검토나 checkpoint 경계를 더해도 기록을 다시 전환하지 않는다.
- 기록 요구. 상태 이벤트의 kind와 필드 이름은 [#4](https://github.com/handochan/aelix-analytics/issues/4)의 공통 기록 계약
  (ADR-0006, docs/issue-4-record-contract 병합 뒤 링크)이 정하고 #13의 writer가 쓴다. 이 ADR은 남길 내용만 정한다. 그 계약이
  B1–B4의 kind를 미리 정하므로 1–4는 그 계약이 이름을 정한다. 5–6은 #17이 그 계약의 선택 필드나 새 kind로 더한다.
  1. 알림: 결정 3의 필드(표면, 근거 버전 집합, 항목별 점수, 요청 주체·실행 수단 포함).
  2. 후보의 논리 키와 버전, 후보 사이의 중복·통합 관계.
  3. 거절·보류의 `record_update`와 그 사유 항목, 그때의 근거 버전 집합·항목별 점수.
  4. 모드 변경의 모드·범위·세션.
  5. 검사 기록: 결과(`passed`·`failed`), 검사한 코드 버전, 검사 run의 확정 연결, 경계 조건 표시.
  6. 사람이 표시한 반복 필요, 작성·유지 비용과 함께 측정한 효과 기록.
- 설정은 #13의 형식 전환 뒤 프로젝트 표식(`analytics.json`)에 둔다([#3](https://github.com/handochan/aelix-analytics/issues/3)).
  지금의 `lab.json`에 넣어도 동작하지 않는다.
- 현재 계약은 바뀌지 않는다. #17이 새 aelix 표면을 쓰면 그 PR에서 A를 고친다.

## 구현에서 확인할 것

#17의 수용 조건에 넣는다. 9의 리허설 항목을 빼면 모델 없는 결정적 fixture로 시험한다.

1. 단위: 요청 시 검토는 창을 쓰지 않는다. 24시간 안의 두 번째 자동 발행은 없다. 같은 후보는 새 근거로만, 거절·보류한 후보는
   사유 항목을 올린 새 근거로만 자동으로 다시 알린다. 후보 문구만 고치거나 같은 근거를 다시 참조해도, 같은 근거로 새 ID의 후보를
   써도 자동으로 알리지 않는다.
2. 이력과 창: 새 세션·재시작·캐시 삭제 뒤에도 재알림이 없고, 이력은 journal에서만 복원한다. 창이 지나면 새 기록이 없어도 다음
   발행 경계에서 대기 후보를 발행하고, 캐시를 지운 뒤에도 같다.
3. 사람 경로: 호스트 세션이 없는 CLI가 같은 창·이력을 쓰고 모델 호출이 0회다. Aelix에서 발행한 후보를 CLI가 다시 발행하지 않고
   답하지 않은 알림으로 보인다. JSON `status`·`context`·모델 도구와 에이전트 요청으로 기록된 CLI 호출은 발행하지 않는다.
4. 표면: 맥락 블록으로 발행하면 이벤트에 그 표면이 남고 사람용 상태 화면에 그 알림이 보인다. 알림의 상세를 여는 읽기는 모델 호출을
   시도하지 않는다(provider와 `send_message`를 실패하도록 무장한 기록 호스트로 시험).
5. 동시성과 시각: 두 프로세스가 같은 창에서 발행하려 하면 많아야 한 번 발행한다. 상시에서 요청 시로 바꾸면 대기 알림이 취소된다.
   시계가 마지막 자동 발행보다 앞으로 돌아가면 발행하지 않고 상태 화면에 이유를 보인다. 기본값보다 짧은 `cooldown_hours`는
   설정 오류로 보고하고 자동 발행을 하지 않는다.
6. 결정적 판정: 공유 점수 fixture에서 CLI와 Aelix, ProposalPolicy의 대체 구현이 같은 항목별 점수와 필수 조건 결과를 낸다. 검사
   기록이 없는 성공 run, 추론 결박, 재실행, 같은 (스크립트 경로, 입력 집합)의 run, 관측하지 않은 효과, 다른 코드 버전의 검사는
   각각 해당 항목을 올리지 않는다. 추정으로 표시한 기대 효과는 순효과를 1까지만 올리고 `순효과 ≥ 1`을 채운다. 기록된 후보가 없는
   신호는 자동으로 알리지 않는다. 자동 경로의 모델 호출은 0회다.
7. ProposalPolicy 계약 시험: 두 모드의 구현을 바꿔 넣어도 후보 정체성·journal 이력·cooldown·사용자 선택을 똑같이 지킨다.
   대체 정책이 거절 이력을 우회하면 실패다([아키텍처](../ARCHITECTURE.md) §10).
8. 세션 한정 모드: `/reload`·`/resume` 뒤에는 그 세션의 모드가 유지되고, `/new`·`/fork` 뒤에는 프로젝트 설정을 쓴다.
9. 측정: 맥락 블록에 더한 바이트·토큰(고정 지침 포함)과 요청한 상세 검토의 사용량을 분석 사용량과 따로 기록한다. 측정 목표를
   넘었다는 이유로 중단하지 않는다. Q5 리허설에서 맥락 블록 알림 뒤 사람이 요청하지 않은 상세 검토가 0회인지 확인하고, 표면별
   유효 제안률을 센다.
