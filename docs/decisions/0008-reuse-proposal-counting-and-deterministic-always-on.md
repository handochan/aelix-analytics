# ADR-0008: 재사용 제안의 계수 단위와 베타 상시 모드의 범위

Date: 2026-10-03

Status: Accepted — 2026-10-03 소유자 결정 (Issue #6)
[Issue #6](https://github.com/handochan/aelix-analytics/issues/6)의 두 질문 — 자동 검토·알림을 무엇으로 세는가, 베타의 상시 모드에서
모델 기반 상세 검토를 어떻게 하는가 — 에 소유자가 권장안을 골랐다. 채택은 결정의 확정이며 구현이 아니다. 현재 코드에는 재사용
제안 기능이 없고 [현재 계약](../CONTRACTS.md)도 바뀌지 않는다. 구현은 [#17](https://github.com/handochan/aelix-analytics/issues/17)이 한다.
아래의 설정 키·이벤트 필드·명령 이름은 제안이며 현재 동작이 아니다.

## 배경

[제안 정책](../SKILL-PROPOSAL-POLICY.md)은 자동 검토·알림의 횟수를 서로 다른 단위로 적었다. 본문은 "checkpoint당 최대 1회 상세 검토,
세션당 최대 1회 자동 알림, 프로젝트 기준 24시간 cooldown" 중 가장 엄격한 것이고, 설정 예시는 검토·알림을 모두 세션당으로 셌다.
측정 목표도 세션 전체 단위였다(이 결정 직전 `d7b6f18`의 56–57행, 86행, 102–107행).

두 단위 모두 사람 경로에서 정의되지 않는다. 사람용 CLI에는 호스트 세션이 없다. 이벤트의 `session`은 aelix 세션 파일 경로가
있을 때만 남는다(현재 계약 C1). checkpoint는 아직 없다([#16](https://github.com/handochan/aelix-analytics/issues/16)).
이 단위 때문에 #17이 #16을 기다렸지만, [베타 품질 기준](../BETA-QUALITY-GATES.md) §5의 B3 의존은 B1뿐이다.

정책은 상시 모드를 "모델 없는 사전 검사 → 필요한 후보만 제한된 상세 검토"의 두 단계로 적었다(81–84행). 그런데 확장은 provider·
모델 API와 `send_message` 같은 세션 조작을 쓰지 않고(현재 계약 A), 사람 경로의 게이트는 모델 호출·시도 0회다(Q17-a).
자동 상세 검토를 실행할 경로가 지금 없다. 베타 품질 기준 §5는 상시 모델 검토를 무요청 모드와 결정적 사전 검사를 완성한 뒤에
더하라고 정했다.

## 결정

1. **요청 시(`on_demand`)가 기본값이고, 횟수는 프로젝트 기록으로 센다.** 호스트 세션과 checkpoint는 계수 단위가 아니다.
   세션은 출처 참조와 Aelix의 세션 한정 모드(결정 7)에만 쓴다. 단위는 동작마다 다르다.

| 동작 | 단위와 한도 |
|---|---|
| 요청 시 검토 | 요청 1건이 검토 1건이다. 자동 한도·창과 무관하고 창을 쓰지 않는다 |
| 자동 사전 검사·판정(`always_on`) | 마지막 검사 뒤 새 기록(journal seq·run 완료)이 있을 때 자연스러운 경계에서 증분으로 한다. 모델 호출도 횟수 한도도 없다 |
| 자동 알림(`always_on`) | 프로젝트당 롤링 24시간에 최대 1회. 같은 후보는 새 근거·검사·적용 범위 변화가 있을 때만, 거절한 후보는 사유를 바꾸는 근거나 명시적 요청이 있을 때만 다시 알린다 |

2. **24시간은 검증 전 초기값이다.** 빈도 설정은 창을 늘리는 쪽(`cooldown_hours` ≥ 24)과 요청 시 모드로 자동 알림을 멈추는 쪽만 받는다.
   기본값은 fixture 결과와 방해 측정을 근거로 바꾼다(베타 품질 기준 §3).
3. **이력은 journal에 있다.** 사용자에게 보여 준 후보와 거절·보류·모드 변경을 journal의 상태 이벤트로 남긴다. 이벤트에는 대상 후보,
   요청 구분(`trigger`: `requested`·`automatic`), 결과, 판정에 쓴 근거 ID와 기준(`as_of_seq`), 모드 변경이면 범위(`project`·`session`)가
   들어간다. 캐시에는 재계산할 수 있는 진행 위치와 통계만 둔다. 새 세션·재시작·캐시 삭제는 새 알림 기회가 아니다.
   요청으로 보여 준 후보는 자동 창을 쓰지 않지만 같은 후보의 자동 재알림을 막는다. 기록된 후보를 목록으로 읽는 화면(Insights 등)은
   알림이 아니며 이벤트를 쓰지 않는다.
4. **알림은 기록한 뒤 보인다.** 표시 직전 journal 잠금 안에서 모드·창·거절 이력을 다시 확인하고 이벤트를 쓴 뒤 표시한다. 표시가
   실패해도 다시 알리지 않는다. 중복보다 누락을 택한다. 같은 확인이 동시 알림의 중복과, 상시에서 요청 시로 바꾼 뒤의 대기 알림을
   막는다. 창은 마지막 자동 알림 이벤트의 기록 시각부터 센다. 시계가 그 시각보다 앞으로 돌아가 경계가 불분명하면 창 안으로 본다.
5. **베타의 `always_on`은 모델 없이 판정한다.** 사전 검사와 필수 조건·점수([정책](../SKILL-PROPOSAL-POLICY.md) §2)는 후보 기록의
   필드(반복되는 문제·적용 조건·제외 조건·기대 효과·검사 run 링크)와 run 관측(모듈 해시·입력·상태)만으로 매긴다. 확인할 수 없는
   항목은 0점이고, 같은 run의 rerun은 독립 사용이 아니다. 기준을 넘은 후보만 제목·이유·근거 ID로 짧게 알린다. 기록된 후보가
   없는 신호(예: 같은 프로젝트 모듈을 다른 스크립트·입력의 run이 씀)는 요청 시 검토에서 미검증 아이디어로만 보여 주고 자동으로
   알리지 않는다.
6. **모델 기반 상세 검토는 사람이 알림을 열거나 요청할 때만 한다.** 그 검토는 요청 시 검토로 기록하고 사용량을 따로 센다.
   확장은 provider·모델 API를 부르지 않는다. 모델이 스스로 새 후보를 찾아 알리는 자동 상세 검토는 베타 뒤에
   [#44](https://github.com/handochan/aelix-analytics/issues/44)에서 측정한 뒤, 계약 A의 변경 여부와 함께 따로 결정한다.
7. **알림과 모드 변경은 기존 표면으로 한다.** 새 모델 도구는 더하지 않는다. Aelix는 에이전트 턴이 끝난 뒤 사전 검사하고, 다음 턴의 맥락 블록에 한 번 넣거나
   사람 명령(`/analytics`)에서 알린다. 맥락 블록에는 제목·이유·근거 ID만 넣고 그 바이트·토큰을 따로 측정한다. 이는 검토 지시가
   아니며, 재사용 검토 지침·후보 목록은 넣지 않는다. 사람용 CLI는 `status` 같은 검토 명령에서만 알린다. run·query·import·오류
   처리 중에는 알리지 않는다. 세션 한정 모드는 호스트 세션이 있는 Aelix에서만 사람 명령으로 바꾸고, CLI는 프로젝트 설정만 쓴다.
   aelix UI 알림(`ui.notify`) 같은 새 호스트 표면을 쓰면 계약 A가 바뀌므로 A의 갱신과 headless 대비를 #17의 수용 조건에 넣는다.
   checkpoint(#16)가 생기면 그 생성을 알림 경계로 더할 수 있다. 계수 단위는 그대로다.
8. **설정은 프로젝트 표식의 `reuse_proposals`다.** `mode`(`on_demand`·`always_on`), `min_score`(초기값 8), `cooldown_hours`(24 이상),
   `measurement_targets`(모델 기반 상세 검토 1건당 입력 1,024·출력 256 tokens)를 둔다. 정책의 옛 예시 키 `skill_proposals`와
   세션별 한도(`*_per_session`)를 대체한다. 측정 목표는 실행 제한이 아니며 실행 허용 여부를 정하지 않는다.

## 대안과 선택 이유

| 대안 | 검토 결과 |
|---|---|
| checkpoint 구간마다 최대 1회 | "질문 하나가 끝나면 한 번"에 맞고 원문 변경이 적다. 그러나 #17이 #16을 계속 기다리고, checkpoint를 만들지 않는 사람 CLI에는 자동 알림이 사실상 없다. 에이전트가 checkpoint를 자주 만들면 알림도 잦아져 빈도가 다른 기능의 사용 습관에 묶인다 |
| 호스트 세션마다 최대 1회 | 확장의 메모리 상태로 가장 쉽게 구현한다. 그러나 세션이 없는 CLI와 의미가 갈리고, 세션을 새로 열수록 기회가 늘어 24시간에만 기대게 된다. 세션 카운터는 재시작하면 사라져 결국 journal 기록이 따로 필요하다 |
| 다음 턴에 주 모델이 상세 검토 | 새 표면 없이 모델 판단을 쓴다. 그러나 검토 비용이 분석 턴에 섞여 Q5의 별도 측정이 추정이 되고, 탐색 중에도 끼어들 수 있다. 사람 CLI에는 모델이 없어 두 경로의 의미가 갈린다 |
| 확장이 따로 모델 호출 | 비용을 정확히 나누고 분석 턴을 방해하지 않는다. 그러나 계약 A의 변경(provider·인증)과 요금·실패·취소·재시도 처리가 필요하고, 대화에 보이지 않는 모델 호출이 생긴다. CLI에는 적용할 수 없다 |
| 베타에서 상시 모드를 뺌 | #17이 가장 작다. 그러나 Q5의 요청 시/상시 옵션과 제품 문서를 줄여야 하고, #17을 베타에 남긴 소유자 결정(2026-10-03)과 맞지 않는다 |
| 알림을 aelix UI 알림으로 기본 표시 | 사람에게 바로 보인다. 그러나 확장이 쓰는 aelix 표면이 늘어 계약 A가 바뀌고, headless에서는 동작하지 않는다. 선택 경로로만 둔다 |

## 결과와 비용

- #17은 #16을 기다리지 않는다. [#13](https://github.com/handochan/aelix-analytics/issues/13)(공통 writer와 상태 변경 검증) 의존은
  남는다. #16은 checkpoint와 인계로 Q17 E2E([#23](https://github.com/handochan/aelix-analytics/issues/23))의 경로에 남는다.
- #16이 B4 경로에서 빠지므로 정정 이력 조회의 소유를 여기서 정한다. 정정(`supersedes`)·철회(`record_update`)는 #13의 공통 writer가
  쓰고 [#15](https://github.com/handochan/aelix-analytics/issues/15)의 제한 조회가 읽는다. #16은 그 이력으로 checkpoint의
  `needs_review`를 표시하지만 조회를 소유하지 않는다. 그래서 B4([#18](https://github.com/handochan/aelix-analytics/issues/18))는
  B2-a(#15)·B3(#17)에 의존하고 checkpoint를 기다리지 않는다(베타 품질 기준 §5).
- 모델이 스스로 새 후보를 찾지 않는다. 자동 알림은 사람이나 에이전트가 기록한 후보가 새 근거(두 번째 독립 사용, 검사)로 기준을
  넘을 때로 한정되어 체감 가치가 낮을 수 있다. 베타 리허설의 세 조건 비교(베타 품질 기준 §3)로 확인한다.
- 교대 중 한쪽(예: Aelix)에 보인 알림은 다른 쪽(CLI)에 다시 뜨지 않는다. 상태 화면·Insights에서 조회한다.
- 24시간은 검증 전 값이다. 너무 드물면 유용한 후보가 늦게 보인다. fixture와 방해 측정으로 기본값을 조정한다.
- 이력이 journal에 있고 요청 구분이 남으므로, 베타 뒤 모델 기반 자동 검토나 checkpoint 경계를 더해도 기록을 다시 전환하지 않는다.
- 상태 이벤트의 kind와 필드 이름은 [#4](https://github.com/handochan/aelix-analytics/issues/4)의 공통 기록 계약(ADR-0006)이 정하고
  #13의 writer가 쓴다. 이 ADR은 남길 내용만 정한다. 그 계약이 B1–B4의 kind를 미리 정하므로 재사용 제안의 상태 이벤트도 그 목록에 든다.
- 설정은 #13의 형식 전환 뒤 프로젝트 표식(`analytics.json`)에 둔다([#3](https://github.com/handochan/aelix-analytics/issues/3)).
  지금의 `lab.json`에 넣어도 동작하지 않는다.
- 현재 계약은 바뀌지 않는다. #17이 새 aelix 표면을 쓰면 그 PR에서 A를 고친다.

## 구현에서 확인할 것

#17의 수용 조건에 넣는다. 모델 없는 결정적 fixture로 시험한다.

1. 단위: 요청 시 검토는 창을 쓰지 않는다. 24시간 안의 두 번째 자동 알림은 없다. 같은 후보는 새 근거로만, 거절한 후보는 사유를
   바꾸는 근거나 요청으로만 다시 알린다.
2. 이력: 새 세션·재시작·캐시 삭제 뒤에도 재알림이 없고, 이력은 journal에서만 복원한다.
3. 사람 경로: 호스트 세션이 없는 CLI가 같은 창·이력을 쓰고 모델 호출이 0회다. Aelix에서 알린 후보를 CLI가 다시 알리지 않는다.
4. 동시성과 시각: 두 프로세스가 같은 창에서 알리려 하면 많아야 한 번 알린다. 상시에서 요청 시로 바꾸면 대기 알림이 취소된다.
   시계가 마지막 자동 알림보다 앞으로 돌아가면 알리지 않는다.
5. 결정적 판정: 확인할 수 없는 항목은 0점이고, 같은 run의 rerun은 독립 사용이 아니며, 기록된 후보가 없는 신호는 자동으로
   알리지 않는다. 자동 경로의 모델 호출은 0회다.
6. ProposalPolicy 계약 시험: 두 모드의 구현을 바꿔 넣어도 후보 정체성·journal 이력·cooldown·사용자 선택을 똑같이 지킨다.
   대체 정책이 거절 이력을 우회하면 실패다([아키텍처](../ARCHITECTURE.md) §10).
7. 측정: 알림이 맥락 블록에 더한 바이트·토큰과 요청한 상세 검토의 사용량을 분석 사용량과 따로 기록한다. 측정 목표를 넘었다는
   이유로 중단하지 않는다.
