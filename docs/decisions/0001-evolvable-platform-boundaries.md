# ADR-0001: 지속 가능한 플랫폼의 핵심 계약과 교체 경계

Date: 2026-09-18

Status: Accepted — 2026-10-03 소유자 결정 (Issue #3)
2026-09-18의 제안을 [#8](https://github.com/handochan/aelix-analytics/issues/8)이 구현한 것([ADR-0003](0003-portable-boundaries-and-in-process-kit-loading.md)·[ADR-0004](0004-minimal-distribution-and-entry-points.md))에
맞춰 개정하고 채택했다. [Issue #3](https://github.com/handochan/aelix-analytics/issues/3)의 전환 순서([ADR-0005](0005-names-first-storage-with-the-new-writer.md))와
같은 날 결정해 그 결정 PR에 함께 기록했다. 결정 1–9의 방향은 바꾸지 않았다. 개정한 것은 아래의 적용 현황, OS마다 다른 구현의 기본값,
배치, 확인 항목의 소유 Issue다. 채택은 결정의 확정이며 구현 완료가 아니다. 현재 코드가 실제로 하는 것은 [현재 계약](../CONTRACTS.md)에 있다.

## 배경

Aelix Analytics는 베타 이후에도 지표·맥락·재사용·근거 탐색·보고서·게시·후속 분석·협업으로 확장한다.
현재 파일 중심 구현의 자유로운 분석 경험을 보존하면서, 기능 추가가 host·저장소·표시·정책을 함께 고치는 작업이 되지 않게 해야 한다.
분석 프로젝트와 공개 계약의 수명은 특정 모델·UI·kit 버전보다 길다.

## 결정

1. 책임과 의존 방향이 분명한 단일 배포 패키지로 시작한다. 도메인·응용 기능·포트·구현·진입점의 조립을 구분한다.
2. 지표·근거·버전·정정·관측 범위의 의미는 core가 소유한다. 구현 교체로 의미를 바꾸지 않는다.
3. 맥락 선택·검색·제안 정책·게시 범위 투영에는 필요한 Strategy 경계를 둔다. 저장·실행·캡처·표시·게시 대상은 어댑터로 연결한다.
4. 작은 Protocol과 명시적 주입·조합을 우선한다. 내부 인터페이스를 곧바로 공개 plugin 표준으로 고정하지 않는다.
5. 기록 쓰기를 공통 응용 경로에서 조정하고, 검색·관계·프로젝트 탐색 HTML·공유본은 원본의 버전 있는 읽기 모델로 만든다. 자유 형식 보고서의 저장 본문·첨부는 정본에 보존하며 내용 버전과 게시 버전을 구별한다.
6. 기록·스크립트 API·읽기·게시·배포 계약의 버전과 호환성을 각각 관리한다.
7. 모델의 자유 Python·라이브러리·방법 선택은 유지한다. Strategy 등록은 분석 방법의 실행 허가가 아니다.
8. 내부 확장점이 늘어도 상시 모델 도구를 그 수만큼 늘리지 않는다. 토큰 목표는 성능 측정 기준으로 유지한다.
9. 공개 명칭은 Analytics로 통일하고 Project·Workspace·Visualization·Report의 역할을 구별한다. 기본 UI·템플릿은 영어로 제공하며 사용자 내용의 언어와 원본 바이트는 보존한다. [용어집](../TERMINOLOGY-AND-LANGUAGE.md)을 함께 따른다.

## OS마다 다른 구현의 기본값

결정 1의 "진입점의 조립"([아키텍처](../ARCHITECTURE.md) §4의 조립)에는 예외가 하나 있다. OS마다 동작이 다른 플랫폼 포트
([ADR-0003](0003-portable-boundaries-and-in-process-kit-loading.md))는 `core`가 모듈을 불러올 때 이 프로세스의 구현을 한 번 골라 기본값으로
둔다(`core.PLATFORM`). 진입점은 이 구현을 따로 넘기지 않고, 시험과 다른 호출자는 `Project(root, platform=…)`로 다른 구현을 넣는다.
환경 변수·이름·기록 속 문자열로 고르지 않는다(ADR-0003 결정 4). OS는 프로세스마다 정해지며 사용자가 고르는 설정이 아니기 때문이다.
정책 Strategy와 저장·실행 backend·게시 어댑터는 이 예외에 들지 않는다. 진입점이 검토한 설정과 등록된 구현 ID로 조립해 명시적으로
넘긴다(아키텍처 §4·§6).

## 배치

[아키텍처](../ARCHITECTURE.md) §9의 트리는 목표 배치다. 기존 모듈을 그 트리로 한꺼번에 옮기지 않는다. 새 책임이 생기는 Issue가
그 모듈을 계층에 맞춰 두고 의존 방향 검사([#43](https://github.com/handochan/aelix-analytics/issues/43))에 등록한다.
첫 사례는 [#12](https://github.com/handochan/aelix-analytics/issues/12)의 읽기 모델과 [#13](https://github.com/handochan/aelix-analytics/issues/13)의
공통 writer다. 계층·Protocol·Strategy를 쓰임보다 먼저 만들지 않는다(아키텍처 §5·§9).
[#9](https://github.com/handochan/aelix-analytics/issues/9)가 `kit/labkit`을 `aelix_analytics` 패키지로 옮기는 것은 이 일괄 재배치가 아니다.
모듈 구성을 그대로 둔 채 이름을 바꾸는 명칭 결정의 일부다(ADR-0005 결정 7. ADR-0004 결정 9는 그 PR에서 개정한다).

## 대안과 선택 이유

| 대안 | 검토 결과 |
|---|---|
| 현재 파일에 기능별 조건 분기를 계속 추가 | 초기 변경은 작지만 기록 의미·UI·backend·정책의 결합이 커짐 |
| 처음부터 모든 기능을 plugin·마이크로서비스로 분리 | 아직 확인되지 않은 경계를 공개 계약·운영 비용으로 고정할 위험 |
| 명확한 내부 계약을 가진 단일 패키지 + 필요한 Strategy/adapter | 현재 실행 경험을 유지하면서 실제 변경 축부터 교체 가능성을 검증할 수 있음 |

### 채택 방식(2026-10-03)

| 대안 | 검토 결과 |
|---|---|
| 원안 그대로 채택 | 가장 빠르다. 그러나 "진입점의 조립"을 글자 그대로 읽으면 `core.PLATFORM` 기본값(ADR-0003 결정 4)이 위반으로 읽혀 리뷰마다 해석이 갈리고, 확인 항목을 맡을 곳이 없다 |

| #8의 구현에 맞춰 개정하고 지금 채택(채택) | #12·#13의 설계 리뷰에 구속력 있는 계층 기준이 생기고, 현재 코드와 아키텍처·기여 가이드의 상충이 풀린다. 배포본을 게시하기 전이라 배치를 바꾸는 비용이 가장 낮다. 증거가 없는 부분은 맡는 Issue가 있는 확인 항목으로 남긴다 |

## 결과와 비용

모듈 이동과 경계 정리, 공유 계약 시험, 새 진입점의 일관성과 과거 기록의 명시적 전환이 필요하다.
공통 계약이 존재한다는 사실만으로 데이터 무결성·샌드박스·트랜잭션·분산 실행을 보장하지 않는다.
새 구현은 자신의 지원 능력을 명시하고 실제 실패·취소·재시도·정합성 시험을 통과해야 한다.
베타에는 현재 요구를 만족하는 기본 구현을 제공하고, 추가 구현·외부 SDK 공개는 검증된 경계부터 진행한다.
채택으로 #12·#13 이후의 설계 리뷰는 결정 1–9와 이 개정을 기준으로 삼는다. 기준이 과하면 쓰이지 않는 계층·Protocol이 생길 수 있으므로
위 "배치"의 원칙을 함께 적용하고, 틀린 것으로 드러나면 후속 ADR로 대체한다.

## 구현에서 확인할 것

베타 기준 Q15의 증거를 포함한다. 증거가 아직 없는 항목은 맡는 Issue가 채운다.

1. host/분석 라이브러리 없이 core의 대표 읽기 흐름이 동작하는가? 지금 있는 증거는 import·로드와 기존 명령이다: 분석 라이브러리가 없는
   격리 환경의 aelix 0.1.0b2 통합(저장소 CI), 확장 로드 뒤 분석 라이브러리가 aelix 프로세스에 없음(`tests/test_platform.py`), 설치본의 3.11에서
   stdlib 명령(`tests/test_packaging.py`). 새 읽기 모델의 대표 호출은 #12가 더한다.
2. 실제 대체 정책·테스트 어댑터를 주입해도 ID·버전·근거·상태 의미가 유지되는가? 플랫폼 포트는 #8의 계약 시험
   (`tests/test_platform.py`의 `test_the_injected_platform_is_the_one_actually_used` 등)이 확인한다. 그 시험 방식을 교체 구현의 공용 계약 시험으로
   옮기는 일은 #43, 제안 정책의 두 모드는 [#17](https://github.com/handochan/aelix-analytics/issues/17),
   공유 범위 투영의 read/evidence는 [#20](https://github.com/handochan/aelix-analytics/issues/20)이 맡는다.
3. 기존 프로젝트·스크립트·Aelix 경로와 실사용 분석의 자유도가 보존되는가? 기존 프로젝트의 읽기와 전환은 #12·#13, 작업 스크립트와 옛 스냅샷은
   #9·#13(ADR-0005 결정 5·9), Aelix 경로는 저장소 CI의 aelix 통합, 자유도(Q13)는 [#24](https://github.com/handochan/aelix-analytics/issues/24)의 출시 리허설이 맡는다.
4. 파일 이동과 스키마·행동 변경을 분리하고, 현재 계약·시험·안내가 같은 구현을 설명하는가? #9-1은 이동만 하고 #13은 세 PR로 나눈다
   (ADR-0005 결정 7). 각 PR의 리뷰가 확인한다.
5. 도메인·공유 응용 코드가 host·UI·분석 라이브러리를 거꾸로 import하지 않는가? 함수 안 import까지 읽는 정적 검사와 제거 조건이 붙은 허용
   목록은 #43이 #9-1 뒤에 만든다. 확장 로드 뒤 `sys.modules`를 보는 런타임 시험은 함께 유지한다. #12·#13은 새 모듈을 계층표에 등록한다.
6. 두 프로젝트·세션의 상태가 섞이지 않는가? 한 aelix가 두 프로젝트를 번갈아 다루는 경우는 `tests/test_extension.py`(#8)가 확인한다.
   정책 상태(모드·cooldown·거절 이력)의 격리는 #17이 맡는다.

확인한 항목이 생기면 위 적용 현황을 갱신한다. 상세 설계는 [ARCHITECTURE.md](../ARCHITECTURE.md),
수용 기준은 [베타 품질 기준](../BETA-QUALITY-GATES.md)의 A0/Q15를 따른다.
