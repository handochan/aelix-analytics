# ADR-0005: 공개 이름을 먼저 바꾸고, 저장 형식은 새 기록 writer와 함께 한 번 바꾼다

Date: 2026-10-03

Status: Accepted — 2026-10-03 소유자 결정 (Issue #3)
[Issue #3](https://github.com/handochan/aelix-analytics/issues/3)의 권장안을 채택했다. 채택은 결정의 확정이며 구현 완료가 아니다.
적용은 [#9](https://github.com/handochan/aelix-analytics/issues/9)·[#10](https://github.com/handochan/aelix-analytics/issues/10)·[#13](https://github.com/handochan/aelix-analytics/issues/13)의 구현 PR이 한다.
현재 코드가 실제로 하는 것은 [현재 계약](../CONTRACTS.md)에 있고, 이 결정만으로 현재 계약을 바꾸지 않는다.
결정 3·6·7은 #4의 공통 기록 계약([ADR-0006](0006-common-record-contract.md))과 #37의 줄 끝([ADR-0007](0007-line-endings.md))에 기댄다.

## 배경

[용어집](../TERMINOLOGY-AND-LANGUAGE.md)은 공개 이름(명령·SDK·도구·환경 변수)과 저장 이름(표식·관리 디렉터리·경로·schema 가족)을 모두
Analytics로 바꾸는 목표를 정했다. [전체 용어 점검](../REVIEW-TERMINOLOGY-2026-09-18.md)은 이 일을 N0-a(공개 이름)·N0-b(저장·legacy)·
N0-c(영어 기본값)로 나누고(§6) 전환의 경계를 정했다(§5). 정하지 않은 것은 저장 이름을 언제 바꾸는가였다.

지금 저장 형식은 표식 `lab.json`, 관리 디렉터리 `.lab/`, 화면 `report/`, 가져온 데이터 `data/raw/`, run의 그림 `runs/<id>/charts/`,
schema 가족 `lab.project/1`·`lab.event/1`·`lab.run/1`·`lab.dataset/1`, 신뢰 목록 `lab-projects.json`이다(현재 계약 B·C).
신뢰 목록의 schema `lab.trust/1`은 코드에만 있다(`core.trust_project`).
코드 `d7b6f18`에서 확인한 사실은 다음과 같다.

- 구버전 kit을 막는 장치는 같은 schema 가족의 버전 숫자를 비교하는 것 하나다(`core.newer_schema`). journal 쓰기(`core._append_event_locked`)는
  표식을 읽지 않는다. `project_too_new`는 표식을 읽는 경로(status·report 등)에서만 난다.
- 현재 kit은 표식 `lab.json`이 있는 디렉터리만 프로젝트로 찾는다(`core.find_project`). 2026-10-03의 프로브(임시 디렉터리)에서 표식을
  `lab.project/2`로 고친 프로젝트에 현재 kit의 `note`가 `lab.event/1`을 기록했고(종료 코드 0), 표식 이름을 `analytics.json`으로 바꾸면
  `no_project`로 거절했다. 같은 가족의 번호를 올려서는 구버전 쓰기를 막지 못한다. 표식 이름의 변경은 옛 kit이 새 프로젝트를 찾지
  못하게 하는 탐색 장벽이다. 이미 프로젝트를 정한 쓰기는 막지 못한다: run 안의 SDK는 run이 정한 프로젝트(`capture.ACTIVE.project`)에
  쓰고, `core.add_note` 같은 쓰기는 표식을 확인하지 않는다.
- 읽기 작업에도 쓰기가 있다. `query`는 `.lab/queries.jsonl`에, status는 해시 캐시(`.lab/cache/`)에 쓴다. 확장의 status 도구와
  프롬프트 직전 hook은 맥락 동기화로 `.lab/context/`와 journal에, 도구 종료 hook은 `.lab/telemetry.jsonl`에 쓴다. 확장의 `lab_run`은
  inline 코드를 kit을 부르기 전에 `scripts/`에 쓴다.
- `core.read_events`는 다른 가족의 journal 줄을 조용히 버린다.
- 배포본은 어디에도 게시하지 않았다(현재 계약 F의 "배포 형태"). 설치본 사용자는 없지만 소유자의 기존 프로젝트가 있다.
  [제품 방향](../PRODUCT.md)의 "기록의 수명"과 [베타 기준](../BETA-QUALITY-GATES.md)의 Q7은 원본 보존·명시적 전환·구버전 쓰기 차단을 요구한다.
- 원본 보존·복사 전환·legacy 읽기·구버전 쓰기 차단은 저장 형식이 바뀔 때마다 새로 만들고 Q7 fixture로 검증해야 하는 장치다.
  참조·경로의 대응(`chart` → `visualization`, `data/raw/` → `data/imported/`)은 [#4](https://github.com/handochan/aelix-analytics/issues/4)가
  정할 공통 기록 계약에 달려 있다.
- #13은 B1-c와 N0-b를 이미 한 Issue로 묶어 #3·#4·#12·#9 뒤에 두었다. 베타 기준 §5는 B1-c가 N0 전체에 의존한다고 적고 있었다.

## 결정

1. **공개 이름과 영어 기본값을 지금 저장 형식 위에서 먼저 바꾼다.** #9(N0-a)와 #10(N0-c)은 명령·하위 명령·모델 도구·flag·환경 변수·
   모듈과 SDK 이름·help·오류 문구·UI label·템플릿 문장만 바꾼다.
2. **저장 이름은 #13(B1-c/N0-b)에서 새 기록 writer와 함께 바꾼다.** #13이 표식, 관리 디렉터리와 경로, schema 가족을 바꾸고 #4가 정한
   새 형식(`analytics.event/2` 등)의 writer를 연다. 필드 이름과 enum 값을 바꾼다면 그것도 #13에서 한다. #13까지 다음은 그대로다: `lab.json`,
   `.lab/`, `report/`, `data/raw/`, `runs/<id>/charts/`, `lab.*/1`, 필드 이름, enum 값(`via`의 `lab.chart`·`lab.read` 등, event kind의
   `gap`·`note` 등), 신뢰 목록(`lab-projects.json`, `lab.trust/1`), `kit_*` 필드. #9·#10은 `core.py`의 `MARKER`·`SCHEMA_*`와 관리 경로를
   바꾸지 않는다.
3. **사용자 프로젝트는 한 번만 전환한다.** 기존 프로젝트는 #13의 명시적 전환으로 `lab.*/1`에서 새 가족으로 한 번 옮긴다. 이 한 번이
   #14 이후의 기능(지표·초점·정정·재사용 제안·checkpoint·보고서·게시)에서도 지켜지도록 #4가 `analytics.event/2`의 kind와 참조 type을
   B1–B4 전체에 대해 미리 정한다. 그 뒤의 추가는 선택 필드와 새 kind, 표식의 최소 writer 버전 상향으로만 한다. 이 결정은 그 규칙을
   정하는 #4의 결정([ADR-0006](0006-common-record-contract.md))에 기댄다. 가족별 버전 번호는 #4·#13의 schema PR이 의미
   변경의 범위에 따라 정하고 한꺼번에 올리지 않는다(용어집 §3).
4. **책임은 다음과 같이 나눈다.**

5. **전환의 기본 동작은 다음과 같다.** 명령 이름·오류 코드 같은 세부는 #13의 설계에서 정하고, 새 공개 이름은 용어집에 먼저 등록한다.
   (#13의 설계: [기록 writer와 프로젝트 전환 설계](../design/RECORD-WRITER-AND-MIGRATION.md), Proposed. 이 결정의 내용을 바꾸지 않는다.)
   - 명시적인 명령으로만 전환한다. 조회·열기만으로 전환하지 않는다.
   - 목적지는 끝까지 푼 경로로 원본과 겹치지 않는다(원본 안도, 원본을 품은 상위도 아니다). 없거나 빈 디렉터리만 받고(init과 같다.
     중단된 전환을 잇는 경우는 아래), 목적지의 위쪽 디렉터리에 프로젝트 표식(`lab.json`·`analytics.json`)이 있으면 거절한다. 옛 kit의 탐색이 목적지에서 위쪽 프로젝트로
     올라가 그 프로젝트에 쓰지 않게 하기 위해서다. 목적지에는 새 표식 `analytics.json`만 두고 `lab.json`은 두지 않는다.
   - 기존 파일은 옮기지 않는다. 같은 상대 경로에 바이트 그대로 복사하고, 새 쓰기만 새 경로(`data/imported/`, `runs/<id>/visualizations/` 등)를
     쓴다. 기존 journal 줄도 그대로 두고 새 이벤트만 새 형식으로 더한다. 옮겨야 하는 파일이 생기면 그 대응을 전환 기록에 남기고,
     reader가 그 대응을 읽는다.
   - 큰 데이터도 복사가 기본이다. 원본 바이트를 바꿀 수 있는 hardlink는 기본으로 쓰지 않는다.
   - 복사하는 동안 원본의 journal·run 잠금(옛 kit과 같은 잠금)을 잡는다. 잠금 없이 쓰는 기록도 있으므로, 복사 전후로 원본의 파일
     목록이나 해시가 다르면 전환을 실패로 끝낸다. 복사 중 원본에 들어온 기록이 사본에서 조용히 빠지지 않게 하기 위해서다.
   - 목적지에는 먼저 전환 보고서를 만들고, 전환이 쓴 파일과 그 해시를 적어 가며 복사한다. 표식 `analytics.json`은 복사와 검증이
     끝난 뒤 마지막에 쓰고, 그때 목적지를 신뢰 목록에 더한다. 표식이 없는 목적지는 프로젝트가 아니므로 어떤 kit도 거기에 기록하지
     않는다. 이전 신뢰 항목을 자동으로 넓히지 않는다.
   - 중단된 전환은 같은 목적지에서 잇는다. 목적지에 전환 보고서가 적은 파일만 있고 해시가 맞을 때만 잇는다. 보고서에 없거나 해시가
     다른 파일이 있으면 덮어쓰지 않고 거절한다. 표식까지 쓴 목적지에는 다시 전환하지 않는다.
   - 전환 뒤에도 원본은 `lab.json` 프로젝트로 남는다. 그 뒤 옛 kit이 원본에 쓴 기록은 목적지에 없으며, 전환 보고서가 이를 알린다.
   - 작업 스크립트(`scripts/`)는 사본과 검토 가능한 diff로 새 SDK에 맞춘다. run 스냅샷은 바꾸지 않는다.
   - 관리 디렉터리 안의 context 이력·로그를 새 관리 디렉터리에 담는 방법은 #13의 설계에서 정한다. 전환한 프로젝트를 원래 경로에 두는
     방식을 #13이 고르면, 그것은 전환과 분리된 명시적 단계다. 원본의 바이트는 그대로 보존하고(옮길 뿐 고치지 않는다), 옛 kit의
     작업(run·세션·명령)이 끝났거나 멈춘 것을 확인한 뒤에만 한다. 원본의 잠금이 잡혀 있으면 거절한다. 표식 개명은 이미 프로젝트를
     정한 옛 프로세스의 쓰기를 막지 못하기 때문이다(배경).
6. **새 kit은 옛 프로젝트를 이렇게 다룬다.** `lab.json`만 있으면 legacy reader로 읽기를 허용하고, 일반 쓰기는 전환이 필요하다는 오류와
   전환 명령 안내로 거절한다. 두 표식이 함께 있으면 정해진 충돌 오류로 거절한다. 모르는 schema 가족과 미래 버전은 건너뛰지 않고 개수와
   함께 보고한다. 새 writer는 모든 쓰기에서 첫 부수 효과 전에 표식의 가족·버전과 #4가 정하는 최소 writer 요구([ADR-0006](0006-common-record-contract.md))를 확인한다. 이미 연 프로젝트나 프로세스 시작 때의 확인을 믿지 않고 쓰기 작업을 시작할
   때마다 표식을 다시 읽는다. 대상은 다음을 포함하며 이 목록으로 닫히지 않는다: note·import·run·Workspace 렌더, run 밖의 SDK 쓰기
   (`save`, run 밖의 시각화 파일), 확장의 도구와 hook, 확장이 kit을 부르기 전에 쓰는 inline 스크립트, 읽기 작업의 부수 쓰기(query 기록·
   캐시·telemetry·status와 프롬프트 직전의 맥락 동기화). 확인을 통과하지 못하면 일반 쓰기는 오류로 거절하고, 읽기 작업의 부수 쓰기는
   건너뛰고 읽기만 한다.
7. **PR 경계와 순서**
   - #9는 두 PR이다. #9-1은 `kit/labkit`을 `aelix_analytics` 패키지로 옮기고 import 이름·`-m` 대상·자식의 PYTHONPATH 루트만 바꾼다(기록의
     형식과 동작은 그대로다). [ADR-0004](0004-minimal-distribution-and-entry-points.md) 결정 9의 개정(경로가 바뀌는 결정 1·5·6 포함)과,
     경로가 바뀌는 [ADR-0003](0003-portable-boundaries-and-in-process-kit-loading.md) 결정 2·3과 기여 가이드의 경로는 이 PR에 코드와 함께
     고친다. `labkit`이라는 이름은 이 PR에서 사라지므로 결정 9의 안내와 `KIT_VERSION` 상향도 이 PR에 싣는다. 이 PR부터
     `python -m aelix_analytics`가 kit 명령이 되므로, 프로젝트 환경 밖에서 kit 명령을 실행하지 않게 하는 가드(프로젝트 환경으로 위임하거나
     거절)와 그 시험도 싣는다. #9-2는 함수·하위 명령·도구·flag·환경 변수의 이름을 바꾼다. #9-1은 다른 코드 PR보다 먼저 병합한다.
   - #9-2 뒤에 kit·확장·런처·체크아웃 명령이 읽던 옛 이름의 환경 변수(`LAB_PROJECT`·`LAB_ACTOR`·`LAB_SESSION`·`LAB_STYLE`·
     `AELIX_LAB_PROJECT`·`AELIX_LAB_TRUST_FILE`·`AELIX_LAB_KIT`·`AELIX_LAB_UV`)가 설정돼 있으면, 그것을 읽던 쪽은 무시하지 않고 새 이름을
     알려 주는 오류로 멈춘다. 옛 값을 따르는 별칭이 아니다. 조용히 무시하면 기록이 다른 프로젝트에 남고(`LAB_PROJECT`), 에이전트의 기록이
     사람의 기록이 되고(`LAB_ACTOR`), 격리용 파일 대신 실제 신뢰 목록에 쓰기(`AELIX_LAB_TRUST_FILE`) 때문이다.
   - #13은 #4·#12·#9 뒤이고, 다음 두 구현 PR 뒤에 병합한다. [#36](https://github.com/handochan/aelix-analytics/issues/36)의 기록 손실·
     계보 단절 항목(1·2·3·5·6번, 4번은 신뢰 목록만)을 고친 #36의 PR(2026-10-03 소유자 결정. [#39](https://github.com/handochan/aelix-analytics/issues/39)의
     베타까지 플랫폼 보강 동결의 예외. 규칙은 [ADR-0006](0006-common-record-contract.md)의 경로 정체성 절), [#37](https://github.com/handochan/aelix-analytics/issues/37)의
     줄 끝([ADR-0007](0007-line-endings.md))을 구현한 [#42](https://github.com/handochan/aelix-analytics/issues/42)의 PR.
     고치기 전의 경로 정체성과 줄 끝으로 전환과 새 기록을 만들지 않고, 전환이 쓰는 신뢰 목록의 링크 처리(4번)를
     먼저 고치기 위해서다.
   - #13은 세 PR로 나눈다. ① 새 가족과 섞인 journal의 읽기, 모르는 가족의 보고, 두 표식의 충돌 오류 ② 복사 전환(결정 5의 목적지 규칙과
     중단 뒤 잇기)·참조 매핑·전환 보고서·전후 해시 검증. 이 PR에서는 전환을 시험에서만 부르고 명령·도구로 열지 않는다 ③ 새 writer,
     모든 쓰기의 표식 확인(결정 6), 전환 명령, 신뢰 목록, `.gitignore`. 지표 같은 새 기능은 #14부터다.
   - 이 분할이 지키는 불변식: 어느 PR이 병합된 main에서도 `analytics.json`이 있는 디렉터리에는 옛 형식(`lab.*/1`, `.lab/`, `data/raw/`,
     `runs/<id>/charts/`)이 써지지 않는다. 그래서 `analytics.json` 프로젝트를 만드는 경로(전환 명령, 새 형식의 init)는 결정 6의 확인이
     들어가는 PR(③)에서 연다. `analytics.json`을 찾는 탐색을 ①·②에서 더하면, 같은 PR에서 그 디렉터리에 대한 쓰기를 결정 6의 대상
     전부(inline 스크립트 포함)에서 첫 부수 효과 전에 막는다. 일반 쓰기는 거절하고 읽기 작업의 부수 쓰기는 건너뛴다.
   - 이름 변경·대규모 파일 이동·기록 의미 변경을 한 PR에 섞지 않는다(베타 기준 §5). 이 규칙은 공개·코드 이름과 파일 이동에 적용한다.
     저장 이름의 개명은 결정 2대로 새 writer와 같은 PR(③)에 들어간다. 둘을 나누면 결정 3이 막으려는 두 번째 전환이 생긴다.
8. **베타 출시 전에는 wheel을 외부에 게시하지 않는다.** 외부 사용자가 이름과 저장 형식의 전환을 한 번만 보게 한다. 내부 평가용 빌드에는
   저장 형식이 바뀔 수 있다고 적는다. 이 조건은 #24의 계획에 적는다. 게시는 지금처럼 소유자가 승인한다.
9. **옛 run 스냅샷의 재실행에는 한계를 둔다.** #9-1부터 일반 run에서는 `labkit`을 import할 수 없고, 별칭은 두지 않는다. 옛 스냅샷을 새 kit으로
   다시 실행해 `No module named 'labkit'`로 실패하면, 이름 전환 전의 kit이 필요하다는 안내를 붙인다(`runner.py`의 `API_HINTS`, 기록의
   `env.kit_version`). 지금까지 `KIT_VERSION`은 모든 kit에서 0.1.0이므로, #9-1이 이를 올리고(배포 버전과 같다, ADR-0004 결정 2) 안내는
   그 버전보다 앞선 kit이 필요하다고 적는다. 원래 바이트를 새 SDK로 고쳐 돌린 실행은 그 run의 재실행으로 기록하지 않는다(점검 기록 §5 6항).
   재실행 전용 shim이 필요하면 작을 때는 #9에서 구현하고, 클 때는 새 Issue로 등록한다.

## 대안과 선택 이유

| 대안 | 검토 결과 |
|---|---|
| 저장 이름도 N0(#9 또는 별도 PR)에서 먼저 바꿈 | #9 직후 코드·파일·문서의 이름이 맞고, #9가 모든 쓰기 경로에 표식 확인을 넣으면 #13은 같은 가족의 번호만 올리면 된다. 그러나 전환기·legacy reader·두 표식 충돌·쓰기 차단을 #9에서 만들고 #13의 새 형식에서 다시 만들어야 한다. 사용자 프로젝트가 두 번 바뀌고(`lab.*/1` → `analytics.*/1` → 새 버전) Q7 fixture도 두 벌이 된다. 참조·경로 대응을 #4 전에 정해야 해 다시 할 위험이 크다. #9가 #4·#12를 기다리므로 두 흐름이 한 줄로 이어진다. #9의 완료 조건("저장 namespace 전환은 N0-b/B1-c 경계와 분리")과 점검 기록 §6의 N0-a 범위도 넘는다 |
| 전환기 없이 옛 프로젝트를 읽기만 함 | #13이 가장 작아지고 원본은 건드리지 않는다. 그러나 제품 방향의 "기록의 수명"과 Q7의 통과 증거(실패한 전환, 원본 보존의 해시 비교)를 줄여야 한다. 소유자의 기존 프로젝트를 지표·보고서·checkpoint로 이어 갈 수 없고, Q17의 인계를 기존 프로젝트로 시험할 수 없다. 출시 기준을 줄이는 제품 결정이 먼저 있어야 한다 |
| 작업 스크립트를 위해 `labkit` 별칭을 남김 | 옛 스냅샷이 그대로 다시 실행된다. 그러나 run 안에서 옛 이름과 새 이름을 함께 import할 수 있게 되어, `labkit`을 공개 이름으로 남기지 않고 사용자를 두 용어 체계로 안내하지 않는다는 용어집 §3·§8과 어긋난다 |
| 공개 이름 먼저, 저장 이름은 #13의 새 writer와 함께(채택) | 전환기·legacy reader·차단 장치를 한 번 만들고 Q7 fixture로 한 번 검증한다. 옛 kit의 탐색을 막는 표식 개명과 새 writer의 쓰기 확인이 같은 PR(결정 7의 ③)에서 열려, 옛 형식이 새 프로젝트에 섞이지 않는다(결정 7의 불변식). 참조·경로 대응은 #4 뒤에 만든다. #9·#10은 #4·#12를 기다리지 않고 바로 시작한다 |

## 결과와 비용

- #9 병합부터 #13 병합까지 main은 중간 상태다. `analytics` 명령이 `lab.json`·`.lab/`·`lab.*/1`을 다루고, 새 SDK 함수로 만든 기록에도
  옛 enum 값(`via`의 `lab.chart` 등)이 남는다. 현재 계약은 코드가 바뀌는 PR에서 이 상태를 사실대로 적는다.
- #9-1부터 기존 프로젝트의 작업 스크립트(`import labkit`)를 #13의 전환 전까지 손으로 고쳐야 한다. #9-2가 SDK 함수 이름도 바꾸므로
  (`note` → `record`, `chart` → `visualize`) 한 번에 고치려면 #9-2 뒤에 고친다. 그 사이 새로 만든 프로젝트도 `lab.*/1`이므로 #13에서 전환한다.
- #9-2 뒤에는 옛 이름의 환경 변수를 설정한 셸·설정이 오류로 멈추므로 새 이름으로 고쳐야 한다(결정 7).
- `labkit`을 import하는 옛 run 스냅샷은 새 kit으로 다시 실행되지 않는다(결정 9). Q15 증거의 "기존 형식·스크립트 호환"과 긴장이 있다.
  기존 형식은 legacy reader와 전환으로, 옛 스냅샷은 필요한 kit의 안내로 다룬다. 이 한계는 #9가 코드와 함께 현재 계약에 적는다.
- #13은 전환기와 새 writer를 함께 담아 커진다. 결정 7의 세 PR로 나누고, ②가 병합된 뒤 ③까지는 전환을 명령으로 쓸 수 없다.
- #4·#12가 늦어지면 중간 상태와 스크립트를 손으로 고치는 기간이 길어진다. 그 사이 게시하면 외부 사용자가 두 번 전환하게 되므로 결정 8을 둔다.
- B5 패키징이나 모델 평가가 새 파일 이름을 전제해야 하는 사정이 생기면 N0-b의 일부를 앞당긴다. 그때 첫 대안의 비용을 다시 따지고,
  모든 쓰기 경로의 표식 확인부터 넣는다.
- 이 결정은 문서 결정이다. 현재 계약은 코드가 바뀌는 #9·#13의 PR에서 갱신한다.

## 구현에서 확인할 것

1. #9·#10: 결정 2의 저장 값이 바뀌지 않는다(기존 프로젝트 fixture의 표식·경로·schema 가족이 PR 전후로 같다). 구·신 모델 도구를 함께
   노출하지 않는다. #9-1: `import labkit`의 실패에 결정 9의 안내가 붙고, `KIT_VERSION`이 올라가며, 설치된 패키지를
   `python -m aelix_analytics`로 부르면 어느 환경에서나 kit 명령을 실행하지 않는다. 진입점·개발·3.11 하한 시험처럼 실행 루트를
   PYTHONPATH로 명시한 호출은 그대로 허용한다(소유자 결정 2026-10-06, [Issue #9](https://github.com/handochan/aelix-analytics/issues/9)).
   목적은 분석 스크립트가 프로젝트의 uv 환경 밖에서 실행되는 것을 막는 것이다. #9-2: 결정 7의 옛 환경 변수마다 새 이름을 알려
   주는 오류가 난다. 옛 aelix flag `--lab-project`도 같은 이유로(aelix가 모르는 flag를 말없이 받아, 무시하면 작업 디렉터리의
   프로젝트에 기록된다) `--analytics-project`를 알려 주는 오류로 멈춘다. 별칭은 두지 않는다(소유자 결정 2026-10-05·06, Issue #9).
2. #13: Q7의 증거 — schema 가족·버전별 fixture, 두 표식의 충돌, 섞인 journal, 실패하거나 중단된 전환, 원본의 전후 해시 비교, 모든 일반 쓰기
   진입점의 구버전 차단. 기존 파일을 옮기지 않는 전환, 작업 스크립트의 diff, 신뢰 목록·`.gitignore`의 처리. 여기에 더해:
   ①·②·③이 각각 병합된 상태에서 결정 7의 불변식, 읽기 작업의 부수 쓰기와 inline 스크립트를 포함한 결정 6의 확인과 다시 읽기,
   겹치거나 비지 않았거나 위쪽에 표식이 있는 목적지의 거절, 복사 중 원본이 바뀐 전환의 실패, 중단된 전환을 덮어쓰지 않고 잇기,
   검증 전에는 표식과 신뢰 목록 항목이 없음, 전환 뒤 원본에 쓴 기록의 안내. 원래 경로에 두는 단계를 두면 실행 중인 옛 run·세션이
   있을 때의 거절도 시험한다.
3. #24: 베타 출시 전에 외부 게시가 없고, 내부 평가용 빌드에 저장 형식이 바뀔 수 있다는 표시가 있다.
