# ADR-0009: 첫 게시 대상 — 사용자가 지정한 폴더

Date: 2026-10-03

Status: Accepted — 2026-10-03 소유자 결정, 2026-10-05 소유자 결정으로 보완 (Issue #21)

[Issue #21](https://github.com/handochan/aelix-analytics/issues/21)의 완료 조건 1 "구현 전에 첫 대상·접근 범위·실패/재시도 계약을
기록한다"를 채우는 결정이다. 소유자가 조사의 권장안을 채택했다: 첫 P1 대상은 사용자가 지정한 폴더(로컬 폴더, 마운트한 공유,
동기화 폴더)이고, 접근 범위는 그 폴더의 권한이며 "팀 전용"으로 표시하지 않고, 확인을 마친 버전만 최신 주소가 된다.
채택은 구현이 아니다. `build`·`publish`는 현재 코드에 없고([현재 계약](../CONTRACTS.md)), 구현은
[#20](https://github.com/handochan/aelix-analytics/issues/20)의 독립 build 뒤에 #21에서 한다. #21은 그 구현을 위해 열려 있다.
구현 착수 조건은 [2026-10-17 소유자 결정](https://github.com/handochan/aelix-analytics/issues/21#issuecomment-6232441756)으로
#20 전체 완료에서 PR-3(build 폴더·manifest·결박) 병합 뒤로 완화했다. Report 내용 버전 구별의 수용은 #20 PR-4 뒤에 확인한다.

이 결정은 다음 두 결정에 기댄다.

- [ADR-0006](0006-common-record-contract.md)([#4](https://github.com/handochan/aelix-analytics/issues/4) 공통 기록 계약):
  기록 가족과 kind(`publication`·`publish_receipt`), 완료 기록을 마지막에 쓰는 커밋 규칙, Report 버전의 참조 형태, 프로젝트 밖
  경로의 표기, 게시의 재시도 범위, 표식의 `project_id`.
- [ADR-0007](0007-line-endings.md)([#37](https://github.com/handochan/aelix-analytics/issues/37) 줄 끝):
  kit이 쓰는 텍스트의 UTF-8·LF.

병합 순서가 바뀌거나 채택된 본문이 위와 다르면 이 ADR을 다시 대조한다. 명령의 인자 문법, 대상 안의 이름, 기록의 kind·필드
철자는 제안이며 구현 PR이 정하고 [용어집](../TERMINOLOGY-AND-LANGUAGE.md)에 먼저 등록한다(용어집 §8).

## 배경

P1은 하나의 검증된 대상부터 시작한다([공유 설계](../PUBLISH-AND-SHARING.md) §6·§8). [베타 기준](../BETA-QUALITY-GATES.md)의 Q14는
그 대상에서 다른 독자의 접근, 페이지와 자원의 일치, 고정 버전 주소와 최신 주소, 중단과 재시도, 이전 게시본 유지를 요구한다.
"팀 전용"은 대상이 실제 권한 기능을 가질 때만 말할 수 있다(공유 설계 §6 팀 접근). [아키텍처](../ARCHITECTURE.md) §5는 `Publisher`의 첫
구현 후보를 공유 폴더로 적었다.

이 결정을 좁힌 사실은 다음과 같다.

- 지금의 `report/`는 프로젝트 파일을 `../` 상대 경로와 `file://` 절대 URL로 가리킨다(`src/aelix_analytics/report.py`의 `Site.file_link`).
  그 자체로는 공유본이 아니며, 독립 패키지는 #20이 만든다.
- 소유자 팀의 실제 환경(웹 호스팅, SSO, 공유 드라이브)을 모른다. 새 자격 증명 없이 CI의 세 OS와 소유자 기기에서 끝까지 시험할 수
  있는 대상이 필요하다.
- 배포본 wheel은 의존성이 없다(현재 계약 F).
- 이 저장소는 private이고 Pages가 꺼져 있으며(`gh api repos/handochan/aelix-analytics`, 2026-10-03: `private: true`,
  `has_pages: false`), 요금제는 GitHub Free다([기여 가이드](../../CONTRIBUTING.md)의 저장소 CI). GitHub 문서(2026-10-03 확인)에 따르면
  GitHub Free의 Pages는 공개 저장소에서만 쓸 수 있고
  ([About GitHub Pages](https://docs.github.com/en/pages/getting-started-with-github-pages/about-github-pages)), Pages 사이트는
  저장소가 private이어도 인터넷에 공개되며([Creating a GitHub Pages site](https://docs.github.com/en/pages/getting-started-with-github-pages/creating-a-github-pages-site)),
  비공개 게시는 GitHub Enterprise Cloud의 조직에서만 된다([Changing the visibility](https://docs.github.com/en/pages/getting-started-with-github-pages/changing-the-visibility-of-your-github-pages-site)).
- 지금의 `AtomicFiles.replace`는 같은 디렉터리 안에서 대상을 덮어쓰는 교체(`os.replace`)이고, `FileLocks.exclusive`는 시간 제한
  없이 기다린다(`src/aelix_analytics/_platform.py`). 새 이름으로만 옮기는 연산과 대기 상한은 지금 포트에 없다.
- 사람 검증의 담당은 [#39](https://github.com/handochan/aelix-analytics/issues/39)의 2026-10-03 운영 결정이 Q6·Q17-a를 소유자에게
  넘겼다. Q14의 실제 다른 독자 열람([#24](https://github.com/handochan/aelix-analytics/issues/24))도 소유자가 한다(2026-10-05 소유자
  결정, 결정 10).

## 결정

1. **첫 대상은 사용자가 지정한 폴더 하나다.** 로컬 폴더, 마운트한 네트워크 공유(SMB·NFS), 동기화 폴더(Dropbox·OneDrive 등)를 모두
   같은 폴더로 다룬다. 새 자격 증명·서버·의존성이 없다. 웹 주소와 접근 제어는 그 폴더와 폴더를 내보내는 인프라의 몫이다.
   대상과 프로젝트는 어느 쪽도 다른 쪽 안에 있으면 안 된다. 대상이 프로젝트 안이면 게시한 파일이 동시에 도는 run의 출력으로
   기록될 수 있고(현재 계약 B), 프로젝트가 대상 안이면 대상의 독자가 원시 데이터·기록·로그를 포함한 프로젝트 전체를 읽는다.
   받은 경로를 그대로 비교한 결과와 링크·junction을 끝까지 푼 실제 위치를 비교한 결과 가운데 하나라도 겹치면 거절한다.
   다른 provider는 같은 `Publisher` 포트와 receipt 계약의 adapter로 더한다(P2).
2. **명령은 `analytics publish`다.** 입력은 #20이 만든 빌드의 `publication_id`와 대상(폴더 경로 또는 저장한 대상 이름)이다.
   그 밖의 동작은 최신 주소를 사람이 고른 버전(이전 버전이나 더 오래된 빌드, 결정 5)으로 바꾸는 되돌리기 하나다. 인자 문법은
   구현 PR이 정한다(공유 설계 §1).
   제안: `analytics publish --build <publication_id> --to <폴더>`, 저장한 대상은 `--target <이름>`, channel 지정은 `--channel <이름>`,
   다른 프로젝트의 channel을 넘겨받는 선택은 `--reassign-channel`, 되돌리기는 `--switch-to <publication_id>`.
   kit의 하위 명령이므로 설치본의 `analytics` 런처와 체크아웃 래퍼가 같은 계약으로 얻는다.
   상시 `analytics_publish` 모델 도구는 두지 않는다. 에이전트는 사용자가 명시적으로 게시를 요청할 때 같은 CLI와 `/analytics`
   경로를 쓴다. 자동 게시는 P1에 넣지 않는다.
3. **저장한 대상은 git이 무시하는 로컬 설정에 둔다.** 폴더 경로는 기기마다 달라 프로젝트 기록에 넣지 않는다. 위치와 파일 이름은
   #13의 관리 디렉터리를 따라 구현 PR이 정하며, 새 프로젝트와 전환한 프로젝트 모두에서 git이 무시하는 곳이어야 한다.
   그때 쓴 경로는 receipt(결정 7)에 남는다.
4. **대상은 analytics가 소유한 폴더이고, 배치는 다음과 같다.**

   ```text
   <대상>/
     analytics-target.json             대상 표식. 형식 버전을 가진다
     .analytics-target.lock            잠금 파일. 정리하지 않는다
     publications/<publication_id>/    버전. manifest와 manifest가 적은 파일만 있고 한 번 쓰면 바꾸지 않는다
       index.html                      버전 주소
     projects/<channel>/
       latest.json                     최신 포인터의 정본
       index.html                      최신 주소. latest.json으로 만든 channel 페이지
     .staging/
       <attempt_id>.json               게시 시도의 소유 기록
       <attempt_id>/                   그 시도의 전송 사본
   ```

   - 대상이 없거나 비어 있으면 첫 게시가 표식을 만든다. 표식은 없을 때만 만든다(배타적 생성). OS나 동기화 프로그램의
     메타데이터(결정 6의 목록)만 있는 폴더는 빈 폴더로 본다. 표식이 없는데 비어 있지 않은 폴더, 형식 버전을 모르는 표식,
     상위 폴더에 다른 대상의 표식이 있는 폴더에는 아무것도 쓰지 않고 거절한다.
   - 관리 경로(표식, 잠금 파일, `publications`·`projects`·`.staging`과 그 아래 channel·버전·시도 디렉터리)에 있는 심볼릭 링크·junction은
     따라가지 않고 거절한다. `.staging`과 `publications`가 다른 볼륨이면 거절한다. 대상 경로까지의 링크는 풀어 쓰고, receipt에 받은 경로와
     푼 경로를 함께 적는다. analytics는 링크·junction을 만들지 않는다. Windows·SMB·동기화 폴더에서 만들 수 없거나 따라가지 않는다.
   - 게시는 버전 디렉터리에 파일을 더하거나 고치지 않는다. 게시 시각·대상 같은 전달 정보는 receipt와 포인터에만 둔다
     (공유 설계 §4: 전달 메타데이터는 계산 결과의 해시와 분리). 그래서 게시 시점과 이전 버전 목록(공유 설계 §3)은 버전
     주소가 아니라 channel 페이지가 보인다.
   - 표식·잠금 파일·소유 기록·`latest.json`·channel·`attempt_id`는 새 공개 이름이다. 구현 PR이 용어집 §5에 먼저 등록한다.
   - 표식·소유 기록·`latest.json`·channel 페이지는 kit이 쓰는 텍스트이므로 모든 OS에서 UTF-8·LF로 쓴다(ADR-0007).

   **channel은 한 프로젝트의 것이다.**

   - `latest.json`은 형식 버전, 소유 프로젝트의 `project_id`(ADR-0006의 표식 값), channel 이름, 최신 `publication_id`, 그 channel에서
     최신이었던 버전의 목록을 담는다. 목록의 항목은 `publication_id`, 패키지 해시, 빌드 순서(결정 5), 빌드 시각, 최신이 된
     시각, 그때의 `attempt_id`, 게시한 프로젝트의 `project_id`다.
   - `projects/<channel>/`에는 그 디렉터리가 없거나, 메타데이터와 publisher의 임시 파일만 있거나, `latest.json`이 이 프로젝트의
     것일 때만 쓴다. 다른 프로젝트의 channel은 `--reassign-channel`을 준 게시만 넘겨받는다. 넘겨받은 사실, 이전 소유 프로젝트와
     이전 최신은 receipt에 남고, 목록의 이전 항목은 지우지 않는다. publisher가 쓰지 않은 파일이 있는 channel 디렉터리는 넘겨받지도
     않는다.
   - channel을 정하지 않은 게시는 이 프로젝트가 그 대상에 이미 가진 channel을 쓴다. 없으면 프로젝트 제목의 slug로 만들고, slug가
     비면(한국어 제목 등) `project_id`에서 만든 짧은 이름으로 만든다. 이 프로젝트의 channel이 둘 이상이면 channel을 지정하라고
     거절한다.
   - channel 이름은 NFC로 만들고 Unicode 정규화와 대소문자를 무시해 비교한다. 이 비교로 같은 channel 디렉터리가 이미 있으면 그
     디렉터리를 같은 channel로 보고 위의 소유 규칙을 따른다. 같은 것이 둘 이상이면 거절한다. 모든 OS에서 쓸 수 없는 이름은
     거절한다([ADR-0003](0003-portable-boundaries-and-in-process-kit-loading.md) 결정 6).
   - 복사한 프로젝트는 같은 `project_id`를 가지므로(ADR-0006) 같은 channel의 소유자다. 복사본이 따로 게시하려면 channel을 지정한다.

   **최신 주소는 `latest.json`이 가리키는 버전이다.** 확인을 마친 버전만 이 포인터에 쓴다(결정 5). 보통은 성공한 게시 가운데
   빌드 순서가 가장 새 버전이고(공유 설계 §3), 되돌린 동안은 사람이 고른 버전이다. 용어집의 Latest(가장 최근 저장본)와 다른
   개념이므로 구현 PR이 최신 주소를 용어집에 등록한다.

   - channel 페이지는 최신 버전과 바로 이전 버전으로 가는 링크, 최신이 된 시각을 포함한 버전 목록, 소유 프로젝트, 접근 범위
     문구(결정 8)를 담고, 가리키는 `publication_id`를 기계가 읽을 수 있게 둔다. 가리키는 버전이 목록에서 가장 새 빌드가 아니면
     그 사실을 보인다. 링크는 `../../publications/<id>/index.html`처럼 대상 안의 상대 경로이고 `index.html`을 직접 가리킨다.
     `file://`에서는 디렉터리 주소가 `index.html`로 열리지 않는다.
   - 최신 버전으로 자동으로 옮기는 것은 페이지 안의 스크립트가 그 기기에서 최신 버전의 도착을 확인한 뒤에만 한다. entry 페이지가
     직접 불러오는 자원 가운데 정적 페이지가 `file://`와 HTTP에서 불러오기 성공을 알 수 있는 종류(스크립트·스타일시트·이미지 등.
     종류는 구현 PR이 측정해 정한다)를 모두 불러 보고, 모두 열리면 옮긴다. 그런 자원이 없거나 하나라도 열리지 않으면 옮기지
     않고, 최신 버전이 이 기기에 아직 다 도착하지 않았을 수 있다는 안내와 이전 버전 링크를 보인다. 스크립트가 꺼진 독자는
     `<noscript>` 안의 meta refresh로 확인 없이 옮긴다.
5. **게시는 다섯 단계이고, 최신 포인터에는 최종 확인을 마친 버전만 쓴다.**

   | 단계 | 하는 일 | 실패하거나 중단되면 |
   |---|---|---|
   | 전송 | 소유 기록을 쓴 뒤, 빌드 폴더에서 manifest와 manifest가 적은 파일만 `.staging/<attempt_id>/`에 복사한다 | 최신 주소는 그대로다. 자기 staging을 지우려 시도하고 결과를 receipt에 적는다 |
   | 확인 | staging에서 다시 읽어 결박과 대조하고(결정 6) 링크 규칙(결정 9)을 확인한다 | 전환하지 않는다. 맞지 않은 파일·링크를 receipt에 적는다 |
   | 확정 | staging 디렉터리를 `publications/<publication_id>/`로 옮긴다. 내용이 있는 항목을 바꾸지 않는 연산이다(아래) | 이미 있으면 결정 6의 같은 ID 판단으로 간다. 그 밖의 실패에서는 전환하지 않는다 |
   | 최종 확인 | 옮긴 위치에서 다시 읽어 결박과 대조한다 | 전환하지 않는다. 버전을 고치거나 지우지 않고 receipt에 적는다 |
   | 전환 | `latest.json`, 그다음 channel 페이지를 각각 원자적으로 교체한다 | 포인터마다 관찰한 상태를 receipt에 적는다(아래). 이전 포인터가 남았다고 가정하지 않는다 |

   - 전송·확인·확정·최종 확인은 "파일 전달" 하나의 재시도 단위이고, 전환은 별도 단위다(공유 설계 §6).
   - **확정 연산.** `AtomicFiles.replace`는 있는 대상을 덮어쓰고, 있는지 본 뒤 이름을 바꾸는 것은 원자적이지 않다. 확정은
     `AtomicFiles`에 더하는 연산(제안: `rename_new`)으로 한다. 같은 볼륨 안에서 디렉터리를 새 이름으로 옮기고, 그 이름에 내용이
     있는 항목(파일, 비어 있지 않은 디렉터리)이 있으면 아무것도 바꾸지 않고 "있음"으로 끝난다. 빈 디렉터리 하나만 있으면 그
     자리에 옮긴다(잃는 내용이 없다). POSIX는 `rename(2)`가 디렉터리를 비어 있지 않은 디렉터리나 파일 위로 옮기지 않는 것
     (ENOTEMPTY·EEXIST·ENOTDIR)에 기댄다. Windows는 교체 플래그 없는 `MoveFileExW`(`os.rename`)로 하고, 빈 디렉터리는 비어 있을
     때만 지운 뒤 옮기며, 다른 프로세스가 연 파일 때문에 생기는 거절은 `replace`처럼 정해 둔 횟수만 다시 시도한다. 다른
     볼륨이라는 오류(EXDEV)나 그 밖의 오류에서는 복사나 교체로 대신하지 않고 실패로 끝난다.
   - **포트.** 포인터 교체는 기존 `AtomicFiles.replace`(Windows의 교체 재시도 포함)를 쓴다. 확정 연산과 잠금의 대기 상한(아래)은
     새 포트가 아니라 기존 `AtomicFiles`·`FileLocks` 계약의 확장이다(ADR-0003 결정 1). 구현 PR이 포트 설명, 현재 계약, 대체
     구현을 주입한 계약 시험을 함께 고친다.
   - **결과가 불확실한 호출.** 이름 변경·교체 호출이 오류를 냈어도 이미 적용됐을 수 있다(NFS의 재전송 등). 오류 뒤에는 관련
     이름을 다시 읽고 호출의 반환이 아니라 관찰한 상태로 판단한다. 확정 뒤 staging이 없고 최종 위치가 결박과 맞으면 확정된
     것으로 본다. 다시 읽지 못하면 그 단계를 `unknown`으로 적고 전환하지 않는다.
   - **포인터의 상태.** receipt는 두 포인터 각각을 `old`(이 시도가 시작할 때 본 버전), `new`(이 시도의 버전), `other`(그사이 다른
     게시가 쓴 버전), `missing`(파일 없음. 첫 게시에서 아직 쓰지 않은 포인터 포함), `unknown`(다시 읽지 못함) 가운데 하나로 적는다.
     두 포인터를 묶는 트랜잭션은 없으므로 전환 도중에 멈추면 둘이 다를 수 있다. 첫 게시에서 `latest.json`만 바뀌면 channel 페이지는
     아직 없다. 두 포인터가 다르면 그 channel에 대한 다음 게시가 `latest.json`을 기준으로 channel 페이지를 다시 만든다.
   - **빌드 순서.** 일반 게시는 `latest.json`이 없거나(첫 게시) 이 빌드가 지금 최신보다 새 빌드일 때만 전환한다. 지금 최신이
     이 빌드면 아래처럼 channel 페이지만 맞춘다. 그 밖에는 버전은 확정하되 포인터를 바꾸지 않고 전환을 `not_newer`로 끝내며,
     CLI와 receipt에 되돌리기(`--switch-to`)로 바꿀 수 있다고 알린다. 더 오래된 빌드는 되돌리기로만 최신이 된다(2026-10-05 소유자
     결정). 빌드 순서는 그 빌드의 `publication` 기록이 프로젝트 journal에서 받은 seq다(ADR-0006: journal 잠금 안에서 배정). seq가
     더 크면 새 빌드이고, 빌드 시각·게시 시각 같은 벽시계로 정하지 않는다. 지금 최신의 순서는 `latest.json`의 목록 항목에서
     읽는다. 순서는 같은 `project_id`의 빌드끼리만 비교하고, 비교할 수 없으면 새 빌드로 보지 않는다. `--reassign-channel`로
     넘겨받는 게시는 순서를 비교하지 않고 전환한다. 복사한 프로젝트는 같은 `project_id`라도 seq가 따로 늘어나므로 같은 channel에
     함께 게시하지 않는다(결정 4).
   - **다른 게시와 겹칠 때.** 전환 직전에 `latest.json`을 다시 읽는다. 이미 이 시도의 버전이면 channel 페이지만 맞춘다. 이 시도가
     시작할 때 본 값과 다르면 바꾸지 않고 전환을 `superseded`로 끝낸다. 중단된 시도를 다시 실행하는 것은 새 시도이고, 그때의
     최신과 빌드 순서를 비교한다. 그래서 중단된 오래된 시도를 다시 실행해도 최신이 되돌아가지 않는다.
   - Ctrl+C 같은 중단을 받으면 다음 단계를 시작하지 않고 자기 staging을 지우려 시도한다. 전환 도중에 받으면 위의 포인터 상태로
     적는다. Windows에서 경로가 길어 쓰지 못하면 전송 실패로 끝난다.
   - **잠금.** 같은 대상의 게시는 잠금 파일을 `FileLocks`로 잡고 시도 전체를 진행한다. 대기에는 상한(값은 구현 PR이 정함)을 두고,
     넘으면 `target_busy`로 실패해 receipt에 적는다. 잠금 파일을 만들 수 없으면 실패한다. 파일 시스템이 잠금을 지원하지 않는다는
     오류면 잠금 없이 진행하고 receipt에 잠금 없음과 그 오류를 적는다.
   - **정리.** publisher의 이름 규칙에 맞는 항목(`.staging/`의 `<attempt_id>.json`과 `<attempt_id>/`, channel 디렉터리에서 이름에
     `attempt_id`를 담은 임시 파일)만 지운다. 소유 기록은 형식 버전, `attempt_id`, `project_id`, `publication_id`, 기기 식별자(OS가 주는
     기기 고유 값), pid, 시도의 시작 시각과 갱신 시각을 담는다. 시도는 진행하는 동안 한 시간보다 짧은 간격으로 갱신 시각을 고친다.
     다른 시도의 항목은 소유 기록이 같은 기기의 끝난 프로세스를 가리키거나(`ProcessControl.alive`가 아니라고 답함), 갱신 시각이
     24시간보다 오래됐을 때만 지운다. 호스트 이름만으로 같은 기기라고 판단하지 않고, 기기 식별자를 얻지 못하면 다른 기기로 본다.
     소유 기록이 없거나 읽을 수 없는 항목은 수정 시각이 24시간보다 오래됐을 때만 지운다. 표식, 잠금 파일, 이름 규칙에 맞지 않는
     항목은 지우지 않고 receipt에 관찰로 남긴다. 시도는 끝날 때(성공·실패·중단) 자기 소유 기록과 남은 staging을 지우려 시도하고
     결과를 receipt에 적는다.
   - **잠금이 듣지 않을 때.** 기기마다 따로인 동기화 폴더나 잠금이 전파되지 않는 마운트에서는 잠금을 잡아도 다른 기기의 게시를
     막지 못한다. 같은 대상에 동시에 게시하는 것은 지원하지 않는다. 겹쳐도 위 규칙으로 다음은 성립한다: 내용이 있는 버전은
     덮어쓰지 않고, 진행 중이며 24시간 안에 갱신한 다른 시도의 staging은 지우지 않으며, 최신 포인터에는 최종 확인을 마친 버전만
     쓴다.
     어느 쪽이 최신이 되는지, 다른 게시의 교체로 `latest.json` 목록의 항목 하나가 빠지는지는 보장하지 않는다. 빠진 항목의 버전도
     `publications/`와 그 프로젝트의 receipt에는 남는다.
6. **재시도의 단위는 `publication_id`, 패키지 해시, 같은 대상이고, 대조의 기준은 빌드 때 남긴 결박이다**(공유 설계 §6).
   - **결박.** #20의 build는 `publication_id`와 패키지 해시의 짝을 프로젝트 기록에 남긴다(ADR-0006의 `publication` 기록). 패키지
     해시는 manifest 파일 바이트의 sha256이고, manifest는 자기 자신을 뺀 패키지의 모든 파일을 담으므로(결정 9) manifest를 통해
     패키지 전체를 가리킨다. 프로젝트 기록에 결박이 없는 빌드는 게시하지 않는다.
   - **대조.** 한 디렉터리를 결박과 대조한다는 것은 manifest의 해시가 결박과 같고, 파일 목록이 아래 "버전의 구성"을 지키며, 모든
     파일의 바이트가 manifest의 sha256과 같은지 보는 것이다. 전송, 확인, 최종 확인, 재사용, 전환만 다시 하는 재시도, 되돌리기가
     모두 이 대조를 한다. 빌드 폴더의 지금 파일이나 대상에 있는 manifest만으로 판단하지 않는다.
   - 게시는 request_id를 요구하지 않는다. Report 저장의 request_id 재시도와 다른 규칙이며, 베타의 재시도 보장은 이 둘이다
     (ADR-0006). `attempt_id`는 시도를 구별할 뿐 재시도 판정에 쓰지 않는다.
   - 대상에 같은 `publication_id`의 버전이 있으면 그 버전을 결박과 대조한다. 맞으면 다시 쓰지 않고 재사용하고(전송 전에 있으면
     전송하지 않는다), 다르면 덮어쓰지 않고 거절한다.
   - **버전의 구성.** staging과 버전에는 manifest와 manifest가 적은 파일만 있어야 한다. 예외는 OS·동기화 프로그램이 만드는
     메타데이터의 닫힌 목록(`.DS_Store`·`desktop.ini`·`Thumbs.db` 등. 목록은 구현 PR이 정한다)이다. 목록의 이름은 같음 판단을 바꾸지
     않고 receipt에 관찰로 남는다. 그 밖의 파일·디렉터리·링크가 있으면 확인 실패이고 재사용하지 않는다. 게시는 불변 버전의 그
     항목을 지우거나 고치지 않고 경로를 알린다. 지울지는 사람이 정한다.
   - 되돌리기는 그 channel의 목록에 있는 버전이나, 이 프로젝트 기록에 결박이 있고 대상에 확정된 버전(전환하지 않은 더 오래된
     빌드)만 고른다. 프로젝트 기록의 결박으로 대조하고, 그 기록이 없는 기기에서는 목록 항목의 패키지 해시로 대조한다. 둘이
     다르면 거절한다. 어느 기준을 썼는지 receipt에 적는다.
   - 게시는 원본 프로젝트를 다시 읽지 않는다. 빌드 폴더의 파일이 게시 도중 바뀌면 결박과 맞지 않아 전환하지 않는다. 빌드
     폴더에 manifest 밖의 파일이 있어도 복사하지 않는다.
   - 버전 삭제는 지원하지 않는다(사람이 지운다). 이미 복사·동기화·다운로드된 사본은 회수할 수 없다(공유 설계 §6 게시 중단).
7. **게시 시도마다 시작 기록과 Publish receipt를 프로젝트 기록으로 남긴다.** 기록 가족·kind·필드 이름은 ADR-0006의 형식 안에서
   구현 PR이 정하고, 새 이름은 용어집에 먼저 등록한다(용어집 §8).
   - 시도는 대상의 내용(표식·staging·버전·포인터)을 바꾸기 전에 `attempt_id`·`publication_id`·대상·channel·시작 시각을 담은 시작
     기록을 쓴다. 쓰지 못하면 대상을 바꾸지 않고 끝난다. 시도가 끝나면(성공·실패·중단) 같은 `attempt_id`의 receipt를 쓴다.
     대상의 파일이 먼저이고 receipt가 마지막이다(ADR-0006의 커밋 규칙).
   - 시작 기록만 있고 receipt가 없는 시도는 결과가 기록되지 않은 시도로 읽는다. 성공으로 읽지 않는다. 강제 종료 뒤에는 대상의
     상태(남은 staging, 확정된 버전, 포인터)가 사실이다. 이 프로젝트가 같은 대상에 다음으로 게시할 때, 정리하거나 전환하기 전에
     그런 시도의 흔적(그 `attempt_id`의 소유 기록과 staging, 그 버전, 포인터가 그 시도의 것인지)을 그 시도를 가리켜 자기 receipt에
     적는다. 이전 기록은 고치지 않는다.
   - receipt를 쓰지 못하면 명령은 대상의 결과(주소)와 기록 실패를 함께 알리고 실패로 끝난다. 그 시도는 시작 기록만 남은 시도로
     읽힌다.
   - 되돌리기도 시도이며 같은 기록을 남긴다. 그 receipt는 동작이 되돌리기임을 적고, 파일 전달 없이 대조와 전환의 상태만 가진다.

   | 내용 | 기준 |
   |---|---|
   | 시도 | `attempt_id`. 같은 시도의 시작 기록과 receipt를 잇는다 |
   | 게시본 | `publication_id`와 패키지 해시, 대조에 쓴 결박의 출처. 빌드의 기록 기준은 빌드의 manifest에 있고 receipt는 `publication_id`로 가리킨다 |
   | 대상 | 저장한 대상 이름(있으면), 그때 쓴 폴더 경로와 링크를 푼 경로, 표식을 만들었는지. 프로젝트 밖 경로의 표기는 ADR-0006을 따른다 |
   | channel | channel 이름, 넘겨받았으면 이전 소유 프로젝트와 이전 최신 |
   | 시각 | 시작과 끝 |
   | 단계별 상태 | 전송·확인·확정·최종 확인·전환 각각의 `done`·`reused`·`failed`·`interrupted`·`not_started`·`unknown`, 전환의 `superseded`·`not_newer`. 실패한 단계·파일·링크와 이유, 확정에 쓴 방법, 잠금 상태 |
   | 포인터 | 두 포인터 각각의 상태(결정 5)와 전환 전의 최신 `publication_id` |
   | 주소 | 버전 주소, 최신 주소 |
   | 관찰 | 메타데이터 파일, 지우지 않은 항목, 결과가 기록되지 않은 이전 시도의 흔적, 원격 이동 링크 목록 |
   | 확인한 접근 범위 | 결정 8에서 실제로 확인한 것만 |
   | 포함한 Report 버전 | 빌드가 담은 `report_id + revision_id`(ADR-0006의 참조 형태). `publication_id`와 따로 적는다 |

   - 다른 독자가 같은 폴더를 여는 주소(다른 기기의 마운트 경로, UNC 경로, 폴더를 내보내는 HTTP 주소)는 analytics가 알 수 없다.
     추측해 적지 않는다.
8. **접근 범위는 폴더의 권한이다.** analytics는 화면·CLI·receipt 어디에도 대상을 "팀 전용"이라고 쓰지 않고, 그 폴더를 열 수 있는
   사람이 읽을 수 있다고 적는다. 한 대상 안의 모든 channel·버전·staging은 같은 독자 범위를 가진다. 독자가 다르면 대상을 나눈다.
   channel 페이지와 CLI도 이 대상을 열 수 있는 사람은 그 안의 모든 버전을 읽을 수 있다고 적는다. receipt에는 실제로 확인한 것만
   남긴다.
   - 게시한 계정이 대상에서 다시 읽은 결과(결정 5의 확인과 최종 확인).
   - POSIX에서 대상까지의 상위 디렉터리와 버전 디렉터리·파일의 그룹·기타 사용자 권한 비트(통과·읽기)의 관찰. 대상이 보고한
     값이며 ACL이나 서버 쪽 권한과 다를 수 있다. 다른 사용자가 읽을 수 없어 보이면 경고만 한다.
   - Windows ACL은 "확인 안 함"으로 적는다.

   권한을 바꾸지 않는다(chmod·ACL 변경 없음). 새 파일은 대상 폴더와 게시한 계정의 기본 권한을 받는다. 공개 범위를 자동으로 넓히지 않는다.
9. **#20의 패키지가 보장할 것.** 폴더 게시가 확인할 수 있도록 #20의 패키지와 manifest(공유 설계 §4의 `publication.json`, 이름은 #20이
   정함)는 다음을 지킨다.
   - manifest는 자기 자신을 뺀 모든 파일의 경로·바이트 수·sha256, entry `index.html`, 빌드 시각을 담는다.
   - build는 `publication_id`와 패키지 해시의 결박을 프로젝트 기록에 남긴다(결정 6).
   - 참조 규칙. 자원 참조(`src`·`srcset`·`<link href>`·CSS `url()`·`@import`처럼 문서가 불러오는 것)는 패키지 안의 상대 경로나
     `data:`만 쓴다. 이동 링크(`<a href>` 등)는 패키지 안의 상대 경로이거나 원격 URL(`http`·`https`·`mailto`)이다. 어느 쪽도
     `../`로 패키지 밖을 가리키거나 절대 경로·`file://`를 쓰지 않는다(공유 설계 §4). 원격 이동 링크는 허용하고 receipt에 목록으로
     남긴다. 게시의 확인과 #20의 공유 범위 검사는 같은 규칙을 쓴다. 스크립트가 실행 중에 만드는 참조는 정적 확인 밖이며 #20의
     시험이 맡는다.
   - 모든 OS에서 쓸 수 있는 이름. Windows 예약 이름이 없고, 대소문자나 Unicode 정규화만 다른 두 이름이 없다. 심볼릭 링크가 없다.
   - `publication_id`는 그대로 디렉터리 이름이 될 수 있고, 무작위 성분을 담아 프로젝트·기기 사이에서도 겹치지 않으며, 대소문자를
     구별하지 않는 대상에서도 다른 ID와 겹치지 않는다.
10. **검증.** 아래 "구현에서 확인할 것"을 #21의 수용 조건으로 삼는다. CI의 두 번째 계정과 HTTP 하위 경로는 대리 증거이고, 실제
    다른 독자의 열람은 [#24](https://github.com/handochan/aelix-analytics/issues/24) 리허설의 별도 증거다(공유 설계 §8: 실제 게시
    대상의 검증과 로컬 링크 검사는 서로 다른 증거). 실제 다른 독자의 열람은 소유자가 하며, 소유자의 다른 기기나 다른 계정으로
    게시본을 연 결과를 Q14의 통과로 본다(2026-10-05 소유자 결정). 수행자는 출시 리허설 결과표의 수행자 열에 적고, 증거에는
    확인한 기기·계정·경로를 그대로 적는다.

## 대안과 선택 이유

| 대안 | 검토 결과 |
|---|---|
| GitHub Pages 브랜치 게시 | 실제 웹 주소가 생기고 ref 갱신이 원자적이다. 그러나 push 권한·토큰과 CI용 시험 저장소·secret이 필요하다. GitHub Free에서는 공개 저장소가 필요하고 Pages 사이트는 인터넷에 공개되므로 분석 데이터가 노출될 위험이 크다(배경). 배포가 늦어 E2E가 느리고 불안정하며, git 이력에 모든 게시본이 남아 원격 사본을 사실상 지울 수 없다 |
| S3 호환 저장소 | bucket 정책·서명 URL로 팀 전용을 줄 수 있다. 그러나 자격 증명이 필요하고, SDK 의존성이나 서명 구현이 의존성 없는 wheel과 부딪친다. CI 검증은 MinIO 컨테이너를 쓰는 Linux뿐이라 세 플랫폼 원칙([ADR-0002](0002-python-support-and-platform-scope.md))과 맞지 않고, 브라우저로 열려면 정적 호스팅 설정이 또 필요하다 |
| 최신 주소를 심볼릭 링크로 | 교체가 원자적이지만 Windows·SMB·동기화 폴더에서 만들 수 없거나 따라가지 않는다 |
| staging을 대상 밖(프로젝트, 임시 디렉터리)에 | 볼륨이 달라 확정이 원자적 이름 변경이 아니라 복사가 된다 |
| 같은 ID의 버전 디렉터리를 덮어쓰기 | 독자가 이미 연 버전 주소의 내용이 바뀐다. 버전 주소는 불변이다(공유 설계 §3) |
| 확정을 `AtomicFiles.replace`나 "있는지 본 뒤 이름 변경"으로 | `replace`는 있는 대상을 덮어쓰고, 확인과 이름 변경 사이에 다른 게시가 끼어들 수 있다 |
| 기존 폴더에 그대로 게시 | 사용자의 `index.html`이나 다른 도구의 `.staging/`을 교체하거나 지운다. 표식으로 analytics가 소유한 폴더만 쓴다 |
| channel을 제목 slug만으로 | 같은 제목이나 빈 slug의 두 프로젝트가 서로의 최신 주소를 조용히 바꾸고 버전 목록이 섞인다 |
| 남은 staging을 모두 지움 | 잠금이 듣지 않는 대상에서 다른 기기의 진행 중인 시도를 지운다 |
| 잠금을 잡지 못하면 거절 | 잠금 서비스가 없는 마운트가 대상에서 빠진다. 계약은 잠금 없이도 덮어쓰기와 확인하지 않은 전환을 막는다 |
| channel 페이지를 meta refresh로만 옮김 | 동기화 폴더의 다른 기기에서 아직 도착하지 않은 버전으로 독자를 보낸다. 스크립트가 꺼진 독자에게만 쓴다 |
| 마지막으로 성공한 게시를 최신으로(경고만) | 중단된 오래된 시도를 다시 실행하면 더 새 최신이 되돌아간다. 경고로는 막지 못한다(2026-10-05 소유자 결정으로 빌드 순서를 택함) |
| 빌드 시각이나 게시 시각으로 새 빌드를 판정 | 기기마다 시계가 다르고 게시 순서는 빌드 순서가 아니다. journal의 seq는 한 프로젝트 안에서 단조 증가한다 |
| 게시 재시도를 request_id로 판정 | 게시 단위는 이미 만든 `publication_id`와 해시다(공유 설계 §6). 같은 빌드는 어느 요청으로 다시 게시해도 같은 결과여야 한다 |
| 다른 사용자가 읽게 chmod | 공개 범위를 사용자 모르게 넓힌다 |
| 대상을 "팀 전용"으로 표시 | 폴더 대상에는 analytics가 확인할 수 있는 팀 권한 기능이 없다(공유 설계 §6 팀 접근) |
| 대상 경로를 프로젝트 기록에 둠 | 기기마다 경로가 달라 다른 기기에서는 틀린 설정이 된다 |
| 상시 `analytics_publish` 모델 도구 | 상시 도구 표면이 늘어난다(Q11). 게시는 사람의 명시적 요청으로 CLI·`/analytics`를 쓴다(공유 설계 §1) |

## 결과와 비용

- analytics는 웹 주소와 접근 제어를 제공하지 않는다. 팀이 웹 호스팅이나 SSO를 요구하면 P2의 adapter를 앞당긴다. `Publisher` 포트,
  receipt, staging과 전환 계약은 그대로 다시 쓰므로 되돌리는 비용은 adapter 하나다.
- 동기화 폴더에서 확인을 마친 버전만 가리킨다는 보장은 게시한 기기의 대상에 대한 것이다. 다른 기기에는 포인터와 버전의 파일이
  따로 도착한다. channel 페이지는 확인할 수 있는 자원이 도착한 뒤에만 옮기고 아니면 이전 버전을 안내하지만, 정적 페이지는 entry
  HTML과 데이터 파일의 도착을 확인하지 못하고 스크립트가 꺼진 독자는 확인 없이 옮겨진다. 다른 기기의 독자가 일부만 도착한
  최신 버전을 열 수 있다. 이것은 동기화 폴더에 대한 P1의 명시한 한계이며, 동기화 폴더는 P1 대상으로 남는다(2026-10-05 소유자
  결정). 구현 PR이 현재 계약 G와 README의 "현재 공유 범위"에 적는다. 독자 기기에서 버전 전체를 확인하는 수단은 독자 기기 검증
  Issue [#48](https://github.com/handochan/aelix-analytics/issues/48)가 다룬다. staging의 파일도 동기화된다.
- 네트워크 볼륨의 잠금, 동기화 폴더의 전파 순서, 같은 대상의 동시 게시는 검증하지 않는 범위다. 구현 PR이 현재 계약 G에 적고,
  `analytics publish`의 현재 동작을 현재 계약에, README의 "현재 공유 범위"를 함께 고친다.
- 최종 확인으로 버전의 모든 바이트를 대상에서 한 번 더 읽는다. 네트워크 대상에서는 게시가 그만큼 느리다.
- 더 오래된 빌드를 최신으로 하려면 게시한 뒤 되돌리기를 한 번 더 실행한다. 복사한 프로젝트끼리는 seq로 빌드 시점을 비교할 수
  없다.
- 공유 폴더를 비공개로 오해할 위험은 receipt와 화면 문구(결정 8)로 줄인다. 권한의 실제 범위는 폴더를 관리하는 사람이 정한다.
- receipt의 주소는 게시한 기기에서의 주소다. 다른 독자의 주소는 폴더를 여는 방법에 달려 있다.
- 실제 팀원 기기에서의 열람은 CI로 증명할 수 없고, Q14도 소유자의 다른 기기·계정으로 통과하므로(결정 10) 팀원의 열람과 팀
  권한은 확인하지 않는다. 대리 증거와 리허설 증거를 따로 남긴다.
- #20의 패키지 규칙(결정 9)이 늘어난다. #20은 설계 단계부터 이 규칙을 따른다.

## 구현에서 확인할 것

#21의 수용 조건이다. 각 항목은 명령·환경·코드 기준·결과를 증거로 남기고, 실행하지 않은 것은 `not_run`으로 적는다.

1. CI Linux(필수): 두 번째 OS 계정이 버전의 HTML·이미지·JS·첨부를 file 경로로 직접 연다. 이것이 권한의 증거다. 다른 사용자가
   읽을 수 없는 위치의 대상에서는 경고가 나오고 두 번째 계정의 읽기가 실패하는 것도 확인한다. HTTP 하위 경로는 일회용 시험 상위
   폴더를 루프백에만 내보내(`python -m http.server --bind 127.0.0.1`) 링크와 하위 경로가 풀리는지 확인하는 자원 해석의 증거다.
   서버를 띄운 계정을 적고, HTTP 결과로 접근 권한을 추론하지 않는다.
2. macOS·Windows: 두 번째 계정을 만들어 같은 읽기를 시도하고 결과대로 기록한다. Windows에서는 루프백 SMB 공유(`New-SmbShare`)를
   거친 게시와 읽기도 측정한다. macOS는 저장소 CI의 macOS 실행(라벨·수동·주간)에서 돈다.
3. 세 OS: 다섯 단계의 각 경계와 두 포인터 사이에서 중단을 주입한다. 첫 게시와 이후 게시에서 포인터에 확인한 버전만 쓰였는지,
   두 포인터의 상태가 receipt와 같은지, 다시 실행이 재사용과 전환으로 끝나는지 확인한다. 전환이 끊긴 빌드 A 뒤에 더 새 빌드 B를
   게시하고 A를 다시 게시하면 최신은 B로 남고 전환이 `not_newer`이며, 되돌리기로만 A가 최신이 되는지 확인한다. 빌드 시각이
   seq와 반대인 두 빌드도 seq로 판정되는지 확인한다.
4. 같은 빌드는 재사용하고 같은 ID의 다른 내용은 거절한다. 버전에 넣은 manifest 밖 파일은 거절하되 지우거나 고치지 않고,
   메타데이터 목록의 파일은 판단을 바꾸지 않는다. 빌드 폴더의 manifest 밖 파일은 복사하지 않는다. 되돌리기는 결박과 대조한
   뒤에만 전환한다.
5. 게시 도중 원본 프로젝트나 빌드의 파일을 바꾼다. 게시는 원본을 다시 읽지 않고, 빌드가 바뀌면 전환하지 않는다.
6. 대상의 소유와 경계: 빈 폴더에는 표식을 만들고, 표식 없이 비어 있지 않은 폴더(사용자의 `index.html`·`.staging/`이 있는 경우
   포함)에는 아무것도 쓰지 않고 거절한다. 다른 대상 안의 폴더, 프로젝트 안의 대상, 대상 안의 프로젝트(링크·junction을 거친 경우
   포함), 관리 경로의 링크·junction, 다른 볼륨을 거절한다. 대상의 버전 바이트가 빌드와 같고, 게시가 링크를 만들지 않으며 권한을
   바꾸지 않는다.
7. channel: 같은 slug나 빈 slug를 가진 두 프로젝트의 두 번째 게시는 거절된다. 대소문자·Unicode 정규화만 다른 이름은 같은
   channel로 판정된다. `--reassign-channel`로 넘겨받은 사실이 receipt에 남는다. 이식할 수 없는 channel 이름은 거절한다.
8. 확정 연산: 세 OS와 측정할 수 있는 마운트(Windows 루프백 SMB 등)에서 내용이 있는 대상 이름은 바뀌지 않고, 빈 디렉터리
   자리에는 옮기며, 다른 볼륨에서는 실패한다. Windows에서 다른 프로세스(백신, 색인, 동기화 프로그램)가 연 파일 때문에 디렉터리
   이동이 거절되는 경우를 측정해 재시도 규칙을 정한다. 포트 계약의 확장(확정 연산, 잠금 대기 상한)은 대체 구현을 주입한 계약
   시험으로 확인한다(ADR-0003).
9. 잠금: 잠금을 지원하지 않는 마운트에서의 동작, 대기 상한을 넘긴 `target_busy`, 잠금 없이 겹친 두 게시에서 진행 중인 다른
   시도의 staging이 지워지지 않고 최신 포인터에 확인한 버전만 쓰이는지 측정해 receipt와 현재 계약 G에 적는다.
10. 기록: 전환 뒤 receipt 전에 강제 종료한다. 시작 기록이 남고, 다음 게시가 그 흔적을 적으며, 이전 기록을 고치지 않는다.
    receipt를 쓰지 못하는 경우의 결과도 확인한다.
11. channel 페이지: 최신 버전의 파일 일부가 없는 사본에서 스크립트가 옮기지 않고 안내와 이전 버전 링크를 보이는지, 스크립트를
    끈 경우를 `file://`와 HTTP에서 확인한다. 정적 페이지가 도착을 알 수 있는 자원의 종류를 측정해 적는다.
12. 실제 다른 독자의 열람(#24): 소유자가 다른 기기나 다른 계정으로 게시본을 연다. 이것이 Q14의 통과다(2026-10-05 소유자 결정).
    수행자는 결과표의 수행자 열에 적고, 기기·계정·경로를 그대로 적는다. 이 결과는 그 기기·계정에서 읽혔다는 증거이며 팀원의
    열람이나 팀 권한의 확인으로 옮겨 적지 않는다. 이 증거가 없으면 `not_run`이다.
