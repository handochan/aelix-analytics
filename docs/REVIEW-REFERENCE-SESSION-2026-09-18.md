# 제품화 참고 세션 검토: 탐색에서 지표·후속 분석까지

검토일: 2026-09-18 · 상태: 로컬 실사용 기록의 읽기 전용 검토. 제품 방향과 후속 검증의 근거이며 지원·분석 정확성의 인증은 아니다.

## 1. 결론과 관측 범위

이 세션에서 보존할 핵심 경험은 **모델이 자유롭게 Python을 작성하고, 데이터를 보며 분석 방법과 지표를 확장하고,
오류를 고친 뒤 사용자 요청에 맞춰 결과를 발전시키는 동안 프로젝트 기록이 함께 남는 것**이다.
기록·지표·메모리 기능은 이 흐름을 더 잘 이해하고 이어 가도록 보강해야 한다.
고정된 분석 절차·사전 지표 등록·허용된 알고리즘 목록을 선행 조건으로 만들면 현재의 유용성을 줄일 수 있다.

사용자가 제품화 가능성을 느낀 참고 사례로 지정한 프로젝트를 확인했다.
입력은 장비 이상 탐지 예제의 트레이스 데이터다. 이 사례의 실사용 경험과 실제 장비의 탐지 성능 검증을 구별한다.

이 세션을 Qwen의 실행 성공 증거로 사용하지 않는다.

## 2. 실제 분석이 이어진 과정

`SESSION`은 위 JSONL의 1-based 줄 번호, `PROJECT`는 실제 lab 프로젝트를 뜻한다.
원문 대화·데이터·이미지 대신 검토에 필요한 요약과 로컬 증거 위치를 남긴다.

| 구간 | 관측된 행동 | 참고할 제품 경험 | 증거 |
|---|---|---|---|
| EDA 요청 | import 후 SQL로 구조를 확인하고 자유 Python으로 분포·프로파일·장비 비교·후보를 그림 | 시작 시 완성된 지표·분석 계획을 요구하지 않아도 탐색이 가능 | SESSION L3–36, scripts/01, journal e3–e13 |
| 작업 위치 수정 | 세션 cwd와 활성 프로젝트가 달라 첫 run이 거절됨. 일반 bash로 코드를 올바른 scripts 위치에 이동 | 오류는 구체적인 프로젝트 경로와 복구 방법을 알려야 함 | SESSION L14–18 |
| 기록 API 오류 복구 | `lab.note(..., refs=...)` 오류 뒤 스크립트를 수정해 성공 | 분석 코드와 기록 API의 자연스러운 사용, 복구 가능한 오류가 중요 | SESSION L18–23, journal e4/e6 |
| 스텝 특성 분석 | 스텝 프로파일을 저장한 뒤 램프 구간의 특성을 보고 시점별 프로파일·점수로 확장 | 한 사용자 요청 안에서도 모델이 방법을 선택·보완할 수 있어야 함 | SESSION L37–44, journal e14–e19 |
| 구현 오류 복구 | Polars scalar 접근 오류와 edit 불일치를 고치고 계산을 이어 감 | 실패가 있어도 코드·출력·진행 상태를 보존하며 수정 가능 | SESSION L44–53, journal e16/e17 |
| 발견과 정의 정리 | 주요·보조 이상 점수를 decision으로 남기고 CONTEXT의 질문·정의·다음 작업을 갱신 | 분석 중에 정의가 생기고 다음 방향으로 이어지는 메모리 | journal e19/e20, CONTEXT 버전 3개 |
| 사용자 요청으로 시각화 확장 | 한 센서의 비교를 모든 센서의 패널로 확장 | 고정된 chart spec 없이 사용자 의도에 맞춰 구성 변경 | SESSION L59–64, scripts/04, journal e21/e22 |

30개 도구 호출은 `lab_import` 1, `lab_query` 4, `lab_run` 7, `lab_note` 5,
일반 `write` 5, `edit` 4, `read` 3, `bash` 1이었다. 이 수는 사용한 도구 종류이며 로드된 전체 도구 수를 뜻하지 않는다.
프로젝트 telemetry와 세션 호출 집계가 일치한다. 오류 표시 4회는 위치 검사·실행 2회·edit 1회다.
모든 run에 입력 기록이 있고 `lab.read`/Polars 관측 경로가 남아 있다. 도구가 없었던 비교 실험과 혼동하지 않는다.

## 3. 지표가 분석 중에 형성된 직접 사례

처음 요청은 데이터의 EDA였고, 미리 등록된 이상 지표 목록은 없었다.
분석은 다음과 같이 발전했다. 모두 `z` 또는 이탈이라는 표현을 쓰지만 의미와 기준 모집단이 다르다.

| 지표·방법 | 실제 계산의 의미 | 정의에 남길 요소 |
|---|---|---|
| 트레이스 평균의 3σ 이탈 | 센서별 각 트레이스 평균을 모아 그 평균들의 분포와 비교 | 트레이스 단위, 센서, 평균 분포의 표준편차 |
| 컨텍스트×스텝 점수 | 트레이스의 스텝 평균을 sensor×step의 전체 샘플 평균·표준편차로 표준화 | 평가 값의 집계 단위와 분모 표준편차의 집계 단위 |
| 시점별 샘플 점수 | 같은 sensor×relativeTime의 프로파일과 개별 샘플을 비교 | 정렬 시간, 기준 프로파일 데이터, 기준 추정 범위 |
| 최댓값·초과 횟수·비율 | 시점별 점수를 context×sensor로 요약 | 집계 창, 임계값, 표본 수, 서로 다른 요약 방식 |

근거는 `scripts/01_eda_training_traces.py` L75–105,
`scripts/02_step_profiles.py` L18–59, `scripts/03_sample_zscores.py` L18–38이다.
같은 정의의 단순 버전 갱신으로 전부 묶지 않는다. 기준·집계 단위가 다른 후보·파생 지표가 함께 존재한다.
journal e19의 주요·보조 구분은 [지표 중심 설계](METRIC-DRIVEN-ANALYSIS.md)의 질문별 역할을 뒷받침한다.

따라서 정의에는 이름·계산식뿐 아니라 **기준 모집단, fit에 사용한 범위, 적용 대상, 통계량의 집계 단위**가 필요하다.
다만 이런 메타데이터를 완성하기 전에는 분석을 못 하게 하는 방향으로 구현하지 않는다.
현재 질문·미정 사항을 이어 가면서 실행에서 관측한 내용과 작성자의 설명을 점진적으로 연결한다.

## 4. 보존할 경험과 개선할 부분

| 채택할 것 | 구체적인 제품 기준 |
|---|---|
| 자유로운 계산·그림 구성 | 임의 Python, 프로젝트 의존성, 사용자 정의 함수, 라이브러리, 다중 패널과 다양한 그림을 유지 |
| 분석에 따른 방법 변경 | EDA → 기준 프로파일 → 보조 점수 → 시각 비교를 모델과 사용자가 선택 가능 |
| 기존 도구의 조합 | 기록을 위한 새 도구를 계속 늘리지 않고 일반 코드 편집·읽기와 함께 동작 |
| 실패 후 이어 가기 | 실패 run과 부분 산출물도 표시하고 모델이 원인을 읽어 수정할 수 있음 |
| 발견·결정의 지속성 | 계산이 끝난 뒤 지표 정의·해석·다음 질문이 CONTEXT와 journal로 이어짐 |
| 사용자 주도 세부 확장 | 전체 센서 요청처럼 범위와 시각화 구성을 자연스럽게 바꿀 수 있음 |

개선은 선택 가능한 방법을 줄이는 대신 다음의 마찰을 줄이는 쪽으로 한다.

- 활성 프로젝트의 경로를 명확히 알려 cwd와 다른 경우의 위치 오류를 줄인다.
- 모델 도구 `lab_note`와 스크립트 API `lab.note`의 차이를 짧은 예와 오류 힌트로 설명하거나 호환성을 개선한다.
- 지표·초점은 기록과 조회에 연결하되 새 계산마다 수동 등록·승인·정해진 단계 통과를 요구하지 않는다.
- 기록 부족은 출처·범위·미확인 상태로 드러내고, 그것만으로 유용한 탐색 결과를 버리지 않는다.

현재 코드에는 이미 일반적인 라이브러리 오류에 대한 `runner.API_HINTS`가 있다.
위 두 위치/API 사례의 구체적 도움말은 현재 소스와 대조해 보완할 후보이며, 이 문서화에서 코드를 수정하지 않았다.

### 기록의 존재와 분석의 타당성을 구별할 사례

다음은 제한된 소스·저장 결과 점검에서 확인한 사항이다. 분석 방법을 고정하기 위한 근거가 아니라,
판단의 강도와 근거의 범위를 정확히 표시해야 하는 이유다.

1. **첨부 표가 있어도 그림 전체의 플롯 데이터는 아닐 수 있다.** 성공 EDA의 histogram 첨부는 센서별 요약 4행이며 bin edges/counts가 아니다.
   마지막 밴드 그림의 첨부 표에는 관측값·프로파일 평균만 있고 밴드 상·하한은 없다. 상·하한은 별도 입력 `timepoint_profile`에 있다.
   차트 자유도를 유지하면서 ‘요약/부분 첨부/플롯 대응’의 범위를 표시하고 필요한 입력·코드로 이어 가야 한다.
2. **시각적 유사성과 수치적 동일성은 다르다.** 마지막 응답의 전 구간 밴드 내 표현과 달리 저장된 값으로는 각 센서의 표시된 트레이스에 밴드 밖 샘플이 1개씩 있다.
   저장된 전체 최대 `|z|`는 약 4.3613이므로 중간 결론의 ‘모두 4.3 이하’도 엄밀한 상한 표현으로는 맞지 않는다.
3. **일반화된 정상 판정은 별도 검증이 필요하다.** 기준을 만든 학습 데이터에 점수를 적용했고 라벨·별도 검증 세트의 성능은 이 세션에서 확인하지 않았다.
   ‘학습 데이터에서 관측한 이탈 패턴’과 ‘완전한 이상 없음’, 실제 FPR·탐지 성능을 구별한다. 센서 단위도 CONTEXT에 추정으로 적혀 있다.
4. **오류 뒤의 파일은 실제로 남을 수 있다.** 실패한 샘플 점수 run도 파생 파일 2개와 차트 레코드 2개를 남겼다.
   이후 성공 run이 같은 경로에 결과를 썼다. 이는 직렬화와 commit·복구의 차이를 보여 주는 후속 검증 사례다.

저장 결과 spot check: 점수 표 320행, 초과 샘플 합 243, 평균 0.759375, 초과가 있는 context×sensor 169개.
성공 run 4개의 주 스크립트 스냅샷은 기록 SHA와 일치했고, 마지막 run의 입력 3개도 현재 파일과 기록 SHA가 일치했다.
이 해시 확인은 결과의 통계적 타당성이나 완전 재현을 증명하지 않는다. 기록된 `rerun_of` 검증은 이 세션에 없었다.

## 5. 토큰 기록을 해석하는 범위

assistant 29개 메시지의 저장된 usage에서 `input_tokens`·`output_tokens`를 각각 한 번씩 합산했다.
동일 값의 alias인 `input`·`output`을 다시 더하지 않았다.

| 항목 | 세션에 기록된 값 |
|---|---:|
| 요청별 입력 누계 | 1,047,365 tokens |
| 출력 누계 | 20,271 tokens |
| `cache_read` 누계(별도 기록) | 769,344 tokens |
| 요청 한 번의 입력 범위 | 6,034–68,394 tokens |

누계는 여러 호출에서 반복 전달된 내용을 포함하며 고유 정보량이나 한 번의 context 크기가 아니다.
provider 청구·캐시 포함 관계를 독립 확인하지 않았으므로 이 값으로 비용 청구액을 계산하지 않는다.
도구 schema·프로젝트 맥락·대화·코드·그림을 따로 계측한 자료도 아니므로 전체 입력을 확장의 맥락 비용으로 돌리지 않는다.

이 기록은 과제 전체 비용과 캐시·정보 회수·성공을 함께 측정할 이유다.
동시에 8K 같은 임의의 작은 문맥을 제품 전체에 강제하는 근거도 아니다.
토큰 목표는 기존 합의대로 성능 측정 기준이며, 유용한 분석·그림·코드를 잘라 목표값에 맞추지 않는다.

## 6. 모델 기준과 자유도

현재 지원 설계의 하단 기준 모델은 사용자가 지정한 **Qwen3.8 27B**다.
정확한 serving model ID, 배포 버전, 양자화, backend, tokenizer, context 설정과 이미지/도구 지원은 실제 검증 시 고정한다.
이 검토에서는 해당 모델을 실행하지 않았고 성능·지원 통과를 확인하지 않았다.
더 작은 모델의 실행을 이름·파라미터 수로 차단하는 정책도 아니다.

지원 평가는 이 기준 모델의 실제 사용 설정과 프론티어 모델을 중심으로 한다.
8K 등의 작은 문맥 시험은 추가적인 열화·복원 진단이며, 기준 모델을 그 크기로 축소해야 지원된다는 뜻이 아니다.
모델이 발전할 때 기준을 재검토하되, 릴리스별 모델·설정을 고정해 이전 결과와 비교한다.
모든 미래 모델의 능력을 보장하지 않으면서도 더 강한 모델이 자신의 방법·코드·도구를 활용할 여지를 유지한다.
