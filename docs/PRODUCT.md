# Aelix Analytics의 비전과 제품 방향

작성: 2026-09-17 · 개정: 2026-09-19 · 제품 비전은 사용자가 명시한 방향이며, 세부 설계·출시 범위는 제안이다.

## 비전과 정체성

**Aelix Analytics는 에이전트 시대에 사람과 에이전트가 검증 가능한 분석과 프로젝트를 함께 이어 가는 새로운 분석 도구·플랫폼을 제시한다. 이 확장은 그 비전을 실현하는 첫 제품 형태다.**

Jupyter Notebook의 코드·서술·탐색과 BI의 시각화·공유를 출발점으로, 목적·질문·지표·데이터·처리·실행·시각화·발견·판단·후속 분석을
하나의 지속 가능한 프로젝트로 연결하는 새로운 분석 패러다임을 지향한다. 모델이나 대화 세션이 바뀌어도 분석의 목적과 근거가 남고,
사람과 에이전트는 직접 분석을 작성·실행하고, 근거를 검토하며 다음 질문을 선택한다. 작성 주체가 바뀌어도 필요한 맥락을 읽어 분석을 이어 간다.

**분석 방향은 목적과 지표를 중심으로 유지한다.** 현재 어떤 지표의 어떤 질문을 풀고 있는지에 따라 다음 작업을 정하고,
이력은 그 방향에서 무엇을 확인하고 판단을 바꿨는지 설명한다. 지표가 모호하면 후보와 미정 사항부터 시작하며,
여러 지표의 병행·정의 수정·새 지표의 파생도 분석 과정으로 보존한다.

검증 가능성은 당시 데이터·코드·환경·판단에 접근하고 검사 범위를 확인할 수 있다는 뜻이다. 결론의 참을 자동 인증한다는 뜻은 아니다.
성공의 단위는 개별 차트나 한 번의 대화에서 끝나지 않고, 검토·수정·재개·재사용할 수 있는 분석 프로젝트까지 이어진다.

이 저장소는 비교 실험용 `aelix-analytics-baseline`에서 출발해 2026-09-18에 `aelix-analytics`로 변경했다.
baseline은 과거 평가의 조건을 설명하는 이름으로만 남으며, 제품을 “경량 분석 확장”으로 정의하지 않는다.
로컬 파일, 프로젝트별 uv 환경, 제한된 문맥과 도구 표면은 이 비전을 효율적으로 실현하기 위한 설계 선택이다.
제품·저장소·배포 이름은 Aelix Analytics / `aelix-analytics`로 통일한다. 공식 명령·도구의 `lab_*`는 `analytics_*`로 전환한다.
분석 인터페이스는 **Workspace**, 시각화 상위 객체는 **Visualization**, 그중 통계 차트는 **Chart**, 문서 산출물은 **Report**로 구분한다.
기본 UI·템플릿·속성은 영어로 제공하고, 목적·발견·보고서 등 작성 내용은 한국어를 포함해 사용자 언어를 보존한다.
코드·상태·데이터·공유까지의 대응은 [용어집](TERMINOLOGY-AND-LANGUAGE.md)을 따른다. 현재 구현의 옛 명칭과 과거 기록은 전환 완료 전까지 사실대로 설명한다.

기존 `../aelix-analytics-engine`에서 개발한 선택 기반 후속 분석은 같은 비전의 후속 역량으로 검토한다.
두 저장소의 현재 계약이 같거나 이미 통합되었다는 뜻은 아니다. 플랫폼 비전과 첫 베타의 검증 가능한 약속은 각각 명시한다.
제품과 저장소의 대표 이름은 **Aelix Analytics**이며, **Aelix Analytics Engine**은 원장·불변 번들·선택·검증·복구를
실험하고 제공하는 엄격한 기반 계층의 이름이다. Engine의 계약을 제품에 도입할 때는 필요한 범위와 비용을 별도로 검증한다.

## 베타 이후의 플랫폼 기반

베타는 첫 번째로 검증할 릴리스 범위다. 제품은 분석의 새로운 표준을 지향하며, 프로젝트와 공개 계약이 특정 모델·호스트·UI보다 오래 지속되게 한다.
초기 구현부터 안정적으로 보존할 의미와 교체 가능한 구현을 나눈다.

지표·근거·버전·관측 범위는 핵심 계약으로 유지하고, 맥락 선택·검색·skill 제안·공유 범위 정책에는 필요한 Strategy 경계를 둔다.
저장소·실행 환경·표시·게시 대상은 포트와 어댑터로 연결한다. 내부 확장점은 모델이 사용할 분석 방법이나 도구 수를 제한·증식시키는 기준이 아니다.
[아키텍처](ARCHITECTURE.md)에 의존 방향·교체 경계·호환성·확장 검증을, [ADR-0001](decisions/0001-evolvable-platform-boundaries.md)에 채택한 결정(2026-10-03)을 기록한다. 채택은 구현 완료가 아니다.

## 사람이 직접 분석하는 사용 경로

**사람은 CLI·Python SDK로 직접 분석하는 동등한 작성자다.** Aelix와 모델은 이 경로의 필수 의존성이 아니다.
프로젝트 생성·데이터 가져오기·SQL 탐색·Python 실행·발견과 판단 기록·보고서 저장·결과 확인을 모델 없이 완료하는 것을 베타의 필수 시나리오로 둔다.
필요한 분석 라이브러리와 실행 환경은 준비하되, 모델 설정·인증·에이전트 대화를 요구하지 않는다. 사용자가 선택한 모델 기반 분석·작성은 별도 경로다.

편집기에서 작성한 코드를 공통 실행 경로로 실행하고, CLI·SDK로 근거와 발견을 남긴다. 사람용 진입점과 에이전트 도구는 같은 기록 계약을 사용한다.
사람 → 에이전트 → 사람의 순차 인계에서도 과거 ID·내용 버전·근거를 보존하고 새 작업은 새 기록으로 연결한다. 작성 주체의 변경을 복제·이관 작업으로 만들지 않는다.
발견·보고서를 사람이 작성하는 경우에도 시스템이 ID·기록 시각·파일 해시를 관리하며, 원장을 직접 편집하거나 긴 메타데이터를 수동 작성하게 하지 않는다.

첫 베타는 스크립트·CLI·SDK와 Workspace의 결과 확인을 대상으로 한다. 노트북의 셀 실행 기록 연동은 명시적인 실행 범위·순서·상태 보존을 정의하는 후속 설계다.
일반 Python·노트북에서 SDK를 호출하는 것만으로 완전한 실행 기록이 생긴다고 안내하지 않는다. 브라우저 분석 편집·실시간 공동 쓰기도 별도 범위다.
상세 흐름은 [직접 분석 설계](DESIGN-CONTINUITY-AND-REUSE.md#사람이-직접-분석하는-경로), 통과 증거는 [Q17](BETA-QUALITY-GATES.md#사람의-직접-분석과-작성-주체-전환-검증)에 둔다.

## 모델의 자유도와 지원 기준

모델이 데이터를 보고 방법·코드·라이브러리·그림을 선택하고, 오류를 고치며 새로운 질문으로 확장할 수 있어야 한다.
기록·지표·메모리 기능은 그 과정을 이해하고 이어 가게 한다. 분석을 미리 정한 지표·알고리즘·chart spec·절차 안에 가두지 않는다.
초기에 정의가 없거나 자유 Python을 썼다는 이유로 분석을 막지 않고, 알려진 내용과 미확인 범위를 점진적으로 기록한다.

현재 사용자가 정한 **지원 기준의 하단 모델은 Qwen3.8 27B**다. 이 모델의 분석 능력을 충분히 활용하고, 더 강한 모델에서도 방법 선택과 표현이 확장될 수 있게 한다.
실제 serving ID·양자화·backend·문맥 설정을 고정해 검증하고, 모델의 발전에 따라 기준을 재검토한다.
이것은 지원 검증의 기준점이며 더 작은 모델의 사용을 차단하는 이름·크기 제한이 아니다.

[실사용 참고 세션](REVIEW-REFERENCE-SESSION-2026-09-18.md)에서는 GLM-5.3-Flash가 EDA → 프로파일 → 지표 비교 → 전체 센서 시각화로
방법을 확장하고 오류를 복구했다. 이 흐름을 보존할 제품 기준으로 삼되 Qwen 실행 증거나 분석 결론의 검증 완료로 간주하지 않는다.

## 사용자가 얻어야 하는 것

1. 새 세션에서 목적, 현재 지표 묶음과 정의, 풀고 있는 질문, 유효한 발견과 다음 행동을 짧게 파악한다.
2. 발견에서 당시 차트·표·실행·코드로 이동하고, 근거가 없거나 보존되지 않았으면 그 한계를 확인한다.
3. 무엇을 언제 알았고, 어떤 근거 때문에 판단을 바꿨는지 따라간다.
4. 원할 때 반복되는 데이터 처리와 분석 방법을 재사용 후보로 남기고, 검사 가능한 코드와 skill로 발전시킨다. 자동 제안 여부와 비용은 사용자가 통제한다.
5. 프로젝트가 커져도 첫 화면과 기본 프롬프트는 필요한 맥락부터 보여 주고, 검색·참조·페이지로 상세를 읽는다. 토큰 수치는 이 흐름의 성능 측정 기준이다.
6. 향후에는 차트에서 선택한 대상을 정확한 데이터 버전에 연결하고, 그 선택을 입력으로 새 질문·분석·발견을 이어 간다.
7. 진행 중인 분석도 팀원에게 독립적인 게시본으로 공유한다. 팀원은 목적·현재 지표·미정 사항·포함된 근거를 보고 같은 분석 방향을 이해한다.
8. 분석 중간에도 자유 형식 보고서와 컬럼별 차트 보고서를 만들고, Reports에서 작성 시점·근거·버전을 찾아 검토·공유한다.
9. 에이전트 없이 직접 분석을 작성·실행·기록하고, 필요할 때 같은 프로젝트를 에이전트와 교대로 이어 간다.

## 혼동하지 않을 주요 기록

| 기록 | 답하는 질문 | 예 | 역할 |
|---|---|---|---|
| 분석 발견 `finding` | 데이터에서 무엇을 알았나? | 특정 기간의 지역별 성장률 차이는 채널 구성과 함께 변한다 | 분석 결론과 근거, 적용 범위 |
| 재사용 제안 `reuse_proposal` — 신설 제안 | 어떤 방법을 다음 분석에서도 쓸 수 있나? | 결측 월을 보완한 뒤 성장률을 계산하는 로직을 모듈화하자 | 절차·라이브러리·skill 후보와 검사 계획 |
| Workflow feedback — 현재 `gap`, 새 `workflow_feedback` 제안 | 분석을 진행하면서 무엇이 막혔나? | 파생 표를 덮어써 과거 값을 열 수 없었다 | 제품 피드백과 개선 근거 |
| 보고서 `report` — 신설 제안 | 그 시점에 무엇을 어떤 목적으로 정리했나? | 중간 경과 요약, 센서별 차트 검토 문서 | 자유 형식 본문·첨부·인용 근거의 버전 보존 |

기존 gap을 일괄적으로 인사이트나 skill 후보로 바꾸지 않는다. 필요하면 새 제안이 원래 gap·실행·발견을 참조한다.
이 기록들은 관련 지표와 분석 초점에 연결한다. 지표 정의는 무엇을 측정하는지, 발견은 그 측정과 탐색으로 무엇을 알았는지를 남긴다.
실행 성공, 기록 충실도, 재실행 일치, 분석 방법 검사, 결론 검토는 서로 다른 상태다.
도구 호출 수나 재사용 횟수가 많다는 이유만으로 분석의 정확성 또는 개선 효과를 인정하지 않는다.
보고서는 발견·지표·차트 등을 선택해 정리하는 산출물이다. 본문 전체를 검증된 발견이나 현재 메모리로 자동 승격하지 않는다.
프로젝트 전체를 탐색하는 Workspace(현재 `report/`, 전환 목표 `workspace/`)와 개별 Report의 보존 파일, 그 보고서를 포함한 Publication은 수명과 버전을 구별한다.

## 개선을 판단하는 기준

| 기준 | 기존보다 좋아져야 하는 점 | 퇴보로 보는 변화 |
|---|---|---|
| 분석 방향 | 목적·지표·현재 질문과 다음 작업의 관계를 설명하고 새 세션에서도 유지 | 차트·로그는 늘지만 어떤 지표를 왜 분석하는지 흐려짐 |
| 분석 표현과 자율성 | 적절한 새 계산·라이브러리·그림·후속 경로를 모델과 사람이 선택 | 기록을 위해 정형 절차·사전 등록·허용된 방법만 강제 |
| 분석의 연속성 | 새 세션에서 이전 정의·발견·열린 질문을 근거와 함께 복원 | 과거 기록이 있어도 최근 몇 건만 알아볼 수 있음 |
| 근거의 정확성 | 당시 버전과 현재 버전을 구별하고 미확인을 드러냄 | 최신 차트를 과거 발견의 근거처럼 연결 |
| 사람의 이해 | 발견 → 근거 → 방법 → 원래 위치의 이동이 자연스러움 | 탭마다 같은 대상을 다시 찾거나 전체 그래프를 해석해야 함 |
| 사람의 직접 분석 | CLI·SDK로 모델 없이 분석·발견·보고서를 작성하고 같은 근거로 인계 | 핵심 작업에 에이전트 세션을 요구하거나 수동 작업의 기록을 빠뜨림 |
| 중간 산출물 | 자유 형식 보고서·반복 차트 묶음에서 당시 내용·근거·변경 이유 확인 | 새 분석이나 화면 재생성이 과거 보고서를 덮어쓰거나 매번 모델을 호출 |
| 공유와 팀 검토 | 특정 시점의 분석 방향·정의·근거를 다른 환경에서도 읽고 검토 | 작업 폴더 경로가 깨지거나 게시본과 최신 분석이 섞여 판단이 달라짐 |
| 에이전트의 비용 | 필요한 정보의 회수율을 유지하면서 전체 입력·출력 토큰을 줄임 | 짧은 응답 대신 수십 번의 재조회가 필요하거나 원문을 숨김 |
| 운영·인지 비용 | 분석에 필요한 자원과 명령만 사용하고 선택 기능의 비용을 분리 | 기능을 쓰지 않는 사용자도 서버·모델 호출·설명 목록 비용을 부담 |
| 분석가의 집중 | 재사용 제안의 방식·빈도·비용을 선택하고 분석을 우선 | 매 턴 skill을 권하거나 제안을 끄면 발견·맥락 기록도 멈춤 |
| 도구 표면의 절제 | 기존 명령과 제한 조회로 기능을 확장하고 실제 선택 오류를 줄임 | 기능·skill·그래프 노드마다 새 도구를 상시 노출 |
| 재사용의 신뢰성 | 적용 조건·코드 버전·검사 결과가 있는 방법을 축적 | 한 번 성공한 코드를 검토 없이 전역 skill로 등록 |
| 기록의 수명 | 구버전 프로젝트를 읽고 명시적으로 전환하며 원본을 보존 | 업그레이드 후 과거 기록을 조용히 버리거나 덮어씀 |
| 장기 확장성 | 새 정책·backend·화면을 핵심 의미와 기존 분석 코드의 보존 아래 추가 | 기능 하나를 위해 host·원본 형식·UI·분석 코드를 모두 수정해야 함 |
| 용어와 언어 | 사람·코드·도구가 같은 개념과 상태를 표현하고 영어 UI에서 다국어 분석을 유지 | 동일 대상을 lab/analysis/analytics 등으로 혼용하거나 사용자 내용을 자동 번역 |
| 규모와 실패 처리 | 비용·누락·중단 상태를 드러내고 복구 경계를 좁혀 나감 | 부분 성공을 완료로 표시하거나 임의 Python의 부작용까지 복구한다고 약속 |

새 기능은 이 중 개선하려는 항목과 영향을 받는 나머지 항목을 PR에 적는다.
기능 개수, 그래프 노드 수, 자동 생성 skill 수를 제품의 성공 지표로 삼지 않는다.

## 설계 경계

- 프로젝트의 정본은 `CONTEXT.md`, journal, run·데이터 기록과 보존된 파일이다. 보고서의 저장 본문·첨부도 형식에 관계없이 정본에 속한다. 프로젝트 탐색 HTML·검색·관계 인덱스는 재생성 가능한 읽기 모델이다.
- 사람과 에이전트는 같은 식별자·버전·관계·누락 상태를 본다. 화면과 프롬프트에 서로 다른 진실을 만들지 않는다.
- 핵심 작성·실행·기록 경로는 모델 없이 동작한다. 작성 주체와 실행 수단을 구별하고, 에이전트 세션 참조가 없어도 유효한 프로젝트 기록으로 다룬다.
- Visualization은 차트·지도·다이어그램·시각화된 표로 확장할 상위 객체다. 데이터셋·Workspace의 관계 그래프·Report와 역할을 구별하며 새 유형마다 도구를 추가하지 않는다.
- 에이전트의 개인적 사용자 메모리와 프로젝트의 분석 지식을 분리한다. 이 확장은 프로젝트 지식을 관리한다.
- 기본 조회·프로젝트 화면 렌더·저장한 보고서의 표시·공유 빌드는 모델 호출 없이 동작한다. 보고서 본문·요약·재사용 제안의 작성은 별도로 요청하거나 분석 과제에 포함해 수행하고 비용을 측정한다.
- skill 제안은 `on_demand`를 기본값으로, `always_on`을 선택 옵션으로 제안한다. 상시 모드도 근거·임계값·중복·빈도 조건을 통과해야 알린다. 비용은 별도로 측정하며 [제안 정책](SKILL-PROPOSAL-POLICY.md)을 따른다.
- 토큰·문자 수 목표는 강제 제한이 아닌 성능 측정 기준이다. 목표 초과만으로 분석·조회·제안을 중단하거나 필요한 정보를 버리지 않는다.
- 토큰 절감과 적은 도구 수는 분석 표현력을 줄이는 목적이 아니다. 도구 표면을 절제하면서 자유 코드와 필요한 기능에 접근할 수 있게 한다.
- skill 제안을 꺼도 분석 발견과 맥락 기록은 계속된다. 등록된 skill의 사용 정책과 새 skill의 제안 정책은 별개다.
- 기능 확장이 상시 도구 수 증가를 뜻하지 않게 한다. 기존 읽기·쓰기·실행 경계를 우선하고, 추가 도구는 더 작은 표면보다 나은 검증 결과가 있을 때 검토한다.
- 계산 로직은 Python 모듈·패키지로 검사하고, skill은 적용 시점·사용 절차·해석·검사·실패 조건을 설명한다. 필요한 작은 실행 스크립트는 skill에 포함할 수 있다.
- 공유는 작업 리포트의 render, 독립 패키지의 build, 선택한 위치로의 publish를 구별한다. 진행 중이라는 상태와 게시 시점·근거 버전을 유지한다.
- 보고서는 분석 완료·지표 확정 없이 작성할 수 있다. 본문 형식을 강제하지 않고 작성 시점·분석 기준·내용 버전·게시 이력을 구별한다. 상세는 [보고서 산출물 설계](REPORT-ARTIFACTS.md)를 따른다.
- 첫 베타는 단일 로컬 프로젝트의 분석과 게시본의 읽기 공유를 대상으로 한다. 실시간 공동 쓰기, 개인 메모리의 사용자 간 동기화, 임의 코드의 완전한 계보·트랜잭션·정확히 한 번 실행은 약속하지 않는다.

## 첫 베타에 담을 범위

독립된 분석 제품으로서의 설명과 설치, **분석 발견·재사용 제안 중심의 인사이트 화면**, 버전을 구별하는 관계 탐색,
**지표·현재 질문을 중심으로 분석 방향을 유지하는 맥락**, 변경 이력을 보존하는 조회, 프롬프트·응답 비용과 분석 품질의 측정·개선을 우선한다.
라이브러리와 skill은 제안·검사·등록 경로를 제공하며, 무인 자동 등록과 전역 배포는 첫 베타의 약속에 넣지 않는다.
**Reports 탭과 자유 형식 보고서의 버전 보존**, 여러 컬럼의 차트 보고서·묶음, 당시 근거로의 이동을 포함한다.
이 범위는 사람이 직접 수행하는 CLI·SDK 경로와 작성 주체 간 인계까지 Q17로 검증한다.
모든 문서 변환기·편집기·예약 생성은 전제하지 않으며, 기본 보기와 파일 보존·다운로드의 지원 범위를 명시한다.
팀 공유는 독립 HTML 폴더·ZIP 빌드와 지원 대상을 명시한 첫 publish 경로부터 시작한다.
모든 호스팅 provider나 공동 편집 서버를 먼저 구현할 필요는 없다. [공유 설계](PUBLISH-AND-SHARING.md)에 범위와 도입 순서를 둔다.

재실행·복구·멱등성은 중요한 후속 우선순위다. 베타에서는 현재 한계를 명시하고 중단·중복·부분 기록을 숨기지 않는 것부터 검증한다.
정확한 순서와 출시 보류 조건은 [베타 품질 기준](BETA-QUALITY-GATES.md)에 있다.
