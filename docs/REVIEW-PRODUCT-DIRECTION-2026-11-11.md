# 첫 베타 이후 제품 방향 검토

작성: 2026-11-11 · 상태: 검토·제안 문서. 채택된 결정이 아니다. · 작업: [#186](https://github.com/handochan/aelix-analytics/issues/186)
기준: 코드는 main `f581e52`(kit 0.32.1), 측정은 [#24 제품 효과 평가의 측정 기록](verification/2026-11-04-issue-24-product-eval.md)(E4, 2026-11-04, kit 0.32.0)

## 1. 이 문서의 위치

이 문서는 첫 베타를 써 본 소유자의 관찰과 E4 측정, 현재 코드를 맞춰 보고 제품의 정체성과 다음 방향을 검토한다.
[제품 방향](PRODUCT.md)의 정체성·방향과 [현재 계약](CONTRACTS.md)을 바꾸지 않는다(PRODUCT.md의 문서 표에 이 문서의 링크만 더한다). 방향의 채택은 소유자 결정이고, 채택하면 PRODUCT.md를 따로 개정한다.
개선 후보는 제안이며, Issue로 등록한 것도 범위·방식은 그 Issue에서 정한다.
첫 베타는 예정대로 출시한다(소유자, 2026-11-11, #186). 첫 출시 번호는 [#24의 2026-11-09 결정](https://github.com/handochan/aelix-analytics/issues/24#issuecomment-6742451632)대로 0.32.1이다.

각 절은 다음을 구별한다.
- **관찰**: 소유자가 사용하며 본 것(2절).
- **확인한 사실**: 측정 기록의 값과 기준 commit의 코드(3절). 재지 않은 일반화는 관찰이나 추정으로 적는다.
- **평가와 제안**: 이 문서의 판단(4–9절). 측정하지 않은 효과는 추정으로 적는다.

## 2. 계기: 소유자의 사용 경험(2026-11-11)

- 가볍고, BI 설치나 Jupyter Notebook 없이도 분석 프로젝트가 이어지고 검증 가능한 agentic 분석 Workspace로 동작한다.
  기존 환경에 그대로 들어오고, 이 확장을 위해 기존 skill을 고치지 않아도 된다.
- 분석이 확장으로 강제되지 않는다. 기존 분석·보고서 skill을 쓰면 bash 등으로 우회해 분석하는 경우가 많고, 그래서 모든 것이 추적되지는 않는다.
- 보고서 등에 로컬 경로 같은 참조가 들어가 공유 build가 `leak_found`로 멈추는 경우가 많다. 그래서 분석을 공유할 수 없는 경우가 많다.
- Overview의 최근 분석 흐름이 사람에게 친화적이지 않고, 연관된 관계가 한눈에 들어오지 않는다.
- 비정형 데이터 분석은 아직 검증하지 않았다.
- 이 프로젝트는 에이전트 시대의 새로운 분석 인터페이스라는 비전의 PoC로 시작했다. 가벼운 방식의 자유도·접근 편의와, 제품화로 의존성은 높지만
  편의·기능을 강화하는 방식 사이에 trade-off가 있다.

### 3.2 run의 입력 기록과 kit 밖 실행

- run의 입력은 세 경로로 기록된다(`src/aelix_analytics/runner.py`, `capture.py`).
  - 런타임 hook: Polars·DuckDB와 SDK 읽기. 계산한 경로도 실제로 읽은 파일로 기록한다.
  - 코드의 문자열 리터럴 정적 검색: 표 형식 확장자(`core.DATA_SUFFIXES`: parquet·csv·tsv·json·ndjson·jsonl·arrow·feather·ipc·xlsx)의 파일만 받고, glob 리터럴은 펼친다. 내용은 run 시작 때의 것이다.
  - 호출자의 선언(`analytics run --input`): 형식을 가리지 않는다.
- 그래서 hook이 없는 읽기(pandas·`open()`·PIL·PDF 라이브러리 등)는 정적 검색이나 선언에 기댄다. 선언하지 않으면, 코드에 리터럴로 없는 경로(실행 중에 조합한 경로, 변수·`os.listdir` 결과로 만든 경로)와 비표 형식(PDF·이미지·텍스트·문서)의 hook 없는 읽기는 입력으로 남지 않는다.
- 가져오기(`analytics import`)는 parquet·csv·tsv·txt(csv로 읽음)·json·ndjson·jsonl만 받는다(`data.py`의 `IMPORT_FORMATS`).
- kit 밖에서 bash로 돈 Python은 #170이 결과 끝에 안내를 붙이고, #171이 관찰된 활동(`observed_activity`)으로 명령 글·앞뒤 파일 상태·명령이 가리킨 스크립트의 바이트를 남긴다([ADR-0015](decisions/0015-observed-activity-outside-the-kit.md)).
  관찰은 run이 아니어서 입력·환경을 남기지 않고, aelix의 `bash` 도구만 대상이다. 사람의 `!` 명령, write·edit 도구의 직접 쓰기, 다른 확장·MCP 도구, aelix 밖 호스트는 관찰하지 않는다.

### 3.3 공유 build의 누출 검사

- build는 금지 토큰의 후보를 모은다(`publishing/build.py`의 `_environment`, `publishing/scope.py`).
  - 환경 값: 프로젝트 루트와 그 실제 경로, 홈 디렉터리와 `~/` 형태, 임시 디렉터리, 호스트 이름, `VIRTUAL_ENV`, `sys.executable` 등.
  - 포함 범위 밖 항목: run·Visualization·CONTEXT·Report ID, 이름·경로·버전 같은 필드의 값, 24자 이상의 글 줄.
- 후보 가운데 8자 이상인 값은 부분 문자열로 찾는 강한 토큰이 되고, 범위 밖 기록의 글 줄은 줄 단위로 찾는다. 8자 미만의 값은 빠지고(`/tmp`, 짧은 호스트 이름 등),
  범위 밖 항목의 짧은 이름·ID는 이름 자리에서만 찾는 약한 토큰이다. 포함한 필드와 같은 값은 빠진다(`scope.py`의 `add`).
- 강한 토큰이나 범위 밖 글 줄이 본문·첨부·차트·사본 코드·Parquet 문자열에 나오면 build 전체가 `leak_found`로 멈춘다(`publishing/checks.py`의 `check_strings`).
  예외는 포함한 run의 사본 코드에 있는 그 스크립트의 시각화 이름과, 포함한 ID 안에만 나오는 범위 밖 ID다.
- 오류는 파일·위치·원본 항목을 알려 주지만 사용자 바이트를 가리거나 고치지 않는다(계약 D2). 사용자가 고친 새 Report 버전을 저장해 고르거나(D4),
  인용한 run을 `based_on`으로 범위에 넣거나, `--scope project --report …`로 범위를 넓힌다.
- 보고서를 저장하는 시점의 사전 검사나, 고친 버전을 만들어 주는 기능은 없다.
- (관찰·추정) 에이전트가 쓴 보고서에는 이미지·링크의 절대 경로, 입력 파일 경로, run ID가 들어가기 쉽다. 멈추는 것은 절대 경로가 환경 값(프로젝트 루트·홈 등)을 담을 때,
  run ID·경로는 그 대상이 범위 밖일 때다. 2절의 관찰과 맞지만 실제 보고서의 통과율은 재지 않았다.

### 3.4 Overview

[설계 7.1](design/WORKSPACE-READABILITY.md)과 `workspace.py`의 `overview_section`이다.
- 머리(제목·목표·수의 두 줄), 현재 분석 방향(CONTEXT.md의 고정 섹션, 분석 초점·지표), 분석 상태 칸, 분석 지도 요약.

- 세션의 상태를 묶은 checkpoint 기록(`analysis_checkpoint/1`: 지표·발견·변경·질문·할 일, [#16](https://github.com/handochan/aelix-analytics/issues/16))은

### 4.2 정체성(제안)

"에이전트 시대의 새 분석 패러다임·플랫폼"으로 보면 지금 제품은 아직 그 자리에 있지 않다. 사용자가 보는 인터페이스는 에이전트 대화와 파일이고,
이 제품은 그 아래에 있다. 분석 인터페이스는 모델 회사·에이전트 호스트·데이터 플랫폼이 모두 만들고 있는 자리이기도 하다.

반대로 **증거 계층**으로 보면 이미 차별적이고 측정과도 맞는다. 에이전트 시대에는 분석을 만드는 비용이 낮아지고 병목이 검토로 옮겨 간다(추정).
상위 모델은 대화를 이어 가는 노트는 스스로 남겼다(3.1). 반면 V에는 실행된 코드 바이트와 입력 해시를 남기는 장치가 없고, E4에서 V는 C2 세션 3에서
근거 파일을 대지 못했다(근거 연결 V 0.88). V가 남긴 근거의 바이트 단위 보존율은 따로 재지 않았다.

제안하는 정체성은 다음과 같다.

> **에이전트가 만든 분석을 사람이 믿고, 검토하고, 공유할 수 있게 하는 증거 계층.**

- 비전의 "새로운 분석 인터페이스"는 여기서 **검토 인터페이스**로 이어진다. 새 노트북·BI를 만드는 것이 아니라, 대화로 만든 분석을 근거로 검토하는 화면이다.
- [PRODUCT.md](PRODUCT.md)는 사람을 CLI·SDK로 직접 분석하는 동등한 작성자로 둔다. 이 제안은 그 원칙을 바꾸지 않는다. 사람이 쓴 분석에도 같은 증거 계층이 적용되고,
  성장의 중심 시나리오를 에이전트가 만든 분석으로 보는 것이다(D1).

## 5. 교훈

1. **에이전트는 범용 도구를 쓴다.** 전용 도구는 매번 선택받아야 한다. 강제하거나 권유하기보다 관찰하는 쪽이 맞다. #170·#171이 그 방향이고, 한 단계 더 내려갈 수 있다(7.3).
2. **연속성은 강한 모델이 상당 부분 흡수하고, 근거는 흡수하지 못했다**(E4 기준). 투자의 중심을 근거로 옮긴다. 이 가설은 O2로 확인한다(8.1).
3. **고치는 일을 돕지 않는 안전장치는 기능을 쓰기 어렵게 만든다.** 막는 기준은 유지하되 사전 검사와 고치는 도움을 함께 준다(7.1).
4. **사람은 기록 목록이 아니라 흐름을 읽는다.** 어떤 표현이 맞는지는 여러 방식을 비교해 정한다(7.2).
5. **엄밀함은 오래 남을 것에 쓴다.** 기록 형식·근거 계약은 지금의 엄밀함을 유지하고, 화면·연동·공유 경험은 빠른 실험으로 다룬다(9절).

## 6. 방향의 선택지

| | A. 지금 형태(로컬 확장) 유지 | B. 범용 에이전트 분석 제품 | C. 가벼운 코어 + 선택형 레이어(권장) |
|---|---|---|---|
| 사용자 의존성 | 낮음 | 높음 | 사용자가 단계별로 선택 |
| 기록 완결성 | 부분적 | 높음(자체 런타임) | 실행 환경 수준의 기록으로 높임(7.3) |
| 경쟁 | 적음 | Hex, Databricks Genie, Snowflake Intelligence, Julius, Claude·ChatGPT의 자체 분석 기능 등과 정면 경쟁 | 틈새와 그 위의 서비스 |
| 기존 환경에 들어가는 장점 | 유지 | 버림 | 유지 |

- A는 제품의 정의가 아니라 배포·연동의 형태를 말한다. PRODUCT.md는 제품을 "경량 분석 확장"으로 정의하지 않는다.
- 가벼움과 제품화는 양자택일이 아니라 층으로 나눌 수 있다. 경계는 이미 단단히 만든 기록 형식(`analytics.event/2`, run 기록)이다.
  코어는 로컬 파일 기반으로 강제 없이 두고, 무거운 편의 기능은 같은 파일을 읽는 선택형 레이어로 얹는다(Git과 GitHub, OpenTelemetry와 관측 백엔드, dbt Core와 dbt Cloud의 관계).
- B를 새로 만드는 것은 권하지 않는다. 작은 팀의 무기는 폭이 아니라 좁고 날카로운 강점인데 B는 폭으로 겨루는 시장이고, 2절의 장점(기존 환경에 그대로 들어감)도 버린다.
- 제품 수준으로 키운다면 강점 위에서 키운다. 그 한 모습이 7.6의 검토·공유 서비스다.
- 어느 선택지를 채택할지는 소유자 결정이다(10절).

## 7. 개선 후보

Issue로 등록한 것은 그 Issue가 범위와 방식을 정한다. 우선순위는 소유자가 정한 것만 적는다.

### 7.1 공유 build가 멈출 때 고치는 일을 돕기 — [#187](https://github.com/handochan/aelix-analytics/issues/187)

환경 값과 제외한 내용이 게시본에 남지 않는다는 보장은 유지한다. 막혔을 때 고치는 일을 돕는 방식을 정한다. 먼저 실제 보고서로 통과율과 막힌 사유의 분포를 잰다.
후보(예시):
- 보고서를 저장할 때 공유 가능 여부를 검사해 도구 결과로 알림. 에이전트는 쓴 직후에 고칠 때 비용이 가장 적다(추정).
- 환경 값을 이식 가능한 표기(`<project>/…`)로 바꾼 새 Report 버전을 제안·생성. 원본 버전을 그대로 두므로 "사용자 바이트를 고치지 않는다"(D2)와
  원본을 정규화하지 않는다는 [ADR-0013](decisions/0013-report-storage-and-collections.md)과 충돌하지 않을 수 있다. kit이 새 버전을 만들지, 제안만 할지는 #187에서 정한다.
- 범위 밖 참조마다 "범위에 포함"과 "자리표시자로 대체" 중 선택.
- 본문이 경로 대신 기호 참조(`run:…`, `chart:…`, `e41`)를 쓰고, 렌더러가 로컬 Workspace와 게시본에서 각각 해석.
- 독자별 검사 강도(팀 내부 / 외부 공개). 보장의 범위를 바꾸므로 소유자 결정이다.

### 7.2 Overview에서 최근 분석 흐름과 관계를 읽는 방식 — [#188](https://github.com/handochan/aelix-analytics/issues/188)

방식은 정하지 않았다. 여러 후보를 시안으로 비교한 뒤 소유자가 고른다(소유자, 2026-11-11).
후보의 예: 세션·checkpoint 단위의 장과 그 차이, 분석 초점·질문 중심의 흐름, 발견 중심의 근거 카드, 관계 그래프의 최근 부분,
"지난번 이후 바뀐 것" 요약, 시간 × 종류의 타임라인, 에이전트가 쓴 세션 요약 기록, 다른 도구의 사례.
비교 기준은 사람이 흐름·판단·근거를 파악하는 시간과 정확도, 모델 호출 없이 만들 수 있는지, 규모, 기록이 성긴 프로젝트에서의 품질, 상태를 합치지 않기,
기존 탭과의 중복, 좁은 화면이다. 자세한 것은 #188에 있다.

### 7.3 기록 지점을 도구 호출에서 실행 환경으로 — [#191](https://github.com/handochan/aelix-analytics/issues/191)(P0, 소유자 2026-11-11)

- **ADR-0015와의 관계**: [ADR-0015](decisions/0015-observed-activity-outside-the-kit.md)는 입력 캡처(OS 추적, `sitecustomize`·`PYTHONPATH` 주입)를
  "플랫폼 포트 밖의 OS별 기능이거나 사용자의 프로그램 동작을 바꾼다"는 이유로 기각했고, 관찰을 run으로 합성하는 안도 run이 실행한 바이트·입력·환경·재실행을
  약속한다(C2)는 이유로 기각했다(대안과 선택 이유). 아래는 소유자의 사용 경험을 근거로 **그 기각을 다시 검토하는 후보**다. 다시 채택하려면 그 이유에 답하고 ADR을 새로 정해야 한다.
- 프로젝트 venv의 `.pth`·`sitecustomize`, 또는 확장이 bash 도구 환경에 넣은 `PYTHONPATH`로 기록 부트스트랩을 올려, bash·skill 스크립트에서 돈 Python도 근거를 남긴다.
  OpenTelemetry의 Python 자동 계측이 같은 방식을 쓰고, noWorkflow·ReproZip이 분석 재현 쪽의 선행 사례다.
  노트북 커널까지 넓히는 것은 PRODUCT.md가 후속 설계로 둔 노트북 실행 기록 연동과 닿는다.
- `sys.addaudithook`의 `open` 이벤트로 pandas·`open()`·PIL·PDF 라이브러리의 읽기·쓰기를 잡는다. 3.2의 hook 없는 읽기 문제도 함께 다룬다.
  Polars·DuckDB처럼 네이티브 코드로 읽는 라이브러리는 지금의 hook을 유지한다.
- run과 관찰의 보장 차이는 유지한다. 관찰된 실행이 run의 보장(C2)을 갖추지 않는 한 run으로 세지 않는다.
- 지표 후보: **근거가 남은 실행의 비율**(가칭. Workspace의 기존 `Record coverage`·기록 범위와 다른 지표다). 먼저 지금의 값을 잰다(8.2).
- 위험: 다른 Python 버전과 `-I`·`-S` 실행, 분석이 아닌 Python(pip 등)의 걸러 내기, 성능, 의도하지 않은 기록, 끄는 방법. 새 기록 종류가 필요하면 기록 형식 PR의 리뷰 예산을 따른다.
- bash의 `python` 호출을 `analytics run`으로 자동으로 바꾸는 방법도 있지만, skill의 인자·작업 디렉터리·환경을 깨뜨릴 위험이 커서 관찰 쪽을 권한다.

### 7.4 호스트 중립 배포 — [#192](https://github.com/handochan/aelix-analytics/issues/192)(P0, 소유자 2026-11-11)

Claude Code·Codex 같은 다른 호스트에서도 hooks·MCP 서버·skill 등으로 같은 기록 계약을 제공한다. [아키텍처](ARCHITECTURE.md)는 호스트 어댑터를 별도 층(`host_adapter`)으로 두었다.
aelix 사용자로 한정된 도달 범위를 넓히는 가장 싼 방법으로 본다(추정). 호스트별 확장 지점과 첫 대상은 #192에서 조사해 정한다.

### 7.5 비정형 데이터와 LLM이 낀 분석의 근거 — [#193](https://github.com/handochan/aelix-analytics/issues/193)(P0, 소유자 2026-11-11)

- 에이전트 시대 분석이 커지는 영역은 텍스트·문서·이미지를 LLM으로 분류·추출·요약하는 일, 즉 LLM을 분석 연산자로 쓰는 경우다(추정).
- LLM 호출을 한 단계로 기록하고(모델 ID, 프롬프트, 파라미터, 표본, 출력, 비용), 다시 돌렸을 때의 일치율을 검증 신호로 삼으면 기존의 재실행 비교가 확장된다.
- 먼저 실제에 가까운 과제 2–3개로 지금 제품이 어디서 끊기는지 본다(8.5).

### 7.6 선택형 검토·공유 서비스: "분석 PR"(장기 후보, Issue 미등록)

- 에이전트가 한 세션에서 만든 변화(새 발견, 정정, 지표 정의 변경, 보고서)를 코드 PR처럼 하나의 변경 묶음으로 본다.
  사람은 주장마다 근거와 지난 검토 이후의 차이를 보며 승인·반려·질문하고, 승인된 것만 게시본과 팀 지식이 된다.
- 지금 전용 기록이 없는 '결론 검토' 상태가 여기서 사람의 손으로 남는다. 공유와 흐름 읽기가 한 흐름이 된다.
- 수익화가 가능한 층은 여기라고 본다(추정). 팀이 이런 검토를 원하는지부터 검증해야 한다.

## 9. 개발 방식에 대한 제안

- **두 속도로 운영한다.** 기록 형식·근거 계약처럼 오래 남는 것은 지금의 ADR·[리뷰 예산](PROJECT-OPERATIONS.md#리뷰-예산)을 유지한다.
  화면·연동·공유 경험은 시안과 사용자 확인으로 빠르게 돌리고, 계약 문서는 채택한 뒤에 쓴다.
- **첫 화면의 문서를 가볍게 한다.** README의 첫 화면은 계약 세부보다 "5분 안에 가치 보기"와 알려진 한계(우회, 공유, 비정형 데이터)를 앞세운다.
- 지금의 엄밀함은 품질 문제가 아니라 학습 속도 문제를 만든다고 본다.
- **바뀌는 기존 규칙**: 이 제안을 적용하면 [리뷰 예산](PROJECT-OPERATIONS.md#리뷰-예산)(문서만 바꾸는 PR을 포함한 모든 일반 PR에 독립 1회·Codex 1회)과
  [기여 가이드](../CONTRIBUTING.md)의 "구현으로 채택된 구조적 결정은 ADR에 남기고 현재 계약을 함께 갱신"이 시안 단계에서 달라진다.
  main에 들어간 동작은 지금처럼 현재 계약에 적는 것을 전제로 한다. 소유자가 정해(2026-11-11, D7) [PROJECT-OPERATIONS.md의 두 속도](PROJECT-OPERATIONS.md#두-속도-계약-경로와-실험-경로)에 반영했다([#194](https://github.com/handochan/aelix-analytics/issues/194)). README 첫 화면의 재구성은 반영하지 않았다(배포본이라 릴리스 후보에 영향, 후속 Issue 미등록).
