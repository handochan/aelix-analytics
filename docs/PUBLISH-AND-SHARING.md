# 진행 중인 분석의 빌드·공유·게시

작성: 2026-09-18 · 상태: 설계 제안. `build`·`publish`는 현재 구현된 명령이 아니다.
여기서 publish는 **분석 프로젝트의 결과와 맥락을 팀원에게 공유하는 기능**이다. 확장 패키지 자체의 배포와 구별한다.
새 명칭은 [용어집](TERMINOLOGY-AND-LANGUAGE.md)을 따른다. Workspace는 분석 인터페이스, Visualization은 표현 객체, Report는 문서 산출물이다.

## 1. 팀원이 같은 분석 방향과 근거를 볼 수 있게 한다

분석이 끝나기 전에도 목적·현재 지표·질문·발견·근거·미정 사항·다음 확인을 공유할 수 있어야 한다.
팀원은 Aelix나 Python 환경 없이 브라우저에서 이를 읽고, 포함된 근거와 관련 요소 사이를 이동한다.
게시하는 시점에 분석이 완료되거나 결론이 승인되어 있을 필요는 없다. 진행 중이라는 상태와 근거 범위를 정확히 표시한다.
공유 범위에는 [자유 형식 보고서](REPORT-ARTIFACTS.md)의 특정 버전도 포함한다. 중간 보고서 하나, 컬럼별 보고서 묶음, 프로젝트 전체 읽기 화면 중 필요한 범위를 고른다.

흐름은 **로컬 분석 → 공유 범위 선택 → 게시본 미리보기 → 고정된 빌드 → 선택한 위치에 게시**다.
게시본을 만드는 동안 원래 분석을 계속할 수 있고, 실패한 공유 작업 때문에 분석을 다시 실행하지 않는다.

| 단계 | 하는 일 | 상태 |
|---|---|---|
| 목표 `analytics render` / 현재 `lab report` | 작업 프로젝트의 기록으로 Workspace HTML을 갱신 | 갱신 역할은 현재 구현. 명칭 전환은 제안이며 작업 폴더의 파일을 참조 |
| `build` | 특정 기록 기준과 공유 범위로 독립적인 HTML 패키지를 생성 | 제안. 폴더 또는 ZIP으로 전달 가능 |
| `publish` | 생성된 패키지를 지정한 공유 위치에 게시하고 주소·게시 기록을 남김 | 제안. 빌드와 전달을 분리 |

보고서 본문의 작성·버전 저장은 위 단계에 앞선 별도 작업이다. render·build·publish가 보고서를 다시 집필하거나 분석 코드를 재실행하지 않는다.
사람 명령의 개념 예시는 `analytics build --profile read`, `analytics publish --build pub_example --target team`이다.
최종 문법은 구현 PR에서 정한다. `/analytics` 명령·CLI를 우선 활용하고 상시 `analytics_publish` 모델 도구를 추가하는 것을 기본값으로 삼지 않는다.
에이전트도 사용자의 명시적인 게시 요청 또는 설정된 자동 게시 정책에 따라 같은 경로를 사용한다.

## 2. 현재 HTML과의 차이

현재 [report.py](../kit/labkit/report.py)의 `Site.file_link()`는 차트·첨부 표 등에 대해 `report/` 밖의 경로를 만든다.
CSS·JS는 report assets에 들어가지만 차트·원본·파생 표 등을 모두 독립 패키지로 복사하지 않는다.
[report.js](../kit/labkit/assets/report.js)의 새로고침은 생성된 `assets/build.js`의 변화를 감지하는 동작이다.
그 자체가 다른 컴퓨터로 파일을 전송하거나 팀원의 접근 권한을 관리하는 기능은 아니다.

2026-09-18에 [참고 프로젝트](REVIEW-REFERENCE-SESSION-2026-09-18.md)의 생성 HTML 14개를 읽어 확인했다.
report 밖을 가리키는 이미지 참조가 28회, 고유 이미지 파일은 15개였다. 링크까지 합친 report 밖의 고유 대상은 35개였다.
이 숫자는 읽기 전용 경로 점검이며 복사·게시·브라우저 E2E를 수행한 결과가 아니다.
따라서 현재의 `report/`만 복사하는 것을 완성된 공유 기능으로 안내하지 않는다.

현재 페이지에는 데이터 미리보기, 코드, 로그, 로컬 경로·세션 정보도 들어갈 수 있다.
공유본은 로컬 보고서를 통째로 복사한 다음 탭을 숨기는 방식이 아니라, 선택한 내용으로 별도의 읽기 모델을 생성한다.
기존 Analytics의 `frozen_payload`·기록 기준 고정 개념은 참고하되, 그 프로토타입의 합성 데이터 전용 export 제한을 이 제품의 공유 정책으로 그대로 가져오지 않는다.

## 3. 특정 시점의 게시본과 갱신되는 주소

**게시본은 특정 시점의 분석 스냅샷**이다. 원본 프로젝트가 계속 바뀌어도 이미 게시한 버전은 바뀌지 않는다.

- 버전 주소: 예를 들어 `.../publications/<id>/`로 그 시점의 결과를 가리킨다.
- 최신 주소: 예를 들어 `.../projects/<channel>/`은 마지막으로 성공한 게시본을 가리킨다.
- 작성 시점·기록 기준·분석 상태·게시 시점·이전 버전으로의 링크를 표시한다.
- 로컬 분석의 현재 상태와 게시본의 상태를 구별하고, 새 게시본이 있으면 독자가 선택해 이동한다.

진행 중 run의 파일을 섞어 완성된 결과처럼 게시하지 않는다.
선택한 기준에서 읽을 수 있는 완료 산출물과 미완료 상태를 묶고, 기록이 바뀌면 안정된 기준으로 다시 빌드하거나 갱신 중임을 알린다.
빌드 시점의 지표 정의·관측·발견·초점을 고정한다. 예전 차트를 최신 정의나 최신 데이터로 조용히 연결하지 않는다.
보고서를 포함할 때는 선택한 `report_id + revision_id`와 그 버전의 근거를 유지한다. 빌드 시점이 더 늦어도 보고서의 분석 기준을 최신 상태로 바꾸지 않는다.
보고서 내용 버전과 `publication_id`는 별개다. 같은 보고서의 재게시나 공유 프로필 변경만으로 새 내용 버전을 만들지 않는다.
입력 변경·stale 판정도 확인 시점이 있는 관측이며 게시본이 계속 원본 파일을 감시하는 것처럼 표현하지 않는다.

자동 갱신은 이후의 선택 옵션이다. 설정한 게시 대상·공유 프로필로 새 스냅샷을 만들고 최신 주소를 바꾸는 방식으로 한다.
단순 페이지 새로고침과 구별하고, 모든 도구 호출마다 빌드·업로드하거나 모델을 호출하지 않는다.
게시를 설정하지 않은 프로젝트는 로컬에서 계속 분석한다.

## 4. 독립적인 공유 패키지

빌드 결과의 구조 예시:

```text
publication/
  index.html                 현재 분석 방향과 공유한 결과
  pages/                     지표·시각화·실행·발견·관계의 상세
  reports/                   선택한 보고서 버전의 본문·구성원·첨부
  assets/                    CSS·JS·차트·필요한 라이브러리
  evidence/                  선택해서 포함한 코드·표·검사 근거
  publication.json           빌드 기준·공유 범위·파일 목록·해시
```

실제 이름은 확정 API가 아니다. 모든 내부 링크·검색·관계 탐색은 패키지 안에서 해결되어야 한다.
게시 UI는 기본 영어 label을 사용하고 빌드에서 선택한 UI locale을 고정한다. 포함한 보고서 본문·시각화 제목은 원래 작성 언어를 유지한다.
로컬 사용자 경로, 원본 프로젝트로 나가는 `../`, symlink 바깥 대상, 원본 `.lab/`·`.venv/`에 기대지 않는다.
정적 `file://` 열기와 HTTP의 하위 경로에서 동작하고, 기본 차트·탐색에 원격 CDN·실행 중인 분석 서버를 요구하지 않는다.
Plotly 등 포함한 라이브러리의 버전과 재배포 고지도 함께 보존한다.

`publication.json`의 후보 내용:

| 항목 | 의미 |
|---|---|
| `publication_id`, format·renderer 버전 | 공유본의 정체성과 해석 방식 |
| `as_of_seq`, `context_version` | 포함한 기록 기준([ADR-0006](decisions/0006-common-record-contract.md) 5절, 모르면 null). `source_revision`은 같은 기계에서만 비교할 뜻이 있는 읽기 토큰이라 기준으로 남기지 않음 |
| `built_at`, `analysis_state` | 빌드 시각과 진행 중/완료 등 분석 상태. 검증·승인 상태와 별개 |
| 공유 프로필·포함 범위 | 선택한 지표·질문·run·발견·근거·보고서 버전과 제외한 범주의 설명 |
| 보고서 원본과 공유 표현의 대응 | 보고서·묶음 버전, 포함 파일 해시, 변환·가림이 있다면 원본 참조와 새 해시 |
| 파일 목록·내용 해시 | 패키지의 구성과 무결성 확인. 결론의 참이나 환경 재현 인증은 아님 |
| 독자 기능 | 읽기·검색·다운로드·상호작용 중 실제 제공하는 기능 |

공유본의 ID는 원래 기록과 대응할 수 있어야 한다. 공개되는 표시명·URL·매핑에도 선택한 공유 범위를 적용한다.
필수 파일이 누락되면 불완전한 빌드를 완료로 표시하지 않는다. 선택적으로 제외한 근거는 ‘이 게시본에 포함되지 않음’으로 표시한다.
원본에도 없는 과거 파일과 공유 설정으로 제외한 파일을 같은 이유로 표시하지 않는다.

큰 결과는 페이지·파일로 나누고 필요한 범위를 선택한다. 토큰 수치는 게시 크기나 정보의 강제 삭제 기준이 아니다.
같은 기록 기준·프로필·renderer로 다시 만들었을 때 콘텐츠 파일 집합과 해시를 비교할 수 있게 한다.
게시 시각·대상 주소 같은 전달 메타데이터는 계산 결과의 해시와 분리한다.

## 5. 공유할 내용은 선택하고, 선택한 만큼만 담는다

| 프로필 후보 | 포함할 내용 | 용도 |
|---|---|---|
| `read` | 목적·현재 지표·정의·질문·발견·차트·선택한 보고서·설명·관계 | 진행 상황 공유. 첫 기본값 후보 |
| `evidence` | read에 더해 선택한 코드 스냅샷·첨부 표·검사 결과·입력 정보 | 팀원의 계산·근거 검토 |
| 프로젝트 인계 | 분석을 이어 하는 데 필요한 데이터·코드·환경·원본 기록 | 별도 후속 범위. read/evidence 게시본을 실행 가능한 전체 프로젝트라고 부르지 않음 |

프로필 이름보다 실제 포함 목록이 기준이다. 미리보기에서 파일·데이터 범위·제외 항목·대략적인 크기를 확인한다.
원시 데이터 전체, 전체 세션 대화, 환경 자격 증명, telemetry·상세 로그, 로컬 절대 경로는 기본 공유 대상에 넣지 않는다.
코드·미리보기·오류 문자열에도 이런 정보가 포함될 수 있으므로 투영된 결과와 실제 패키지 모두를 검사한다.

숨긴 데이터가 HTML·inline JSON·검색 인덱스·다운로드 파일에 남아 있으면 제외한 것이 아니다.
지표·질문·근거의 일부를 제외할 때 그 관계도 공유 범위 안에서 다시 생성한다. 제외된 자료의 이름·내용을 tooltip 등으로 새지 않게 한다.
첨부 표가 요약 또는 일부 계열이면 그 범위를 표시한다. 코드·데이터가 빠진 read 게시본에서 완전 재현이 가능하다고 안내하지 않는다.
가려진 코드 발췌는 실행된 원본 스냅샷과 구별해 표시한다.
자유 형식 보고서에 이미 포함된 표·문장·이미지도 실제 공유 내용이다. 근거 링크나 메타데이터에서 제외해도 본문에 남으면 제외한 것이 아니다.
원본 파일을 그대로 포함할 수 없으면 검토한 별도 공유용 산출물을 만들거나 해당 파일을 제외한다. 가공 결과의 해시와 원본 보고서 버전을 연결하고 원본과 구별한다.

모델이 작성한 사용자 정의 HTML·외부 자원 의존 차트는 로컬 분석에서 계속 사용할 수 있다.
공유에서는 검증된 격리 보기 또는 정적 이미지 대체 등 지원 방식으로 다루고, 보존되지 않은 상호작용은 명시한다.
표준 그림으로 표현할 수 없다는 이유로 분석 자체를 제한하지 않는다. 공유 가능한 근거·그림·설명과 미포함 요소를 구별한다.

## 6. publish는 생성된 패키지를 전달한다

게시 대상은 사용자가 고른 공유 폴더·사내 정적 문서 경로·호스팅/스토리지 등의 설정으로 분리한다.
처음부터 모든 provider를 지원하거나 별도 분석 서버를 운영할 필요는 없다. 첫 구현은 하나의 검증된 대상부터 제공한다.
모델에게 대상별 업로드 도구를 모두 상시 노출하지 않고 기존 사람 명령과 설정을 통해 선택한다.
내부 구조는 [아키텍처](ARCHITECTURE.md)의 공통 Publisher 포트와 대상별 adapter를 따른다.
공유 범위를 선택하는 PublicationProjection과 파일을 전송하는 Publisher는 별도 책임이며, 어느 구현도 공통 범위·버전 검증을 생략하지 않는다.

게시 단위는 이미 만들어진 `publication_id`와 artifact 해시다. 업로드 중 내용이 바뀌도록 원본 프로젝트를 다시 읽지 않는다.
완료 기록에는 빌드 ID·대상·성공 시각·버전 주소·최신 주소·실제 확인한 접근 범위를 남긴다.
주소만 추측해서 성공으로 반환하지 않고 게시된 entry page와 참조 자원의 일치 여부를 확인한다.

동일 패키지·동일 대상으로 재시도하면 가능한 한 기존 게시 결과를 재사용한다.
새 버전은 staging에 전송·확인한 뒤 최신 주소를 전환한다. 실패하면 이전 성공 게시본을 유지한다.
프로젝트의 분석 실행·보고서 빌드·파일 전달·최신 주소 전환은 별도 상태와 재시도 단위다.
이 게시 계약은 임의 Python 분석의 외부 부작용까지 복구한다는 뜻이 아니다.

### 팀 접근과 게시 중단

팀 전용 접근은 실제 게시 대상의 권한 기능으로 제공한다. 화면의 ‘팀 전용’ 표시나 주소를 모른다는 사실만으로 비공개라고 부르지 않는다.
같은 정책이 HTML뿐 아니라 이미지·JS·첨부 표·코드 다운로드에도 적용되는지 확인한다.
해당 대상이 접근 제어를 지원하지 않으면 실제 공개 범위를 표시하고, 팀 전용 요구를 충족한 대상으로 안내하지 않는다.

게시 중단·이전 버전으로 전환·원격 사본 삭제는 지원 대상의 기능과 결과를 명시한다.
이미 전달된 ZIP이나 독자가 내려받은 사본을 회수할 수 있다고 약속하지 않는다.

### 첫 대상: 지정 폴더

2026-10-03에 채택한 설계이며 아직 구현하지 않았다([ADR-0009](decisions/0009-first-publish-target.md), [#21](https://github.com/handochan/aelix-analytics/issues/21)).
첫 대상은 사용자가 지정한 폴더 하나다. 로컬 폴더·마운트한 공유·동기화 폴더를 같은 폴더로 다루며, 대상은 프로젝트 밖이어야 한다.
대상 안에 버전 `publications/<publication_id>/`와 최신 주소 `projects/<channel>/`(`index.html`·`latest.json`)를 둔다. 버전은 한 번 쓰면 바꾸지 않는다.
대상 안의 `.staging/`에 전송하고 sha256·링크를 확인한 뒤 이름을 바꿔 버전을 확정하고, 마지막에 최신 포인터를 교체한다. 실패하거나 중단돼도 최신 주소는 확인을 마친 버전만 가리킨다.
같은 빌드의 재시도는 대상의 버전을 재사용하고, 같은 `publication_id`에 다른 내용은 거절한다. 되돌리기는 최신 주소를 이전 버전으로 바꾸는 것만 지원하며 버전 삭제는 사람이 한다.
접근 범위는 폴더의 권한이다. ‘팀 전용’으로 표시하지 않고, 게시 기록에는 실제로 확인한 것(게시한 계정의 다시 읽기, POSIX 권한 비트의 관찰)만 남기며 Windows ACL은 ‘확인 안 함’으로 적는다.
네트워크 볼륨의 잠금, 동기화 폴더의 전파 순서, 같은 대상의 동시 게시는 검증하지 않는 범위다.

## 7. 독자의 흐름과 이후 협업

프로젝트 공유형의 첫 화면은 **목적 → 현재 지표·질문 → 유효한 발견 → 포함된 근거 → 다음 확인**으로 시작한다.
보고서 중심 게시본은 선택한 본문 또는 묶음을 먼저 보여 주고, 작성 시점·분석 기준·버전과 포함된 근거로 이어진다. 공유하지 않은 프로젝트 내용을 첫 화면에 자동 추가하지 않는다.
진행 중 상태와 이 게시본의 시각·범위를 보이며 원본 프로젝트의 최신 상태처럼 오인되지 않게 한다.
근거·관계·이력으로 이동했다 돌아올 때 같은 지표·버전·카드 위치를 유지한다.
게시본에서 Python 실행이나 원본 프로젝트 수정은 제공하지 않는다.

팀원의 의견·질문·선택을 원래 분석으로 돌려보내는 기능은 후속 범위다.
이때는 `publication_id`, 원래 차트·지표 정의 버전, 선택 단위·데이터 기준을 함께 전달한다.
원본이 바뀌었으면 변경 여부를 알리고, 과거 게시본의 선택을 최신 데이터에 조용히 적용하지 않는다.
이를 [선택 기반 후속 분석](DESIGN-CONTINUITY-AND-REUSE.md#향후-선택-기반-후속-분석)의 F1·F2와 연결한다.
동시 편집·서버 실행·공유 메모리의 쓰기 조정은 별도 계약이며, 정적 게시만으로 제공되었다고 표시하지 않는다.

## 8. 도입 순서와 검증

| 단계 | 제공 범위 | 수용 기준 |
|---|---|---|
| P0: 공유 build | read/evidence의 포함 범위, 선택한 보고서·묶음 버전, 독립 폴더·ZIP, 진행 중 상태·고정된 근거 | 원본 경로가 없는 환경의 file/HTTP에서 링크·그림·관계·필요한 파일이 동작 |
| P1: 첫 publish 대상 | 사용자가 지정한 폴더 하나(로컬·마운트한 공유·동기화 폴더. [ADR-0009](decisions/0009-first-publish-target.md), 채택, 구현 전), 버전 주소·최신 주소와 게시 기록 | 다른 독자의 접근, 자원 일치, 실패 시 이전 버전 유지, 재시도와 대상 범위 확인. 네트워크 볼륨의 잠금·동기화 전파·동시 게시는 검증하지 않는 범위로 적음 |
| P2: 확장된 팀 게시 | 원격 provider, 실제 팀 접근 제어, 선택적 자동 갱신 | 대상별 접근·수명주기·갱신 일관성 시험 |
| P3: 피드백·인계 | 의견·질문·선택을 분석에 연결하거나 인계 패키지 제공 | 게시 당시 버전과 후속 실행·질문의 관계 보존 |

첫 베타 후보는 P0와 지원 대상을 명시한 P1이다. 외부 호스팅이 미구현이면 ZIP/폴더 전달과 구현된 대상만 안내한다.
P0·P1은 분석의 지표·맥락·관계와 함께 제공하며, 모든 원격 provider·협업 서버의 구현을 베타 조건으로 요구하지 않는다.

검증 사례는 진행 중 분석의 게시, 원본 폴더 이동·미존재, 인터넷 없는 열기, HTTP 하위 경로,
미포함 근거·누락 파일의 구별, Unicode 파일명, 지표 정의 변경 전후, 작업 중 기록 갱신, 업로드 중단·재시도,
이전 게시본 유지, HTML·raw payload·다운로드의 제외 범위, 사용자 정의 차트의 표시 범위를 포함한다.
보고서 v1을 게시한 뒤 로컬 v2 작성, 같은 v1의 재게시, 일부 컬럼만 포함한 묶음, 자유 본문에 제외 대상이 남는 경우도 검증한다.
실제 게시 대상에서 팀원에게 보여 준다는 검증과 로컬 링크 검사는 서로 다른 증거로 남긴다.
P1 폴더 대상의 검증 항목은 [ADR-0009](decisions/0009-first-publish-target.md)의 ‘구현에서 확인할 것’에 있다. CI의 두 번째 계정과 HTTP 하위 경로는 대리 증거이고, 실제 다른 독자의 열람은 [#24](https://github.com/handochan/aelix-analytics/issues/24) 리허설의 증거다.
