# 제품 효과 평가 설계 — 확장이 있을 때와 없을 때

- 상태: **채택(2026-10-31 소유자), 구현 전.** [베타 품질 기준](../BETA-QUALITY-GATES.md) §3의 모델 측정(12과제 × 3회 × 두 모델, 성공률 90%)을
  이 설계의 비교와 판단 규칙으로 바꿨다. 소유자가 정한 것은 13절에 있다. 측정은 10절의 단계로 한다.
- 작업: [#24](https://github.com/handochan/aelix-analytics/issues/24) 출시 리허설(B6)의 모델 측정.
- 따르는 결정(2026-10-31 소유자):
  - 같은 작업을 aelix-analytics가 있을 때와 aelix 순정(확장·kit 없음)으로 비교한다.
  - 모델은 상위 gpt-6.1-sol, 하위 Qwen3.8 27B(OpenRouter)다.
  - 판단 규칙과 수치는 측정 전에 정한다.
  - 평가는 분석 판단의 정오보다 제품의 약속(재개·근거·흐름 파악·분석 프로젝트의 사용성)을 재고, 개선할 곳을 찾게 한다.
- 기준 코드: main `644e080`. kit은 출시 후보 0.32.0(`26c28d0`)과 같다.

## 1. 왜 다시 설계하나

제품이 약속하는 것은 [제품 방향](../PRODUCT.md)의 "사용자가 얻어야 하는 것"과 "개선을 판단하는 기준"이다. 핵심은 네 가지다.
- 새 세션에서도 분석을 이어 간다.
- 모든 분석에 근거가 있고, 그 근거로 되돌아갈 수 있다.
- 에이전트가 분석의 흐름(목적·질문·판단과 그 변경)을 파악한다.
- 분석 프로젝트를 하기에 알맞은 사용성을 준다.

같은 문서는 "결론의 참을 자동 인증한다는 뜻은 아니다"라고 적는다.

지금의 측정(§3, 하네스는 [실제 모델 평가 안내](../../tools/model_eval_data/README.md))은 정답 대비 절대 성공률 하나를 본다. 2026-10-31의
시범 캠페인(두 모델 × 64 run, 아래 11절)에서 기본 조건의 자동 채점은 gpt-6.1-sol 22/36, Qwen 17/36이었다. 실패의 상당수는 제품의 약속과
거리가 있었다.
- **답 형식**: 분석은 대부분 맞았지만 답에 근거 ID를 적지 않았다(gpt의 근거 검사 실패 9). 그 ID는 모두 그 run이 받은 도구 결과에 있었다.
- **분석 판단**: 분모·기간·집계 키·주장 판정의 정오가 갈렸다. 모델의 역량이다.
- **정답의 엄격함**: T04는 "4,000자에서 잘렸다"를 요구한다. kit의 ID 읽기는 e74의 저장된 글 4,000자를 생략 없이 주고, 기록 목록은 글자 수를
  준다. 그러나 원래 더 길었다는 표시(잘림)는 주지 않는다. gpt는 세 번 모두 글이 문장 중간에서 끊겼다고 맞게 말했다. 길이까지 말한 한 번은
  확장을 두고 원시 기록(`journal.jsonl`)을 직접 읽어 셌다.

절대 성공률 하나로는 실패가 제품 탓인지 모델 탓인지 가를 수 없고, 제품이 무엇을 더해 주는지도 보이지 않는다.

## 2. 원칙

1. **비교한다.** 같은 모델·데이터·요청 글·제한 시간에서 조건만 바꾼다. 두 조건의 차이가 제품의 효과다.
   채점 기준의 엄격함은 두 조건에 똑같이 걸리므로 비교 결과를 흔들지 않는다.
2. **제품의 약속을 잰다.** 재개, 근거 추적, 판단 이력, 작업 축적, 비용, 분석의 자유도를 잰다(4절).
3. **분석 판단의 정오는 판정 기준이 아니다.** 확장이 판단을 나쁘게 만들지 않는지만 본다(E6).
4. **진단이 결과물이다.** 실패마다 제품 쪽 원인 후보를 자동으로 가리키고 사람이 확정한다(7절).
5. **미리 정한다.** 판단 규칙과 수치는 측정 전에 정한다. 정답이나 채점 규칙을 바꾸면 두 조건 모두 다시 채점한다.
6. **자동 채점은 필요조건이다.** 모델의 자기평가는 쓰지 않는다. `needs_review`는 에이전트의 1차 판단을 표로 내고 사람이 확정한다.

## 3. 조건

| 조건 | 무엇 |
|---|---|
| A 확장 | aelix 0.1.0b2와 aelix-analytics 확장. 지금 하네스의 `default` 표면(aelix 기본 도구 목록과 확장의 도구 6개)과 kit 프로젝트 |
| V 순정 | aelix 0.1.0b2의 기본 도구만(`aelix_status`·read·bash·edit·write·grep·find·ls). 확장도 kit(`analytics` 명령·SDK)도 없다. 같은 데이터와 같은 분석 라이브러리(프로젝트의 uv 환경)는 있다 |

- **모델**: 상위는 gpt-6.1-sol, 하위는 Qwen3.8 27B(OpenRouter)이고, 설정은 지금 하네스의 것이다(2026-10-30 소유자 결정 D1·D2).
  OpenRouter는 요청마다 상위 제공자와 양자화를 고를 수 있고, 지금 설정은 이를 고정하지 않는다. aelix의 기록에는 상위 제공자가 남지 않는다.
  그래서 A와 V를 번갈아 돌려 그 차이가 두 조건에 고르게 퍼지게 한다. 고정(aelix의 `openRouterRouting`)은 후속 선택지다.
- **지원 하단**: 로컬 Qwen(지원 하단 기준)은 `not_run`으로 남는다. BETA §7에 따라 출시 보류 사유이고, 출시 판정 때 소유자가 다시 본다(D2).
- **같게 두는 것**:
  - 요청 글. 요청 글은 도구 이름을 말하지 않는다.
  - 제한 시간, 작업 루트의 격리, `--no-context-files`, 비밀 검사.
  - 작업 루트의 준비(프로젝트 사본·환경)는 제한 시간과 비용에 넣지 않는다.
- **실행 순서**: A와 V를 같은 시간대에 번갈아 돌린다(2026-10-31 소유자). 시범 run은 다시 쓰지 않는다. 모델과 제공자가 바뀌어 생기는 차이를 줄이기 위해서다.
- **V의 현실성**: V는 이 확장이 없는 사용자의 현실이다. Part II에서는 분석을 여러 세션에 걸쳐 이어 간다는 사실을 두 조건 모두에 세션 1의
  요청 글로 똑같이 알린다(O1). Part I은 한 세션의 과제라 요청 글이 지금 그대로다.

### 정답의 형태

- **상태 사실**(재개·이력): fixture의 기록이나 앞 세션이 남긴 것에서 정해진다.
- **근거의 식별자**: Part I은 두 조건에 같은 기록·run ID가 있다. Part II의 V에는 kit의 ID가 없으므로, 두 조건 모두에서 파일 경로·스크립트
  이름·출력 파일도 근거로 인정한다. 그 목록은 E3에서 체인마다 정답에 적는다.
- **앞 세션 결과의 회수**(Part II): 정답은 데이터가 정하는 값(예: 같은 기간 비교 +20.6%)과 앞 세션이 실제로 말하거나 기록한 값이다.
  - 앞 세션이 그 값을 내지 못했으면 그 세션의 회수 검사는 "해당 없음"이다.
  - 세션 1의 완수는 E6(분석 결과)에서 따로 센다. 실패한 세션 1도 그 분모에 남는다.
- **분석 판단의 정오**: 지금 정답(T06–T10의 값)을 그대로 쓰되 E6에서만 쓴다.

## 7. 진단 — 개선할 곳 찾기

1. **정보 가용성.** 실패한 근거 검사와, 기록된 상태를 묻는 과제(E1–E3)의 실패한 사실 검사마다, 그 값이나 ID가 그 run에서 모델이 받은 도구
   결과(맥락 블록 포함)에 있었는지 본다. 모델이 계산해야 하는 값(E6)과 낱말로 판정하는 검사는 대상이 아니다.
   - 받았는데 답에 없음: 활용 문제다. 모델의 문제이거나, 결과가 길어 묻힌 것이다. 시범에서 gpt의 근거 ID 누락이 모두 이 경우였다.
   - 받지 못했지만 확장의 읽기로 얻을 수 있음: 발견 가능성 문제다(도구·설명).
   - 확장의 어떤 읽기로도 얻을 수 없음: 제품의 공백이다.

   "어떤 읽기로 얻을 수 있나"는 과제마다 fixture의 새 사본에서 kit의 읽기(맥락 블록, 상태, 정답의 ID 읽기)를 결정적으로 돌려 판정한다.
2. **도구 흐름.**
   - 조건별 도구 호출의 분포
   - A에서 확장을 두고 원시 파일을 읽은 호출과 그때 찾으려던 것
   - 같은 조회의 반복
   - 도구별 오류와 그 인자
3. **비용 분해.** 맥락 블록, 도구 결과, 재시도가 토큰의 어디를 차지하는지 본다.
4. **언어 이탈.** 요청의 언어와 다른 문자로 쓴 답을 센다.
5. **개선 후보 보고서.** 제품 부품(맥락 블록, 상태, 조회, 기록 도구, Workspace)별로 사례 수와 대표 run을 묶는다.
   소유자가 고른 것을 Issue로 만든다.

## 8. 판단 규칙(사전 등록)

모델마다 A와 V를 비교한다. 집계는 다음과 같다.
- **비율**: 규칙의 범위에 든 모든 run(반복 3회)과 검사를 합산한다(통과한 검사 수 / 검사 수).
- **과제별 비교**: 같은 방식으로 과제 하나의 반복 3회를 합산한다.
- **동점**: 두 조건이 모두 만점이면 "차이 없음"으로 통과로 본다(2026-10-31 소유자).

| 규칙 | 내용 | 상위 모델 | 하위 모델 |
|---|---|---|---|
| R1 재개 | E1·E3 과제와 Part II 재개 검사의 재개 정확도가 A ≥ V이고, 과제마다도 A ≥ V | 판정 | 판정 |
| R2 근거 | E2 과제와 Part II 근거 검사의 근거 연결률과 한계 표시가 A ≥ V(과제마다도). 없는 ID의 합은 A ≤ V | 판정 | 판정 |
| R3 맥락 오류 | 비교한 모든 과제와 세션에서 사람이 확정한 맥락 오류의 합이 A ≤ V | A = 0 | A ≤ V |
| R4 축적 | Part II 회수율이 A > V(엄격히), 중복 작업의 합은 A ≤ V | 판정 | 판정 |
| R5 해 없음 | E6 과제와 체인마다의 세션 1에서 답 성공 run 수가 A ≥ V − 1(반복 3회 중) | 판정 | 판정 |
| R6 비용 | 두 조건 모두 답 성공 run이 있는 과제·체인에서, 답 성공 run의 총 토큰(비캐시·캐시 입력과 출력) 중앙값이 A > 1.2 × V이면 이유를 적고 검토한다 | 보고 | 보고 |
| R7 절대 하한 | A의 재개 정확도(R1의 범위)와 회수율(R4)이 각각 2/3 이상 | 판정 | 보고 |

- **R4의 "해당 없음"**: 같은 체인·같은 반복의 짝에서 한쪽이라도 "해당 없음"인 회수 검사는 두 조건 모두에서 뺀다(2026-10-31 소유자). 뺀 수와
  그 이유(세션 1의 실패)는 따로 보고한다. 짝의 절반 넘게 빠지면 R4는 판정하지 않고 보류한다.
- **판정 상태**: 사람이 아직 확정하지 않은 맥락 오류에 기대는 규칙은 "잠정"이다. 데이터가 없는 규칙은 "미실행"이다.
- **통과**: 상위 모델이 R1–R5와 R7을, 하위 모델이 R1–R5를 만족하면 모델 게이트를 통과한다. "잠정"이나 "미실행"이 남으면 보류다.
- **보류**: 하나라도 만족하지 못하면 출시 보류 사유다. 진단(7절)의 제품 공백을 고친 뒤 다시 잰다.
- **출시와의 관계**: 모델 게이트의 통과는 출시의 필요조건이다. 지원 하단의 로컬 Qwen이 `not_run`인 동안은 BETA §7에 따라 출시 보류 사유가
  남는다(3절).
- **수치**: 2/3, 1.2배, 반복 1회분은 소유자가 측정 전에 확정했다(2026-10-31, O3).

## 9. 규모·비용·시간

- **Part I**: 14과제(판정 8, E6 6) × 3회 × 2조건 × 2모델 = 168 run이다. 모두 새로 돈다.
- **Part II**: 3체인 × 3세션 × 3회 × 2조건 × 2모델 = 108 세션이다.
- **토큰**:
  - 시범의 기본 조건(모델마다 36 run)의 두세 배를 본다.
  - 시범에서 Qwen 토큰의 87%가 T12(자유 EDA)였다. T12 run 9개의 평균은 비캐시 입력 0.37M, 캐시 입력 3.37M이었다.
  - 그래서 Part I의 T12와 Part II의 C1이 비용의 중심이 된다. Qwen은 그만큼 OpenRouter 크레딧이 들므로 실행 전에 확인한다.
- **시간**:
  - 하네스 구현과 시나리오 작성에 1–2일
  - 실행에 하루(두 모델을 병렬로)
  - 사람 확정(정답 확인, `needs_review`)에 소유자의 몇 시간
- **출시**: 이 평가가 끝날 때까지 기다린다(O5).

## 11. 시범 캠페인(2026-10-31)에서 배운 것

두 모델 × 64 run을 돌렸다. 후보 kit으로 돈 run이 모델마다 62개(기본 12과제 × 3회, Q5 제안 조건, Q11 도구 표면)이고, #9 이름 전환 전
비교(kit 0.2.0)가 2개다. 원자료는 이 기기의 run 디렉터리에 있다.

- **결과**: 기본 조건의 자동 채점은 gpt-6.1-sol 22/36, Qwen 17/36이었다. 아래 채점기 결함을 고친 뒤의 값이고, 사람 확정 전 값이다.
  Q17-b는 두 모델 모두 통과했다.
- **채점기 결함**: 둘을 고치고 모든 run을 다시 채점했다.
  - 중대 오판 검사가 물음표로 끝나는 줄을 모델의 질문으로 보고 건너뛰었다. 그래서 닫힌 질문을 그 질문의 글과 함께 열린 질문으로 나열한
    답(Qwen T01 r1)을 놓쳤다.
  - 문장 단위 검사가 인용 안의 마침표에서 문장을 끊었다. 그래서 e74의 길이와 잘림을 한 문장에 말하면서 그 마지막 글("…낮다. 센")을 인용한
    답(gpt T04 r3)을 실패로 채점했다.
- **휴리스틱 오판**:
  - 후보 kit의 124 run에서 중대 오판 검사가 발생한 run은 18이고, 실제 오판은 1이었다(Qwen T01 r1).
  - 나머지 17은 부정문, 비교표의 틀린 값 칸, 코드 주석을 잘못 읽은 것이었다. 그 가운데 14 run은 사람이 오판을 확정하면 성공이 된다.
  - 이름 전환 전 비교의 4 run에서는 2 run에서 발생했고, 둘 다 실제 오판이었다(gpt T01 r1, Qwen T01 r1: 닫힌 e56 등을 열린 질문으로 나열).
  - 새 설계는 맥락 오류를 사람이 확정하는 항목으로 두고, 1차 판단을 표로 낸다.
- **비밀 검사의 오탐**:
  - 모델이 돈 24 run에서 486개(조회 `cursor` 226, Visualization `token` 260)였다. 모두 kit 자신의 값이다.
  - 402로 끝난 21 run에서는 174개가 잡혔다. OpenRouter 오류 본문의 계정 ID(`user_id`)와 키 관리 주소의 키 식별자다. 자격 증명은 아니지만
    계정을 가리키는 값이라 가린 것이 맞고, 오탐으로 고치지 않는다.
- **비용**: T12가 Qwen 토큰의 87%를 차지했다.
- **운영**: OpenRouter 크레딧이 떨어져(402) 21 run이 끝났고, 충전한 뒤 21 run을 다시 돌렸다.
  - 20 run은 모델이 아무것도 하기 전에 거절됐다.
  - T12 requested r2는 도구를 46번 호출하고 토큰 1.7M을 쓴 뒤 거절됐다.
  - 실행 전에 예산을 확인한다.
- **언어**: Qwen은 T01 r3와 T03 r1을 거의 중국어로 답했고, 다른 답 9개에도 중국어 낱말이 섞였다. gpt는 T12 requested r3의 마지막 답을
  일본어로 했다. 언어 이탈은 진단 항목으로 둔다.
