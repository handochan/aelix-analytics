## 1. 목적과 경계

Workspace는 기록·관계·정확한 버전을 빠짐없이 보여 주지만 실제 화면에서 읽기 어렵다(#95 문제 목록).
이 설계는 같은 기록과 ReadModel 판정을 유지하면서 세 가지를 하는 화면을 정한다.

1. 현재 분석 상태를 한눈에 본다.
2. 근거를 데이터까지 끝까지 따라간다.
3. 무엇이 확인됐는지를 상태별로 따로 본다.

바꾸지 않는 것:

- **저장 형식.** journal·run·프로젝트 표식(`analytics.json`)·context 스냅샷에 새 기록 종류나 필드를 더하지 않는다. 버전 번호·흐름·출처 경로는 화면을 만들 때 계산하는 값이다.
- **판정.** 참조 상태·버전 결박·생산자·관측·재실행·record state는 ReadModel이 정한 값 그대로다. 화면은 판정을 다시 만들지 않고 표현만 바꾼다.
- **공개 이름.** CLI·SDK·모델 도구·환경 변수를 새로 만들지 않는다. 이 설계의 ReadModel 함수는 내부 함수다(§12의 열린 결정 3).
- **게시본.** 공유 build의 UI locale은 [PUBLICATION-BUILD](PUBLICATION-BUILD.md)대로 `en` 고정이다(#20·#21).
- **범위 밖.** 행 단위 계보, 선택 기반 후속 분석(F1·F2), Report 저장(#19), 판단 규칙 변경.

## 3. 문구 카탈로그와 언어 선택 (#96)

### 3.1 카탈로그

- `src/aelix_analytics/assets/i18n/en.json`이 kit 문구의 원본이다(key → English). `ko.json`은 같은 key의 한국어다.
  두 파일은 패키지 자료로 설치된다. `ko.json`에 없는 key는 영어로 보인다(용어집 §7 "누락한 번역은 영어로 대체").
- **key**: `영역.이름` 꼴의 안정된 식별자다(`tab.insights`, `ref.unbound`, `action.trace`, `label.version_of`).
  URL anchor·저장 값·JSON key와 무관하며, 번역 때문에 바뀌지 않는다.
- **값**: 글자와 `{name}` 자리표시자다. 수에 따라 달라지는 문구는 `{"one": "...", "other": "..."}`로 쓴다(한국어는 `other`만).
  값에 HTML을 넣지 않는다. 그리는 쪽이 escape한다.
- **링크가 든 문장**은 조각으로 나눈다(앞뒤 문구 key와 링크 key). 한국어 조사가 자리표시자 바로 뒤에 오는 문장은 만들지 않는다
  (예: `{place}(으)로 돌아가기` 대신 `돌아가기: {place}`).
- **날짜·시각**: 형식 key로 영어 `Aug 3, 23:46`, 한국어 `8월 3일 23:46`처럼 보인다. 데이터의 offset을 바꾸지 않고
  `<time datetime>`에 원래 시각을 둔다(용어집 §7 "날짜·수치 표시는 locale과 시간대·단위를 구별"). 용량 단위(KiB 등)는 그대로다.
- **번역하지 않는 것**: 사람·에이전트·스크립트가 쓴 글(`lang=""` 요소), 저장 값(kind·state·binding 등), 경로·ID·URL·anchor,
  CLI·SDK·도구 이름, 코드. 저장 값은 화면 문구(예: `Version not named`)와 따로 Details에 원문 그대로 남는다.

### 3.2 생성기

- 생성기는 지금처럼 영어로 그린다. 문서의 `lang`은 `en`이다.
- 바꿀 수 있는 kit 문구 요소는 `data-i18n="key"`를 갖는다. 자리표시자 값은 `data-i18n-args`(JSON), 속성 문구는
  `data-i18n-attr`(`aria-label`·`title`·`placeholder`와 key)에 둔다.
- 생성기는 두 카탈로그를 `workspace/assets/i18n.js` 하나로 쓴다(`window.AelixI18n = {en, ko}`). 페이지는 `<script src>`로 읽는다.
  `file://`에서도 fetch 없이 동작하고, 페이지마다 카탈로그를 넣지 않는다.
- 카탈로그 내용은 Workspace의 변경 판정(fingerprint)에 들어가, 카탈로그만 바뀌어도 다시 그린다.

### 3.3 브라우저

- **언어 결정 순서**: URL 상태의 `lang` → 저장된 선택(localStorage, 접근 실패는 무시) → 문서 기본(`en`).
- **적용**: `[data-i18n]` 요소의 글자와 속성, `<html lang>`, 문서 제목, 언어 메뉴를 갱신한다. 스크립트가 나중에 넣는 알림 등도 같은 함수를 쓴다.
- **저장소가 막혔을 때**: #18의 URL 상태 codec에 `lang`을 더해 내부 링크로 다음 페이지에 넘긴다.
- **언어 메뉴**: 상단 막대의 `<select>`이고, 이름표는 "Language · 화면 언어"다. 선택지는 각 언어로 쓴다(English, 한국어).
  JS가 없으면 메뉴를 숨기고 영어로 보인다.
- **사람이 쓴 글**: 언어와 관계없이 `lang=""`를 유지한다. 프로젝트 글의 언어를 추정하지 않는다(용어집 §7).
- 첫 그림 전에 적용하도록 본문 끝에서 동기적으로 실행한다. 언어 전환의 깜박임과 시간은 #96에서 잰다.

### 3.4 프로젝트 기본 언어 — 열린 결정

#95 본문은 '프로젝트 기본 언어'를 적었다. 그대로 하려면 `analytics.json`(`analytics.project/2`, 기록 schema의 `project_2`)에 선택 필드를 더해야 한다.

비용과 성격:
- 표식은 기록 schema의 일부다. 그래서 리뷰 예산의 기록 형식 PR이 되고, 계약·schema와 설정 명령(새 공개 이름)이 함께 필요하다.
- 화면 언어는 사람마다 다를 수 있는 표시 설정이다(같은 프로젝트를 영어 사용자와 함께 볼 수 있음).

**권장**: 이번에는 프로젝트 설정을 두지 않는다. 기본은 영어이고, 사람의 선택은 브라우저에 기억하며, 저장소가 막히면 URL로 넘긴다.
JS 없는 화면의 기본 언어나 프로젝트 기본값이 필요해지면 별도 결정으로 다룬다. 이 결정이 바뀌어도 바뀌는 것은 생성기의 기본 언어뿐이다.

### 3.5 검증과 문서

- 생성된 HTML이 쓰는 모든 key가 `en.json`에 있다. `ko.json`의 key는 `en.json`의 부분집합이고 자리표시자 이름과 복수형 모양이 같다.
- `tests/test_language.py`는 한국어를 `assets/i18n/ko.json`과 그 파일로 만든 `i18n.js`에만 허용한다.
  Workspace HTML은 영어로 그리므로 지금처럼 `lang=""` 밖에 한국어가 없어야 한다.
- Node 시험: 전환·되돌리기, 새로고침, 저장소 차단과 URL 전달, 자리표시자·복수형, 나중에 넣은 알림.
- 용어집 §7 '현재 구현'과 [현재 계약](../CONTRACTS.md)의 Workspace 설명을 같은 PR에서 고친다.

## 4. 종류와 상태 표현 (#97–#100 공통)

출처 그래프·분석 지도·Overview 요약·버전 페이지가 같은 표현을 쓴다. 토큰은 `workspace.css`에 둔다.

| 종류 | 색 토큰 | 모양 | 종류 이름(카탈로그 key) |
|---|---|---|---|
| 데이터 파일(가져온·파생) | 청록 `--kind-data-*` | 둥근 사각형 | `Imported data`·`Derived data` |
| run | 남보라 `--kind-run-*` | 육각형(`clip-path`) | `Run`. 스크립트와 코드 스냅샷을 함께 적음 |
| 시각화 버전 | 보라 `--kind-viz-*` | 둥근 사각형 | `Visualization`과 `v1 of 2` |
| 인사이트(발견·결정·가정 등) | 초록 `--kind-insight-*`와 기록 종류 점 | 둥근 사각형 | `Finding` 등 기록 종류 |

- **상태는 종류 색과 따로 표시한다.** 아이콘과 글자 배지(`Unchanged`, `Changed since read`, `Missing`, `Succeeded`, `Failed`)로 보이고,
  읽은 뒤 바뀐 파일에는 주황 테두리를 더한다. 색만으로 구분하지 않는다.
- **종류 이름**을 상자 위에 써서 색을 구분하기 어려워도 읽힌다.
- **`forced-colors`**에서는 run의 육각형 대신 테두리와 종류 이름으로 구분한다.
- **대비**: 글자는 4.5:1 이상, 아이콘·테두리는 3:1 이상이다.

## 5. 버전 기록 (#99)

### 5.1 공통 표현

모든 버전 대상이 같은 순서와 기호를 쓴다.
- '버전 n/N · 시각'
- 시간축 띠: ○ 버전, ● 보고 있는 버전, 작은 점은 같은 내용을 다시 쓴 것, ×는 실패한 run
- 바뀐 이유 배지와 같은 원인 묶음·접기
- 버전별 사용처
- 최신 버전 안내

시간축은 정적 SVG이고, 같은 내용을 목록으로도 둔다. **번호는 생성할 때 계산하는 표시 값이다.** 주소·인용·URL은 기존 식별자(run ID, sha256,
스냅샷 파일 이름)를 쓴다. 기록이 늘어도 기존 버전의 번호는 바뀌지 않는다(처음 나타난 시각 순서).

### 5.2 대상별 기준

| 대상 | 새 버전이 생기는 때 | 순서 | 버전별 사용처 | 원천 |
|---|---|---|---|---|
| 시각화 | 성공한 run이 같은 시각화 key를 만들 때 | run 시작 시각 | 그 버전을 정확히 인용한 기록 | `visualization_versions(key)`, `references()` |
| 데이터 파일 | 성공한 run의 출력 중 같은 경로의 다른 sha256. 같은 바이트를 다시 쓰면 같은 버전(재기록) | 처음 쓴 시각 | 그 sha256을 입력으로 기록한 run | run 출력·입력, 지금 파일의 hash |
| 가져온 데이터 | 가져오기 기록의 바이트와, run이 읽은 다른 sha256(가져오기 밖의 변경) | 처음 본 시각 | 읽은 run | 가져오기 기록, run 입력 |
| 스크립트 코드 | run이 기록한 다른 `script.sha256` | 처음 실행 시각 | 그 코드의 run과 그 run들이 만든 시각화·데이터 버전 | run의 `script`, 코드 스냅샷 |
| CONTEXT.md | 맥락 스냅샷 | 스냅샷 시각 | 그 버전이 최신이던 동안 쓴 인사이트 수 | context 버전(`.analytics/context/`) |
| 기록 정정·철회 | 정정·철회 기록이 원래 기록을 대체할 때 | 기록 순서 | 인용한 기록 | record state. 번호 없이 정정 이력으로 표시 |

**실패한 run** 은 버전이 아니며 시간축에 ×로만 둔다.

**묶음**:
- 시각화·데이터: 같은 코드 hash와 같은 입력 hash로 이어진 버전을 묶는다.
- 코드: 같은 hash가 이어진 run을 한 구간으로 묶고, 예전 hash로 돌아가면 그 번호를 다시 쓴다("v1 again").
- CONTEXT: 고정(pin) 섹션이 바뀌지 않은 버전을 묶는다.

**최신 안내**: 최신 버전을 아직 아무도 인용·사용하지 않았으면 그 사실과 마지막으로 사용된 버전을 알린다.

시안 9행의 예(fixture M):
- `t10_delivery_delay`: 19번 쓰여 14개 버전이 됐고, 최신 v14는 아직 어떤 run도 읽지 않았다.
- `s10_delivery_delay.py`: 코드 버전 3개. v2가 실패한 뒤 v1로 돌아갔다.
- CONTEXT.md: 13개 버전. 고정 섹션은 v2 이후 그대로다.

**사용처의 의미**: 사용처 수는 사실 집계다. 결론의 근거 강도가 아니다(용어집 §6).

### 5.3 ReadModel과 페이지

- **ReadModel 함수**: 데이터 파일·스크립트 코드·CONTEXT.md·시각화의 버전 이력 함수를 더한다. 반환값은 판정과 집계(dict)이며 HTML이 아니다.
  기존 함수와 같은 기준 seq에서 결정적이다.
- **시각화**: 선택 버전 페이지와 카드에 둔다(시안 6행).
- **데이터 파일**: 데이터셋 페이지에 둔다.
- **CONTEXT.md**: Context 페이지에 둔다(지금의 diff 목록을 버전 목록으로 바꾼다).
- **스크립트 코드**: 스크립트 페이지를 새로 만든다. 경로마다 하나다(fixture S 22개).
- **긴 이력**: 묶음을 접어 보이고, 한 페이지의 목록 행이 100개를 넘으면 이어 보기 페이지로 나눈다.

## 6. 출처 추적 (#100)

### 6.1 무엇을 보여 주나

**출발점**: 선택한 기록·시각화 버전·run.

**출처 방향(Where it comes from)**: 다음 순서로 가져온 데이터에 닿거나 생산자가 없을 때까지 따라간다.
1. 인용: 기록 → run 또는 시각화 버전
2. 그 run의 입력 데이터
3. 그 데이터를 만든 생산자 run
4. 다시 2로

각 run이 만든 시각화 버전은 곁가지로 보인다. 사용처 방향(What uses it)과 양방향(Both)은 같은 규칙으로 반대쪽을 따라간다.

| 연결 | 판정 원천 | 선 |
|---|---|---|
| 기록 → run·시각화 버전 | `references(source)`의 상태·결박·basis | 점선: 기록에 적힌 인용 |
| run → 입력 데이터 | run의 입력 기록과 `observation(run, "input", path)` | 실선: 실행 중 관측 |
| 입력 데이터 → 생산자 run | `producer(run, path)`: resolved·ambiguous·none·unknown, basis observed·inferred | 실선(observed). 옛 kit 경로로만 찾은 inferred는 따로 표시 |
| run → 시각화 버전 | run이 기록한 시각화 | 실선 |

**노드 상태**:
- 데이터: 그 run이 읽은 바이트와 지금 파일의 관계(그대로·읽은 뒤 바뀜·없음)
- run: status
- 인용: 참조 판정

**판정이 하나로 정해지지 않는 경우**:
- 생산자 후보가 여럿이면 후보를 모두 갈래로 보이고 'Several possible sources'로 적는다.
- 순환은 표시하고 그 지점에서 멈춘다. 같은 run에 두 길로 닿으면 한 번만 그린다.

### 6.2 '확인할 수 있는 것'

경로 옆에 다음을 **따로** 보인다. 하나의 판정이나 점수로 합치지 않는다([PRODUCT](../PRODUCT.md), 용어집 §6).

| 줄 | 원천 |
|---|---|
| 인용 | 출발점 참조의 판정(정확한 버전·버전 미지정·인용 뒤 바뀜·없음) |
| run | 경로의 run 성공 수 |
| 코드 보존 | 각 run의 코드 스냅샷 파일을 다시 hash해 기록된 `script.sha256`과 같은지 확인한다. 저장 형식을 바꾸지 않는 파생 확인이다 |
| 가져온 데이터 | 경로 끝 데이터의 관측 상태 |
| 중간 데이터 | 파생 데이터의 관측 상태(읽은 뒤 바뀐 파일과 바꾼 run) |
| 재실행 비교 | `run_reproduction`의 판정. 비교하지 않았으면 'Not run' |
| 분석 검사·결론 검토 | 지금 기록 형식에 전용 기록이 없어 'None recorded'. 없는 기능을 동작하는 버튼처럼 보이지 않는다(DESIGN-CONTINUITY §5) |

페이지에는 "기록된 run 입력과 인용을 따라간 경로이며, 결론의 증명이나 행 단위 계보가 아니다"를 적는다(용어집 §5).

### 6.3 크기와 순서

- **[DESIGN-CONTINUITY §5](../DESIGN-CONTINUITY-AND-REUSE.md#각-요소의-관계-그래프)의 기본 1-hop 이웃**은 'All relations' 탭(#18의 관계 페이지)에 그대로 둔다.
- **'Provenance' 탭**은 소유자 요청(2026-10-14)으로 출처 방향의 여러 단계를 기본으로 보인다. 초기 예산 20 nodes/30 edges 안에서 가까운 단계부터 그린다.
  - 넘는 단계는 '다음 단계' 정적 페이지로 이어 본다(한 페이지 최대 50 nodes/100 edges).
  - 생략한 노드·선의 수를 적는다.
  - 입력이 많은 run(예: 503개)은 한 줄로 접고 수를 적는다.
- **순회**: 단계(깊이) 순이다. 같은 단계 안은 참조 순서와 run의 입력 기록 순서를 따라 결정적이다.
- **글 목록**: 같은 순서의 문장이 같은 내용을 담는다. JS 없이 읽히고, 키보드·화면 낭독기·좁은 화면의 기본 표현이다.
  모바일은 세로 경로다(시안 7-C).

### 6.4 페이지와 읽기

- **탭 배치**: #18의 선택 버전 페이지(`relations/<id>-<n>.html`)에 'Provenance'·'All relations'·'History' 탭을 둔다.
  출처 경로가 있는 대상(인용이 있는 기록, run, 시각화 버전)은 'Provenance'가 기본이다. 새 페이지 종류를 만들지 않는다.
- **ReadModel**: 출처 읽기 함수를 더한다(출발점·방향·예산 → 노드·선·생략 수·순환·확인 줄).
  - 기존 판정(`references`, `observation`, `producer`, `upstream`, `run_reproduction`)을 조합하며 새 판정은 없다.
  - 같은 결과를 CLI·SDK·에이전트가 읽게 할 공개 방식은 §12의 열린 결정 3이다.
- **배치**: 출발점을 맨 아래에 두고 단계별로 위로 쌓는다. 곁가지(다른 입력, 시각화)는 좌우에 둔다.
  상자는 실제 DOM이고 선은 SVG다(#18과 같음). 외부 배치 라이브러리는 쓰지 않는다.

## 7. Overview 상태 요약과 분석 지도 (#98)

### 7.1 Overview

**현재 분석 방향**(맨 위)

**분석 상태 6칸**: 칸마다 따로 보이고 하나의 점수로 합치지 않는다.

| 칸 | 내용 | 원천 |
|---|---|---|
| 근거 연결 | 인사이트 중 정확한 버전 인용·버전 미지정·인용 뒤 바뀜·인용 없음 | 인사이트의 `references()` 판정 |

**그 밖의 구성**
- 분석 지도 요약: 가져온 데이터 → run → 시각화 → 인사이트 4칸이며, §4의 종류 색을 쓴다.

### 7.2 분석 지도 탭

- **노드**: 스크립트 하나와 그 run들이다(run 육각형). 노드에 run 수, 최근 run 상태, 시각화 수, 인용한 인사이트 수(정확한 인용 수 포함), 가져온 데이터 입력을 적는다.
- **선**: 한 스크립트의 run이 쓴 파일을 다른 스크립트의 run이 읽은 관계다(`producer` 판정, 경로와 바이트). 파일 이름을 선 위의 데이터 칩으로 보인다.
  - 생산자 후보는 확정 연결이 아님을 적는다.
  - 같은 스크립트 안의 연결(재실행)은 선으로 그리지 않는다.
- **흐름**: 선으로 이어진 스크립트 묶음이다. run 수가 많은 순으로 주요 흐름 3개를 펼치고, 나머지는 수와 함께 한 줄로 접는다.
- **표시**: 최근 run 실패, 읽은 뒤 바뀐 입력, 생산자 후보 여러 개, 순환을 표시한다.
- **배치**: 흐름마다 가장 긴 경로 기준 단계로 열을 나누고, 같은 열은 이름순으로 둔다(결정적). 정적 HTML·SVG다.
- **글 목록**: 같은 내용을 글 목록으로 둔다.
- 탭 이름 'Analysis map'은 §12의 열린 결정 2다.
