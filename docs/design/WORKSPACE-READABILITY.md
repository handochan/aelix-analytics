## 1. 목적과 경계

Workspace는 기록·관계·정확한 버전을 빠짐없이 보여 주지만 실제 화면에서 읽기 어렵다(#95 문제 목록).
이 설계는 같은 기록과 ReadModel 판정을 유지하면서 세 가지를 하는 화면을 정한다.

1. 현재 분석 상태를 한눈에 본다.
2. 근거를 데이터까지 끝까지 따라간다.
3. 무엇이 확인됐는지를 상태별로 따로 본다.

바꾸지 않는 것:

- **저장 형식.** journal·run·프로젝트 표식(`analytics.json`)·context 스냅샷에 새 기록 종류나 필드를 더하지 않는다. 버전 번호·흐름·출처 경로는 화면을 만들 때 계산하는 값이다.
- **판정.** 참조 상태·버전 결박·생산자·입력 상태·재실행·record state는 ReadModel과 [계약 E](../CONTRACTS.md#e-계산-규칙)가 정한 값 그대로다. 화면은 판정을 다시 만들지 않고 표현만 바꾼다.
- **공개 이름.** CLI 명령·SDK 함수·모델 도구·환경 변수를 새로 만들지 않는다. 출처 읽기의 공개 방식은 §12의 결정 3이다(2026-10-17).
- **게시본.** 공유 build의 UI locale은 [PUBLICATION-BUILD](PUBLICATION-BUILD.md)대로 `en` 고정이다(#20·#21).
- **범위 밖.** 행 단위 계보, 선택 기반 후속 분석(F1·F2), Report 저장(#19), 판단 규칙 변경.

## 3. 문구 카탈로그와 언어 선택 (#96)

### 3.1 카탈로그

- **파일**: `src/aelix_analytics/assets/i18n/en.json`이 kit 문구의 원본이다(key → English). `ko.json`은 같은 key의 한국어다.
  - 두 파일은 패키지 자료로 설치된다.
  - `ko.json`에 없는 key는 영어로 보인다(용어집 §7 "누락한 번역은 영어로 대체").
- **key**: `영역.이름` 꼴의 안정된 식별자다(`tab.insights`, `ref.unbound`, `action.trace`, `label.version_of`).
  URL anchor·저장 값·JSON key와 무관하며, 번역 때문에 바뀌지 않는다.
- **값**: 글자와 `{name}` 자리표시자다.
  - 수에 따라 달라지는 문구는 `{"one": "...", "other": "..."}`로 쓴다(한국어는 `other`만).
  - 값에 HTML을 넣지 않는다. 그리는 쪽이 escape한다.
- **자리표시자의 값**: 수·kit의 짧은 값(ID 포함)만 둔다. 문구 요소는 `a`, 속성은 `data-i18n-<속성>-args`에 JSON으로 둔다.
  - 사람·스크립트가 쓴 글(데이터셋 이름, 제목, 경로)은 자리표시자 값으로 넘기지 않는다.
  - 그런 글은 그 자리의 자식 `<span lang="">` 요소로 남고, 번역은 그 요소를 옮길 뿐 글자로 바꾸지 않는다.
  - 그래서 사람이 쓴 글은 언어와 관계없이 `lang=""`이고, 영어 요소의 속성에 들어가지 않는다.
- **링크가 든 문장**은 조각으로 나눈다(앞뒤 문구 key와 링크 key).
- **조사**: 한국어 조사가 자리표시자 바로 뒤에 오는 문장은 만들지 않는다(예: `{place}(으)로 돌아가기` 대신 `돌아가기: {place}`).
- **날짜·시각**: 형식 key(`time.date.<월>`)로 영어 `Aug 3, 2026 23:46`, 한국어 `2026년 8월 3일 23:46`처럼 보인다.
  - 데이터의 offset을 바꾸지 않고, `<time datetime>`에 원래 시각을 둔다(용어집 §7 "날짜·수치 표시는 locale과 시간대·단위를 구별").
  - 날짜 제목 아래에 시각만 적는 곳(`23:46`)은 언어마다 같으므로 표시를 붙이지 않는다.
  - 용량 단위(KiB 등)는 그대로다.
- **번역하지 않는 것**
  - 사람·에이전트·스크립트가 쓴 글(`lang=""` 요소)
  - 저장 값(kind·state·binding 등): 화면 문구와 따로 Details에 원문 그대로 남는다
  - 경로·ID·URL·anchor
  - CLI·SDK·도구 이름, 코드

### 3.2 생성기

- 생성기는 지금처럼 영어로 그린다. 문서의 `lang`은 `en`이다.
- 바꿀 수 있는 kit 문구는 `<k-w>` 요소다. HTML이 모르는 요소라 스타일이 없는 inline 요소이고, 스크립트가 없어도 같은 글로 읽힌다.
  - 값이 없고 영어 글로 번역 하나를 가리키는 문구는 key 없이 쓴다(`<k-w>Evidence</k-w>`). 스크립트가 영어 글로 key를 찾아 요소에 남긴다.
  - 그 밖의 문구는 `k`(key)와 `a`(값)를 가진다(`<k-w k="…" a='{"n":3}'>`).
  - 속성 문구는 `data-i18n-<속성>`(`title`·`aria-label`·`placeholder`)에 같은 규칙으로 key를 적거나 비워 둔다. 스크립트가 넣는 문구는 `data-i18n`을 쓴다.
  - #96에서 처음 쓴 `<span data-i18n="key">`는 첫 HTML을 S·M에서 28–37% 늘렸고, `.crumbs span`·`.badge span` 스타일에 걸렸다. 그래서 위처럼 바꿨다.
- 생성기는 두 카탈로그를 `workspace/assets/i18n.js` 하나로 쓴다. 이 파일은 전역 `AnalyticsI18n`을 정한다(지금의
  `AnalyticsWorkspaceState`와 같은 이름 규칙). 페이지는 `<script src>`로 읽으므로 `file://`에서도 fetch 없이 동작하고,
  페이지마다 카탈로그를 넣지 않는다.
- 카탈로그 내용은 Workspace의 변경 판정(fingerprint)에 들어가, 카탈로그만 바뀌어도 다시 그린다.

### 3.3 브라우저

- **언어 결정 순서**
  1. 저장소가 동작하면 저장된 선택이 우선한다. 저장 키는 `analytics-language`이며 지금의 `analytics-live`와 같은 규칙이다.
  2. 저장된 선택이 없으면(저장소가 막힌 경우 포함) URL 상태의 `lang`을 쓴다.
  3. 둘 다 없으면 문서 기본(`en`)이다.
- **URL 상태와 복귀**: #18의 URL 상태 codec에 `lang`을 더한다. 스크립트가 만드는 모든 내부 이동(목록·상세 링크와 복귀·Escape·Back이 되살리는 origin)에 지금 언어를 실어,
  상세 페이지에서 언어를 바꾸고 돌아가도 옛 언어로 되돌아가지 않게 한다.
- **적용**
  - `<k-w>`·`[data-i18n]` 요소의 글자, 표시한 속성, `<time datetime>`, `<html lang>`, 문서 제목을 갱신한다.
  - 스크립트가 나중에 넣는 알림 등도 같은 함수를 쓴다.
  - 한국어 화면에서 번역이 없어 영어로 남는 요소에는 `lang="en"`을 붙인다. 속성은 언어를 따로 적을 수 없으므로, 속성에 쓰는 key는 모두 번역한다.
  - 저장소가 막히면 Back/Forward는 그 history 항목의 언어로 보인다(불러올 때와 같은 순서로 다시 고른다).
- **언어 메뉴**: 스크립트가 `i18n.js`로 상단 막대에 만든다.
  - 생성된 HTML에는 메뉴의 한국어가 없고, JS가 없으면 메뉴도 없다(그때는 영어로 보인다).
  - 메뉴의 이름표는 "Language · 화면 언어"이고, 선택지는 각 언어의 이름(English, 한국어)이다.
  - 각 이름은 그 언어로 표시한다(`lang="en"`·`lang="ko"`). 언어를 아는 kit 문구이므로 `lang=""`로 두지 않는다.
- **사람이 쓴 글**: 언어와 관계없이 `lang=""`를 유지한다. 프로젝트 글의 언어를 추정하지 않는다(용어집 §7).
- **첫 그림**: `<head>`의 스크립트가 `<html lang>`을 먼저 정한다. 영어가 아니면 파서가 요소를 넣는 대로 글자를 바꾼다.
  - 요소 뒤에 다음 노드가 들어온 뒤에 바꾼다. 그때는 글자가 다 들어와 있다. 본문 끝의 스크립트가 페이지 전체를 다시 적용한다.
  - #96 측정(headless Chrome, S/M 첫 페이지): 본문 끝에서만 바꾸면 첫 그림 뒤 약 190ms 동안 영어가 보였다.
    지금은 첫 프레임까지 읽힌 단어 480여 개 중 5개만 영어다.

### 3.4 프로젝트 기본 언어 — 결정(2026-10-15)

#95 본문은 '프로젝트 기본 언어'를 적었다. 그대로 하려면 `analytics.json`(`analytics.project/2`, 기록 schema의 `project_2`)에 선택 필드를 더해야 한다.

- **비용**: 표식은 기록 schema의 일부다. 그래서 리뷰 예산의 기록 형식 PR이 되고, 계약·schema와 설정 명령(새 공개 이름)도 함께 필요하다.
- **성격**: 화면 언어는 사람마다 다를 수 있는 표시 설정이다. 같은 프로젝트를 영어 사용자와 함께 볼 수 있다.

**결정**(소유자, 2026-10-15): 프로젝트 기본 언어는 영어다. 프로젝트 설정은 두지 않는다.
- 생성한 화면은 영어이고, JS가 없어도 영어로 읽힌다.
- 사람의 선택은 브라우저에 기억하고, 저장소가 막히면 URL로 넘긴다(#96).
- 프로젝트마다 다른 기본값이 필요해지면 별도 결정으로 다룬다. 그때 바뀌는 것은 생성기의 기본 언어뿐이다.

## 4. 종류와 상태 표현 (#97–#100 공통)

출처 그래프·분석 지도·Overview 요약·버전 페이지가 같은 표현을 쓴다. 색은 `workspace.css`의 지금 종류 토큰(`--k-*`)을 잇는다.

| 종류 | 색 | 모양 | 종류 이름(카탈로그 key) |
|---|---|---|---|
| 데이터 파일(가져온·파생) | `--k-import` 계열 | 둥근 사각형 | `Imported data`·`Derived data` |
| run | `--k-run` 계열 | 육각형(`clip-path`) | `Run`. 스크립트와 코드 스냅샷을 함께 적음 |
| 시각화 버전 | 새 토큰 `--k-viz` | 둥근 사각형 | `Visualization`과 `v1 of 2` |
| 인사이트(발견·결정·가정 등) | 그 기록 종류의 토큰(`--k-finding` 등) | 둥근 사각형 | `Finding` 등 기록 종류 |

- **`--k-viz`**: 지금의 어느 `--k-*` 색과도 겹치지 않게 고른다. 특히 `--k-decision`(남보라)과 `--k-run`(파랑)과 다르게 한다.
  run 상자에 남보라를 쓴 시안의 색은 결정의 점과 겹치므로 따르지 않는다.
- **강조 색**: `--k-run`은 지금 강조색(`--accent`)과 같은 파랑이다. 그래서 선택·포커스 표시는 강조색만으로 하지 않고 두께와 글자를 함께 쓴다.
- **상태는 종류 색과 따로 표시한다.**
  - 배지는 아이콘과 글자다: `Unchanged`, `Changed since read`, `Missing`, `Unknown`, `Succeeded`, `Failed`.
  - 읽은 뒤 바뀐 파일에는 주황 테두리를 더한다. 색만으로 구분하지 않는다.
- **종류 이름**을 상자 위에 써서, 색을 구분하기 어려워도 읽힌다.
- **`forced-colors`**에서는 run의 육각형 대신 테두리와 종류 이름으로 구분한다.
- **대비**: 글자는 4.5:1 이상, 아이콘·테두리는 3:1 이상이다.
- **문서**: 화면 문구가 바뀌는 상태 이름(예: `Version unbound` → `Version not named`)은 그 PR에서 [계약 E](../CONTRACTS.md#e-계산-규칙)와 용어집 §6의 표시 문구를 함께 고친다.

## 5. 버전 기록 (#99)

시안: [6-B](workspace-readability/6-B-visualization-versions.webp), [6-C](workspace-readability/6-C-versions-card.webp), [9-A](workspace-readability/9-A-data-versions.webp), [9-B](workspace-readability/9-B-code-versions.webp), [9-C](workspace-readability/9-C-context-versions.webp), [9-D](workspace-readability/9-D-version-rules.webp).

### 5.1 공통 표현

모든 버전 대상이 같은 순서와 기호를 쓴다.
- '버전 n/N · 시각'
- 시간축 띠: ○ 버전, ● 보고 있는 버전, 작은 점은 같은 내용을 다시 쓴 것, ×는 실패한 run
- 바뀐 이유 배지와 같은 원인 묶음·접기
- 버전별 사용처
- 최신 버전 안내

시간축은 정적 SVG이고, 같은 내용을 목록으로도 둔다.

**번호는 생성할 때 계산하는 표시 값이다.** 주소·인용·URL은 기존 식별자(run ID, sha256, 스냅샷 파일 이름)를 쓴다.
기록이 늘어도 기존 버전의 번호는 바뀌지 않는다. (구현 #99: 시작 순서로 세므로, 먼저 시작한 run이 뒤에 시작한 run보다 늦게 끝나면 뒤의 번호가 밀린다. 계약 C15)

### 5.2 대상별 기준

| 대상 | 새 버전이 생기는 때 | 버전별 사용처 | 원천 |
|---|---|---|---|
| 시각화 | 갤러리와 같은 규칙: 성공 run이 같은 시각화 key를 만들 때. 재실행 run은 빼고 같은 순서로 센다 | 그 버전을 인용한 기록 | 계약 E "차트 버전", `references()` |
| 데이터 파일 | 성공 run의 출력 중 같은 경로의 다른 sha256. 처음 쓴 순서로 센다. 같은 바이트를 다시 쓰면 같은 버전(재기록) | 그 sha256을 입력으로 기록한 run(기록 방식 구별, §6.1) | run 출력·입력, 지금 파일의 hash |
| 가져온 데이터 | 가져오기 기록의 바이트와, run이 기록한 다른 sha256(가져오기 밖의 변경) | 그 sha256을 기록한 run | 가져오기 기록, run 입력 |
| 스크립트 코드 | run이 기록한 다른 `script.sha256`. 처음 실행한 순서로 센다 | 그 코드의 run과 그 run들이 만든 시각화·데이터 버전 | run의 `script`, 코드 스냅샷 |
| CONTEXT.md | 맥락 스냅샷. 스냅샷 순서로 센다 | 그 버전이 최신이던 동안 쓴 인사이트 수 | `core.context_versions`(`.analytics/context/`와 옛 `.lab/context/`) |
| 기록 정정·철회 | 정정·철회 기록이 원래 기록을 대체할 때 | 인용한 기록 | record state. 번호 없이 정정 이력으로 표시 |

**재실행**:
- 재실행 run은 새 번호를 받지 않는다. 다시 실행한 버전 옆에 재실행 표시와 비교 판정(`run_reproduction`)으로 둔다.
- 참조 판정은 [ADR-0006](../decisions/0006-common-record-contract.md)대로 재실행 run의 버전도 후보로 센다(계약 E). 재실행 버전을 인용한 기록은 그 재실행 표시 아래에 보인다.
- 카드·이력·출처 노드는 모두 위의 같은 버전 집합과 번호를 쓴다.

**실패한 run**:
- 시각화·데이터 파일의 버전을 만들지 않고, 시간축에 ×로 둔다.
- 코드는 실행 전에 스냅샷을 남긴다. 그래서 실패한 run의 코드 hash도 코드 버전이 되고 '실패' 표시를 단다([시안 9-B](workspace-readability/9-B-code-versions.webp)의 v2).
- 완료되지 않은 run은 어느 버전도 만들지 않는다.

**묶음**:
- 시각화·데이터: 같은 코드 hash와 같은 입력 hash로 이어진 버전을 묶는다.
- 코드: 같은 hash가 이어진 run을 한 구간으로 묶고, 예전 hash로 돌아가면 그 번호를 다시 쓴다("v1 again").
- CONTEXT: 고정(pin) 섹션이 바뀌지 않은 버전을 묶는다.

**최신 안내**: 최신 버전을 아직 아무도 인용·사용하지 않았으면 그 사실과 마지막으로 사용된 버전을 알린다.

**[시안 9행](workspace-readability/README.md#9행-다른-버전-기록)의 예**(fixture M):
- `t10_delivery_delay`: 19번 쓰여 14개 버전이 됐고, 최신 v14는 아직 어떤 run도 읽지 않았다.
- `s10_delivery_delay.py`: 코드 버전 3개. v2가 실패한 뒤 v1로 돌아갔다.
- CONTEXT.md: 13개 버전. 고정 섹션은 v2 이후 그대로다.

**사용처의 의미**: 사용처 수는 사실 집계다. 결론의 근거 강도가 아니다(용어집 §6).

### 5.3 ReadModel과 페이지

- **ReadModel 함수**: 데이터 파일·스크립트 코드·CONTEXT.md·시각화의 버전 이력 함수를 더한다. 반환값은 판정과 집계(dict)이며 HTML이 아니다.
  - 기록에서 오는 값(버전 번호·묶음·사용처)은 같은 기록 입력(journal·run 기록)에서 같다.
  - 지금 파일과 비교한 값(지금 파일이 어느 버전인지, 읽은 뒤 바뀜)은 읽은 때의 관측이다.
    페이지는 지금처럼 읽은 기준(`as_of_seq`, `source_revision`)을 함께 적는다([ADR-0006](../decisions/0006-common-record-contract.md) §5).
- **시각화**: 선택 버전 페이지와 카드에 둔다([시안 6행](workspace-readability/README.md#6행-시각화-버전)).
- **데이터 파일**: 데이터셋 페이지에 둔다.
- **CONTEXT.md**: Context 페이지에 둔다. 지금의 diff 목록이 버전 목록이 된다.
- **스크립트 코드**: 경로마다 스크립트 페이지를 새로 만든다(fixture S 22개).
  #18의 복귀 상태는 정해진 디렉터리의 페이지만 받으므로(`workspace-state.js`의 `safePage`), 새 디렉터리를 그 목록과 시험에 더한다.
- **긴 이력**: 묶음을 접어 보인다. 한 페이지의 목록 행이 100개를 넘으면 이어 보기 페이지로 나누고, 그 페이지 수를 §9에 센다.
- **구현(#99)**
  - 시각화의 '선택 버전 페이지'는 그 버전을 만든 run 페이지의 차트다. 새 시각화 페이지를 만들지 않아 페이지 수는 스크립트 페이지만 는다.
    갤러리 카드는 `vN` 배지와 접은 띠, 최신 버전의 run 페이지로 가는 `Version history`다(전의 `Earlier versions:` 날짜 링크 대신).
  - 긴 이력: 이어 보기 페이지 대신, 시각화 이력의 버전과 실패한 run이 100개를 넘으면 최신이 아닌 버전의 run 페이지는 그 버전에 가까운 100개만 보이고 전체는
    최신 버전의 run 페이지에 둔다(run 페이지마다 전체를 두면 버전 수의 제곱으로 커진다). 데이터셋·스크립트·Context 페이지는 대상마다 한 페이지라 모두 보인다.
  - 묶음의 경계: 실패한 run이 사이에 있으면 같은 코드·입력이라도 묶음을 나눈다(시각화와 데이터가 같은 규칙. 시안 9-A는 나누지 않았다).
  - CONTEXT의 '그 버전일 때 쓴 인사이트'는 시각이 아니라 journal 순서로 센다: 그 버전의 완료 기록 뒤, 다음 버전의 완료 기록 전의 발견·결정·가정.
    스냅샷 이름의 시각은 오프셋이 없어 기록의 시각과 비교할 수 없다. 완료 기록이 없는 버전은 수를 적지 않는다.
  - 데이터 버전의 사용처는 읽은 run이고, 실패한 run의 읽기도 따로 적는다. 시안 9-A의 'Compare versions'·'Trace' 버튼과 버전 선택 메뉴는 없다
    (선택은 목록의 `Open` 링크, Trace는 #100).
  - 정정 이력은 관계 페이지의 `Correction history`다(정정으로 이어진 기록이 있을 때만, 이 기록의 앞뒤 10개).
  - 재실행은 코드 구간을 만들지 않는다(예전 run을 다시 실행해도 코드가 돌아간 것이 아님). 카드의 띠는 최근 40개다.

## 6. 출처 추적 (#100)

시안: [7-B](workspace-readability/7-B-provenance.webp), [7-C](workspace-readability/7-C-provenance-mobile.webp).

### 6.1 무엇을 보여 주나

**출발점**: 선택한 기록·시각화 버전·run·데이터셋(#95 범위 2).

**출처 방향(Where it comes from)**: 출발점에서 가져온 데이터에 닿거나 더 갈 곳이 없을 때까지 다음을 되풀이한다.
1. 기록의 인용: run·시각화 버전·데이터·다른 기록
2. run의 입력 데이터
3. 그 데이터의 생산자 후보 run(같은 바이트를 출력한 run)
4. 다시 2로

- 각 run이 만든 시각화 버전은 곁가지로 보인다.
- 기록이 다른 기록을 인용하면 그 기록의 인용으로 이어 간다.
- 데이터셋에서 시작하면 지금 바이트의 생산자 후보부터 따라간다.

**사용처 방향(What uses it)**: 데이터·run·시각화 버전에서 시작해 반대로 따라간다.
- 그 바이트를 입력으로 기록한 run
- 그 run이 만든 시각화
- 그것을 인용한 기록

두 방향은 각각 따로 그린다. 양쪽을 한 번에 보는 것은 'All relations' 탭의 한 단계 이웃이 맡는다.

| 연결 | 판정 원천 | 선 |
|---|---|---|
| 기록 → run·시각화 버전·데이터·기록 | `references(source)`의 상태·결박·basis | 점선: 기록에 적힌 인용 |
| run → 입력 데이터 | run의 입력 기록(`inputs[].via`)과 입력 상태 | 실선. 기록 방식을 구별한다(아래) |
| 입력 데이터 → 생산자 후보 run | `producer(run, path)`: resolved·ambiguous·none·unknown, basis observed·inferred | 실선. 같은 바이트의 출력이라는 관측이며 확정 연결이 아니다. 옛 kit 경로로만 찾은 inferred는 따로 표시 |
| run → 시각화 버전 | run이 기록한 시각화 | 실선 |

**입력의 기록 방식**: [계약](../CONTRACTS.md)의 run 기록 `inputs[].via`대로 선과 글 목록에서 구별한다.
- 실행 중 읽기(`polars.*`·`duckdb.*`·`analytics.read`·`analytics.scan`·`analytics.sql`)는 'read'다. sha256은 읽은 시점의 내용이다.
- 정적 탐지(`scan`)와 선언(`declared`)은 'found by scan'·'declared'다. sha256은 run 시작 때의 내용이며, run이 그 파일을 읽었다는 뜻이 아니다.
- 한 입력에 여러 방식이 있으면 실행 중 읽기를 앞에 둔다.

**노드 상태**:
- 데이터: 계약 E의 입력 상태와 같은 규칙이다(run 페이지와 같음). `same`·`changed`·`missing`, 그리고 해시 없음·디렉터리·URI의 `unknown`.
  같은 run이 읽고 다시 쓴 파일은 `same`이다.
- run: status.
- 인용: 참조 판정.

**판정이 하나로 정해지지 않는 경우**:
- 생산자 후보가 여럿이면 후보를 모두 갈래로 보이고 'Several possible sources'로 적는다.
- 순환은 `upstream()`이 알리는 순환 그대로 표시하고 그 지점에서 멈춘다. 같은 run에 두 길로 닿으면 한 번만 그린다.

### 6.2 '확인할 수 있는 것'

경로 옆에 다음을 **따로** 보인다. 하나의 판정이나 점수로 합치지 않는다([PRODUCT](../PRODUCT.md), 용어집 §6, AGENTS).

| 줄 | 원천 |
|---|---|
| 인용 | 출발점 참조의 판정. 확정 연결(`confirmed`)·버전 미지정·인용 뒤 바뀜·없음 등 |
| run | 경로의 run 성공 수 |
| 코드 보존 | 각 run의 `code_snapshot` 참조 판정(ADR-0006, 모듈 스냅샷 포함) |
| 가져온 데이터 | 경로 끝 데이터의 입력 상태 |
| 중간 데이터 | 파생 데이터의 입력 상태. 읽은 뒤 바뀐 파일에는 지금 바이트를 출력한 run 후보를 적는다. 같은 바이트라는 관측이며 확정 연결이 아니고, 없으면 'No matching run output' |
| 재실행 비교 | `run_reproduction`의 판정. 비교하지 않았으면 'Not run' |
| 분석 방법 검사 | 지금 기록 형식에 전용 기록이 없어 'None recorded' |
| 결론 검토 | 지금 기록 형식에 전용 기록이 없어 'None recorded' |

- 기록이 없는 상태는 없는 기능을 동작하는 버튼처럼 보이지 않는다(DESIGN-CONTINUITY §5).
- 페이지에는 "기록된 run 입력과 인용을 따라간 경로이며, 결론의 증명이나 행 단위 계보가 아니다"를 적는다(용어집 §5).

### 6.3 크기와 순서

- **'All relations' 탭**: [DESIGN-CONTINUITY §5](../DESIGN-CONTINUITY-AND-REUSE.md#각-요소의-관계-그래프)의 기본 1-hop 이웃(#18의 관계 페이지)을 그대로 둔다.
- **'Provenance' 탭**: 소유자 요청(2026-10-14)으로 출처 방향의 여러 단계를 기본으로 보인다. 사용처 방향도 같은 탭에서 따로 고른다.
  - 방향마다 초기 예산 20 nodes/30 edges 안에서, 가까운 단계부터 그린다.
  - 예산을 넘으면 그 경계의 노드(run·시각화 버전·기록·데이터셋)에 '여기서 이어 보기' 링크를 단다. 링크는 그 노드의 선택 버전 페이지로 간다.
    그 페이지는 이미 생성되므로 새 페이지가 생기지 않는다.
  - 생략한 노드·선의 수를 적는다. fixture M에서 예산을 넘는 경로는 일부다(설계 독립 리뷰의 대략 계산으로 인용 2,356개 중 약 32개). #100에서 정확히 센다.
  - 입력이 많은 run(예: 503개)은 한 줄로 접고 수를 적는다.
- **순회**: 단계(깊이) 순이다. 같은 단계 안은 참조 순서와 run의 입력 기록 순서를 따라 결정적이다.
- **글 목록**: 같은 순서의 문장이 같은 내용을 담는다. JS 없이 읽히고, 키보드·화면 낭독기·좁은 화면의 기본 표현이다.
  모바일은 세로 경로다([시안 7-C](workspace-readability/7-C-provenance-mobile.webp)).

### 6.4 페이지와 읽기

- **탭 배치**: #18의 선택 버전 페이지(`relations/<id>-<n>.html`)에 'Provenance'·'All relations'·'History' 탭을 둔다.
  출처 경로가 있는 대상(인용이 있는 기록, run, 시각화 버전, 데이터셋)은 'Provenance'가 기본이다.
- **페이지 수**: 새 페이지 종류는 만들지 않는다. 늘어나는 것은 기존 관계 페이지 안의 그림과 글 목록의 크기다(§9).
- **ReadModel**: 출처 읽기 함수를 더한다(출발점·방향·예산 → 노드·선·생략 수·순환·확인 줄).
  - 기존 판정(`references`, 입력 상태, `producer`, `upstream`, `run_reproduction`, `code_snapshot`)을 조합하며, 새 판정은 없다.
  - 결과의 결정성은 §5.3과 같은 기준이다.
  - 같은 결과를 CLI·SDK·에이전트에 주는 방식은 §12의 3에서 정했다.
- **배치**: 출발점을 맨 아래(사용처 방향은 맨 위)에 두고 단계별로 쌓는다. 곁가지(다른 입력, 시각화)는 좌우에 둔다.
  상자는 실제 DOM이고 선은 SVG다(#18과 같음). 외부 배치 라이브러리는 쓰지 않는다.

### 7.1 Overview

**분석 상태 6칸**: 칸마다 따로 보이고, 하나의 점수로 합치지 않는다. 수는 ReadModel 판정과 같아야 한다(#98 수용 조건).

| 칸 | 내용 | 원천 |
|---|---|---|
| 근거 연결 | 인사이트를 가장 강한 인용 하나로 센다: 확정 연결(`confirmed`) → 결박 없이 맞음(resolved, 확정 아님) → 버전 미지정 → 인용 뒤 바뀜 → 없음·모호·알 수 없음·지원 안 함 → 인용 없음. 칸은 인사이트마다 하나씩 세고, 상세 목록은 모든 인용을 보인다 | 인사이트의 `references()` 판정, `confirmed` |
| 실행 | 성공·실패 run 수 | run `status` |
| 입력 변경 | 입력이 직접 바뀐 run의 시각화 수와, 생산자 후보만 stale인 시각화 수를 따로 | `Freshness`, 계약 E "stale" |
| 열린 항목 | 열린 질문·다음 할 일 | record state |
| 재실행 비교 | 비교한 run 수와 결과. 없으면 'Not run' | `run_reproduction` |
| 분석 방법 검사 · 결론 검토 | 두 줄로 따로 보인다. 각각 기록이 없으면 'None recorded' | 전용 기록 종류 없음(§6.2) |

**그 밖의 구성**
- 분석 지도 요약: 가져온 데이터 → run → 시각화 → 인사이트 4칸이며, §4의 종류 표현을 쓴다.
- 긴 목록은 6개와 '모두 보기'로 보인다. 최근 활동·기록 범위는 기본으로 접는다. 탭에 개수를 적는다.
- **구현(#98)**
  - 한 문장 요약 대신 수의 두 줄이다(일·기간, 인사이트와 종류별 수). 영어의 단수·복수와 한국어 어순을 한 문장 틀로 맞출 수 없어서다.
  - 근거 연결 칸은 지금의 인사이트(C1의 핵심 정보: 닫히지 않고 `current`)를 센다. 정정·철회된 기록의 근거는 지금의 판단이 아니어서다. 상태를 바꾸는 참조(`supersedes`·`updates`·`resolves`)는 근거로 세지 않는다.
  - 첫 목록의 이름은 'Current findings and decisions' 대신 `Current insights`다(가정도 들어 있음). 나머지는 Insights 탭과 새 목록 페이지 `lists/open-<n>.html`(열린 항목)로 잇는다.
  - 머리의 Goal은 그 섹션을 통째로(600자까지) 보이고, 현재 방향 패널은 그 섹션 하나만 빼고 고정 섹션을 600자까지 보인다. 분석 초점은 질문과 지표 id만 보이고 나머지는 맥락 탭과 기록에 있다.
  - 최근 시각화는 Visualizations 탭과 같은 카드 3개다.

### 7.2 분석 지도 탭

- **노드**: 스크립트 하나와 그 run들이다(run 육각형). 노드에 다음을 적는다.
  - run 수와 최근 run 상태
  - 시각화 수
  - 인용한 인사이트 수(확정 연결 수 포함)
  - 가져온 데이터 입력
- **선**: 한 스크립트의 run이 쓴 파일을 다른 스크립트의 run이 입력으로 기록한 관계다(`producer` 판정, 경로와 바이트).
  - 파일 이름은 선 위의 데이터 칩으로 보인다.
  - 생산자 후보는 확정 연결이 아님을 적는다.
  - 같은 스크립트의 run 사이 연결은 선으로 그리지 않는다.
- **흐름**: 선으로 이어진 스크립트 묶음이다. run 수가 많은 순으로 주요 흐름 3개를 펼치고, 나머지는 수와 함께 한 줄로 접는다.
- **표시**: 최근 run 실패, 입력이 직접 바뀐 run, 생산자 후보 여러 개, 순환을 표시한다.
  - '순환'은 run 수준에서 `upstream()`이 알리는 순환이다.
  - 스크립트 단위로 모으면 순환이 없어도 A↔B가 생길 수 있다(A1 → B1 → A2: 되풀이한 분석). 이것은 순환이 아니라 '서로 주고받음'으로 적는다.
- **배치**
  - 서로 닿는 스크립트 묶음(강한 연결 요소)을 한 단계로 접은 뒤, 가장 긴 경로 기준 단계로 열을 나눈다.
  - 묶음 안과 같은 열은 이름순이다(결정적).
  - 정적 HTML·SVG다.
- **글 목록**: 같은 내용을 글 목록으로 둔다.
- **탭 이름**: 'Analysis map'(한국어 '분석 지도'). 소유자가 정했다(2026-10-17, §12의 2).
- **구현(#98)**
  - 주요 흐름은 run 수가 많은 셋이고, 같으면 그 스크립트들의 run을 인용한 인사이트가 많은 쪽이다. 보이는 순서는 흐름의 처음 run 시각이다(fixture S에서 k → s01 → s04, 시안과 같음).
  - 상자는 고정 크기(13 × 10rem)이고 화살표는 같은 rem 좌표의 SVG다. 그래서 글자를 키워도 화살표가 상자에 닿는다. 열이 많은 흐름은 그 상자 안에서 가로로 넘긴다.
  - 파일 칩은 화살표 위에 두어 화살표 끝이 보인다. 열을 건너뛰는 화살표는 상자 사이 틈으로 지나간다.
  - 상자의 '입력 바뀜'은 그 스크립트의 지금 시각화를 만든 run과 마지막 성공 run 기준이다(실패한 run의 시각화는 기록에 남아도 갤러리에 들지 않음). Overview의 입력 변경 칸과 같은 run을 본다.
  - 순환 표시는 run 수준 순환의 구성원만이다. 위쪽에서 순환을 만나기만 한 스크립트에는 붙이지 않는다. 점선 화살표는 생산자 후보가 둘 이상의 스크립트 run일 때다.
  - 그림은 상자 목록 하나를 CSS로 그린 것이다. 40em 아래에서, 넓은 화면에서는 'Read the map as a list'를 펼치면(JS 없이 `:has()`로 동작) 같은 목록이 차례로 보이고, 상자마다 쓴 파일과 그 파일을 읽는 상자를 글로 적는다.
  - 작은 흐름은 펼치면 스크립트마다 한 줄이다(첫 HTML 크기, §9). 스크립트가 아주 많으면 첫 HTML이 스크립트 수만큼 커지는 한계는 #110이 다룬다.
  - 시안의 'Main flows · All scripts' 단추 대신 나머지 흐름을 `<details>`로 접는다(JS 없이 동작). 상자를 골라 run·파일·인용을 따라가는 동작은 #100(출처 추적)이 한다.
